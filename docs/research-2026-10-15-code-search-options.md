# Endless weighs symbol-name search over graph tools

> **Status: exploratory research, not a plan.** Written 2026-10-15; most facts were gathered on 2026-10-14. Nothing here is decided, and this document authorizes no work. It records options, evidence and the current leaning so that later decisions have something to stand on. Where it says "the direction under consideration" or "an option", that is all it means. A Claude Code session reading this as a reference should not treat any part of it as a task, a requirement or an acceptance criterion.

The thinking has moved from "adopt a code-graph tool" to "give Claude a few precise, symbol-name lookups built on Go's own tooling." An earlier pass compared six popular graph tools and recommended Codebase Memory MCP (CBM) behind Endless's hooks. Further evidence showed that independent, controlled gains from such tools on current models are modest: a point or two of resolve rate and single-digit to low-double-digit percentage savings, concentrated in large repos and cheaper models. Go, with explicit imports and greppable identifiers, is close to the worst case for a graph tool's marginal value. The option now being explored is a small set of Endless-provided commands with language-neutral names (`endless def`, `endless refs`, `endless callers`, `endless impls`). These take **symbol names rather than file:line:col positions**, which is the point that motivates the idea, since most gopls CLI navigation verbs are position-based. Possible backings are the gopls CLI, or a two-layer index: a fast syntactic layer from `go/parser`/`go/ast` stored in SQLite and keyed by git blob SHA so worktrees share main's rows, plus a type-aware layer from `go/packages`/`go/types` or scip-go on demand. A crowded field of Go-written tools already covers much of this (notably cymbal and gosymdb). Trying or contributing to one of them is a live alternative to building, and building as an independent tool that Endless calls is a third. Two concerns stay open whichever way it goes: whether Claude will actually use the commands without being pushed by hooks, and how a multi-language version would work if Endless becomes a product.

**Scope and corrections.** Mike's own code is Go, plus some Python he plans to remove. PHP is not a requirement for his code (an earlier brief said Go+PHP, which was wrong). Multi-language support matters only for Endless as a potential product, where users would likely want Python, TypeScript, Rust, Zig and others. **Sourcing caveat:** the GitHub web UI and REST API were blocked during research, so repos were cloned and read directly. Star, issue and contributor counts are therefore **largely missing or from unverified third-party trackers**.

## Controlled evidence shows small gains that strong models erode

No independent, multi-run benchmark compares any of the popular graph tools against plain Claude Code, and none exists on Opus 5 or 5.5. The large numbers ("62% fewer tokens", "120x", "63x") are vendor-measured narrow Q&A tasks. Code Review Graph's own README calls its baseline "an upper bound no real agent pays" ([CRG README](https://github.com/tirth8205/code-review-graph/blob/main/README.md)). The controlled evidence is an order of magnitude smaller. An LSP ablation in SWE-Master raised resolve rates by **1.4–2.0 points** and cut turns 3–6% ([arXiv 2602.03411](https://arxiv.org/html/2602.03411v1)). ContextBench (1,136 tasks) found that "agents with more elaborate retrieval scaffolding did not reliably beat" a simple baseline, and Claude had the best Pass@1 with a plain scaffold ([arXiv 2602.05892](https://arxiv.org/html/2602.05892v1)). Cursor's A/B test with a real control group found semantic search raised code retention **+0.3% overall but +2.6% on codebases above 1,000 files** ([Cursor, 2025-11-06](https://cursor.com/blog/semsearch)). CBM's own paper reports about 10x fewer tokens per question, but answer quality **fell to 0.83 against 0.92** for grep/read exploration ([arXiv 2603.27277](https://arxiv.org/html/2603.27277v1)). In a 500-trial eval, the bare-shell baseline had the best correctness, and MCP cost more than 6x on complex tasks ([Arize, 2026-05-01](https://arize.com/blog/mcp-vs-cli-skills/)). Anthropic's Claude Code team dropped RAG for agentic grep, though on "internal vibes" rather than a published benchmark ([OfficeChai, 2025-05-27](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/)).

No study holds a tool fixed while the model improves, so "shrinking benefit" is inferred, not measured. The single-run YouTube comparison that started this discussion (CodeGraph saving ~35% on Opus 5, then ~10% on Opus 5.5) fits that pattern but sits inside normal run-to-run noise. Where tools do help, the evidence points to large repos, concept queries where names are unknown, cross-package "who calls X / what breaks" questions, and cheaper models such as Haiku or Sonnet subagents. That last category, impact and caller questions, is exactly what type-aware Go tooling answers precisely and grep answers poorly. That is part of why the leaning moved toward narrow precise commands rather than broad graph context.

### Why the earlier "adopt CBM via hybrid" recommendation is superseded

The first report recommended CBM as the index engine, called through its CLI (`codebase-memory-mcp cli <tool> --format json`) from Endless hooks, with Claude Code's gopls LSP plugin as a precision layer. CBM was picked on fit: a single native binary, MIT, no telemetry, an external cache and JSON from every tool. That reasoning was sound for "which graph tool," but the discussion changed the question. The evidence above shows only modest independent gains, and **CBM's own paper traded answer quality for tokens**. CBM rates its own Go accuracy one tier below its best languages ("Good 75–89%"), using a C reimplementation "structurally inspired by" gopls rather than gopls itself ([README](https://github.com/DeusData/codebase-memory-mcp#hybrid-lsp)). Go's real type checker is available from Go, for free. CBM also pays a full index per worktree path. It has an exact-version admission barrier, under which all CBM processes on an account must run the same build or the newcomer "fails before doing work". And every merge needs one owner's approval ([MAINTAINERS.md](https://github.com/DeusData/codebase-memory-mcp/blob/main/MAINTAINERS.md)). An always-on injection layer would add context on every turn for a benefit that may be small on a mid-size Go repo. The earlier recommendation also leaned on CBM's PHP support, which turned out to be irrelevant to Mike's code. CBM remains a reasonable thing to benchmark against if a benchmark is ever run; it is not the default under consideration.

All performance claims are self-reported; for example, cymbal reports 10–40 ms for most queries.

Older tools are not agent-ready. guru survives only at deprecated tags, gogrep is unmaintained, and go-callvis is a visualizer. `golang.org/x/tools/cmd/callgraph` is maintained, but it takes package patterns, not symbol names ([golang/tools](https://go.googlesource.com/tools)).

**gosymdb is close to the type-aware half of the idea, and cymbal is close to the syntactic half plus worktree awareness plus Claude Code hooks.** Neither combines both layers. The gap none of them fills is narrower than it first looked:

- **Index sharing across many short-lived worktrees.** cymbal builds a full index per worktree and federates lookups; gosymdb ignores worktrees. None documents content-addressed rows that a fresh worktree reuses from main.
- **Both layers in one tool**, with each answer labelled syntactic or type-verified.
- **A stable, permissively licensed library API.** gosymdb disclaims stability, and gopher-mcp has no license.

One option before building anything is to try cymbal and gosymdb hands-on against Endless's own repo. Another is to contribute the missing piece, either worktree-delta indexing or a `go/types` layer, to one of them. Both are cheaper than a new tool if either project is receptive. The counter-risk is that both are young, and depending on a single-author 2026 project carries the same bus-factor concern raised about CBM.

### gopls is moving toward name-based queries, slowly

`gopls mcp` remains "experimental". Its default tools are `go_workspace`, `go_package_api`, `go_diagnostics`, `go_rename_symbol`, `go_symbol_references`, `go_search`, `go_file_context` and `go_vulncheck`. It still has **no MCP go-to-definition, implementations or call hierarchy**, and `go_symbol_references` takes a name relative to a file's import scope ([mcp.go](https://go.googlesource.com/tools/+/refs/heads/master/gopls/internal/mcp/mcp.go); [gopls MCP docs](https://tip.golang.org/gopls/features/mcp)). On the CLI, `definition`, `references`, `implementation` and `call_hierarchy` all take `file:line:col`. `workspace_symbol <query>` is name-based, with fuzzy and case-sensitive matchers. The v0.23.0 notes describe "an ongoing effort to revamp the `gopls` CLI (which is not a supported stable interface) to make it more useful and efficient for both humans and agents" ([v0.23.0 notes](https://go.googlesource.com/tools/+/refs/heads/master/gopls/doc/release/v0.23.0.md)). A new **`gopls inspect <target>`** landed on master on 2026-10-07 (commit abf1056, golang/go#80874). It takes symbol names such as `gopls inspect -pkg go/ast Decl` and returns definition, hover docs and signature with `-json`. The commit says target queries are "designed to replace the need for users to specify definition spans (file+line+col)." It is unreleased, and which release will ship it is unverified ([golang/tools](https://go.googlesource.com/tools)). The Go team is visibly closing the name-vs-position gap, but today only definition/hover is name-based, and only on master.

## The symbol-name CLI option and its backing choices

The direction under consideration is a handful of Endless commands that take a symbol name (`Store.Save`, `store.Open`, `github.com/x/y/store.Open`), resolve it, and return compact results with file:line. The names are language-neutral so the same verbs could later front other languages. Bare names will be ambiguous in any real repo, so qualification syntax and disambiguation output are design questions. gopls's own forms (`Foo`, `lib.Bar`, `T.M`, `lib.T.M`) are one precedent.

| Command | gopls CLI backing | Index backing |
|---|---|---|
| `endless def` | `gopls inspect` (unreleased), or `workspace_symbol` then `definition` | Syntactic layer alone (go/ast declarations) |
| `endless refs` | Resolve name to a position, then `references` | `go/types` `Info.Uses`, or scip-go occurrences |
| `endless impls` | Resolve, then `implementation` | `go/types` method sets / `types.Implements` |
| `endless callers` | Resolve, then `call_hierarchy` | Static + CHA call graph from x/tools |

**Option A: wrap the gopls CLI.** It is the least code and always exact, because it is the type checker. Endless would turn a name into a position, via `workspace_symbol` today or `inspect`/`resolve_target` later, and then call the positional verb. `-remote=auto` lets CLI invocations share a gopls daemon instead of cold-loading each time; the daemon address is "specific to the executable" ([golang/tools cmd.go](https://go.googlesource.com/tools)). gopls's persistent per-package file cache can be shared by multiple instances ([Go Blog, 2023-09-08](https://golang.google.cn/blog/gopls-scalability)), which softens cold starts in new worktrees. The downsides are that the CLI is explicitly not a stable interface, each worktree is a distinct gopls view (so memory multiplies across worktrees, untested), and every query pays a round trip. **gopls is also a poor bulk-export producer for a database.** It has no dump command, its internals live under `internal/`, and filling SQLite would mean one positional query per symbol. If Endless wants rows in its own SQLite, gopls is the wrong source.

**Option B: a two-layer index Endless owns.** The syntactic layer uses `go/parser` + `go/ast` per file, which is fast, needs no build and tolerates broken code. It is stored in SQLite and keyed by git blob SHA, because per-file extraction is context-free, so the key is exact. That layer answers `def`, name search and package outlines. The type-aware layer, for `refs`, `impls` and `callers`, comes from `go/packages` + `go/types` in-process, or from running scip-go and ingesting its protobuf through the Go SCIP bindings. scip-go is active: v0.2.7 was released 2026-05-25 and the last commit was 2026-10-11 ([scip-go](https://github.com/sourcegraph/scip-go)). It is batch per module with no documented incremental mode. Type data is not per-file. It would be keyed per package (a hash of the package's file SHAs plus its dependencies' export hashes, which is the gopls design) or computed on demand per worktree, since worktrees are short-lived. For call graphs, x/tools' benchmark puts CHA at about 1.6x the time and 2.7x the memory of static-only, and VTA at about 11x the time ([x/tools commit a4455feb](https://go.googlesource.com/tools.git/+/a4455febdef318395153612ab0489e96418ec51b%5E%21)). CHA over-approximates interface calls (about 3.5x the edges of static), so static+CHA looks like the practical default, with results labelled as such. The supporting libraries are mature. modernc SQLite stays cgo-free and now hosts sqlite-vec if vectors are ever wanted ([gorse.io, 2026-03-15](https://gorse.io/posts/sqlite-vec)).

**Option C: an independent Go tool that Endless calls.** Mike raised the possibility of building the search tool decoupled from Endless, with its own module, CLI and library API, and Endless as one consumer. That would make it useful outside Endless and would fill the "stable library API" gap. The cost is a second project to maintain, plus an API boundary to design before the needs are known. Option C is compatible with A or B as the backing, and with starting from a fork of or contribution to cymbal or gosymdb.

The first pass produced rough, **unsourced** size estimates: about 800–1,500 LOC for a Go-only syntactic index with blob-SHA incremental updates and CLI; 1,000–2,000 more for `go/types` refs plus a static+CHA call graph; and 300–600 for hook integration. These are guesses, not measurements.

## Short-lived worktrees favor content-addressed rows over per-path indexes

Endless creates task worktrees itself and later rebases them into main, so its own task-creation and landing steps are the natural lifecycle points. Claude Code's WorktreeCreate hook fires only for Claude-created worktrees ([Hooks docs](https://code.claude.com/docs/en/hooks.md)). Every surveyed adoptable tool except GitNexus (license-excluded) and Graft (Node, telemetry) pays a full index per worktree.

The content-addressed design sketched in the research uses one shared SQLite DB per repo, with `blobs(sha, …)`, `symbols(blob_sha, …)`, `refs(blob_sha, …)` and `trees(worktree_id, path, blob_sha)`. Creating a worktree copies main's `trees` rows in one `INSERT…SELECT`. Refreshing runs `git diff --name-only main...HEAD` plus `git status --porcelain`, hashes changed files with `git hash-object`, and parses only unseen SHAs. Landing updates main's mapping the same way, and orphan blobs are garbage-collected periodically. This sidesteps copying SQLite files, which is safe only after a WAL checkpoint with no writer. If per-worktree files were ever preferred, APFS `clonefile` gives O(1) copies on the M4 ([rclone clone_darwin.go mirror](https://git.frostfs.info/alexvanin/rclone/src/branch/test/backend/local/clone_darwin.go)). The syntactic layer shares perfectly under this scheme; the type layer shares only per unchanged package.

Freshness probably does not need a file watcher. fsnotify on macOS uses kqueue, with one file descriptor per watched file and no recursive watching ([fsnotify README, fork copy](https://github.com/nshalman/fsnotify/blob/9dcb6e29524fe0b10c120070761df8a1db6e9f9d/README.md)). The alternative is to reindex touched files from a PostToolUse hook on Edit/Write, plus a `git diff` sweep at SessionStart and at landing. That covers edits made through Bash or outside Claude. Option A (gopls) needs none of this, since gopls reads disk. That is its main operational advantage over an owned index.

## Discoverability may matter more than the engine

A command Claude doesn't call saves nothing. The evidence on optional tools is consistent. Skill activation in one sandboxed test was **55%/50% without a hook versus 100%/100% with a forced UserPromptSubmit hook** ([Scott Spence, 2026-02-08](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)). A 2026 measurement study reportedly found agents "defaulted to grep" even with LSP available, though the paper itself could not be fetched ([RuntimeWire, 2026-09-04](https://runtimewire.com/article/agentconnect-coding-agents-grep-lsp-tool-harness)). An HN user reported never seeing Claude use its LSP tool ([yage.ai, 2026-03-27](https://yage.ai/share/why-coding-agents-still-use-grep-en-20260327.html)). In the Arize eval, the agent "gave up and shelled out to bash" despite instructions ([Arize](https://arize.com/blog/mcp-vs-cli-skills/)).

Teaching Claude through `endless guide` alone has the same weakness as MCP: the model must choose to call it. The options discussed, not decided, range from light to heavy:

- **A short cheat sheet injected at SessionStart.** It re-runs on resume and costs a few hundred tokens per session.
- **A PreToolUse hook on search-shaped calls.** On macOS, Claude's searches mostly appear as `Bash` running grep/find rather than `Grep` tool calls ([tools reference](https://code.claude.com/docs/en/tools-reference.md)). Mike accepts this as a given. The hook would recognize an identifier-shaped `grep`/`rg` pattern and either add a one-line nudge naming the equivalent `endless refs …` or attach that command's result directly. cymbal's hooks already "soft-nudge bash grep/find/fd usage back toward cymbal-first navigation" ([cymbal README](https://github.com/1broseidon/cymbal)), and CBM's installer adds non-blocking PreToolUse context on Grep/Glob/Bash ([CBM README](https://github.com/DeusData/codebase-memory-mcp)).
- **UserPromptSubmit injection.** This extracts identifiers from the prompt and pushes results before Claude searches at all. It is the most forceful option and the most expensive per turn.

The documented hook limits shape all three ([Hooks docs, fetched 2026-10-14](https://code.claude.com/docs/en/hooks.md)). **`additionalContext` is capped at 10,000 characters per string.** Overflow goes to a file, and Claude sees only the path plus a 2,000-character preview it is not told to read. **All matching hooks run in parallel with no documented order**, so concurrent SQLite access needs WAL mode and `busy_timeout`, and no hook can assume another ran first. **UserPromptSubmit command hooks time out at 30 s** (most other events default to 600 s), and in practice a lookup there has to finish in well under a second. Hook output is saved to the transcript and replayed on resume. The docs advise factual statements rather than imperative instructions, which can trip prompt-injection defenses. Injected context is paid on every turn whether or not it is needed, so the attach-on-search variant has the best cost profile on paper: it fires only when Claude was about to search anyway.

## A product version would need a language-neutral schema and per-language sources

None of this is needed for Mike's own Go code. It matters only if Endless becomes a product used with Python, TypeScript, Rust, Zig and others. The research found that the hypothesis "no Go-native multi-language agent tool exists" is false. **Gortex** (Apache-2.0, ~4,800 commits since 2026-04-06, v0.64.8 on 2026-10-12) already does Go + tree-sitter + LSP + SQLite + MCP across 257 grammars, but requires cgo ([gortex](https://github.com/zzet/gortex)). That cgo cost may shrink later. A Go proposal, "cmd/cgo: cgo without a C toolchain" ([golang/go#81450](https://github.com/golang/go/issues/81450), still open and in discussion with no target release as of 2026-10-15), would let Go call *prebuilt* C shared or static libraries through Go-syntax binding files, with no C compiler at build time. The proposal explicitly excludes C source code: packages that compile C still need a toolchain. Tree-sitter grammars are C source (`parser.c`), so gortex would only benefit if its grammars were shipped as prebuilt per-platform libraries with bindings. That is plausible, but nothing indicates it is planned. **abdul-hamid-achik/codemap** (MIT, v0.70.6) uses pure-Go gotreesitter plus pure-Go SQLite, with `--precise` driving `go/types`, typescript-language-server or pyright ([codemap](https://github.com/abdul-hamid-achik/codemap)). Lordymine/codegraph consumes scip-typescript output ([repo](https://github.com/Lordymine/codegraph)). Two patterns recur: tree-sitter for definitions plus a type checker (via LSP or SCIP) for precise edges, and explicit provenance or confidence labels on edges. Both fit a language-neutral SQLite schema with a `lang` column on symbols and a provenance column on edges.

For the syntactic layer, **gotreesitter** is a pure-Go tree-sitter runtime with 206 grammars, tags queries and incremental reparse; v0.56.0 was released 2026-10-13 ([gotreesitter](https://github.com/odvcencio/gotreesitter)). It keeps `go install` and cross-compilation cgo-free. It is also young and fast-moving, and it warns about GLR caps on huge or deeply nested inputs ([pkg.go.dev v0.20.3](https://pkg.go.dev/github.com/odvcencio/gotreesitter@v0.20.3)). For precision, language servers cover every target:

- **Python:** pyright 1.1.414 and basedpyright 1.40.2, plus Astral's `ty` 0.0.87, which is still pre-1.0 ([npm pyright](https://www.npmjs.com/package/pyright), [PyPI basedpyright](https://pypi.org/project/basedpyright/), [PyPI ty](https://pypi.org/project/ty/)).
- **TypeScript:** TypeScript 7, the Go port, shipped GA but "without a stable programmatic API… expected in TypeScript 7.1" ([InfoQ, 2026-08](https://infoq.com/news/2026/08/typescript-7-released/)).
- **Rust:** rust-analyzer.
- **Zig:** zls 0.16.0 ([zls](https://github.com/zigtools/zls)).

PHP would be served the same way, for example by Intelephense, a freemium Node language server; it is one language among many, not a focus. Whether TS 7's server and ty support call hierarchy was not verified.

### Paths to cgo-free multi-language parsing

Tree-sitter grammars are C, so multi-language parsing in Go has normally meant cgo and a C toolchain in every build. Three routes could avoid that. They are options, not decisions:

- **cgo now.** This works today, at the cost of a C toolchain wherever the tool is built.
- **purego ([ebitengine/purego](https://github.com/ebitengine/purego)).** Loads prebuilt `.dylib`/`.so` files at runtime on macOS and Linux, without cgo. Unverified: how well it handles tree-sitter's struct-by-value types (`TSNode`, `TSPoint`) and its callbacks on darwin/arm64.
- **gotreesitter as a swappable backend.** A pure-Go runtime with grammars converted to Go data: 206 grammars versus gortex's 257, and possibly different parse behavior. A `nocgo` build tag that swaps a cgo tree-sitter backend for gotreesitter, for example offered upstream to gortex, would reach the cgo-free goal without waiting on Go itself.

**Later: the "cgo without a C toolchain" proposal** ([golang/go#81450](https://github.com/golang/go/issues/81450); open, no target release as of 2026-10-15). It would let the C build and the Go build separate. Grammars and the tree-sitter runtime would be compiled once per platform in CI and shipped as prebuilt libraries; Go would bind them through Go-syntax binding files with no C compiler at build time. Tree-sitter's C surface (one exported function per grammar, plus a versioned runtime API) is smaller than the macOS framework APIs Mike has asked the proposal to support. It shares the same hard features, though: struct-by-value and callbacks are among the proposal's open questions, and they would have to be solved for macOS frameworks anyway. A product would not need to ship every grammar. A curated first-class set plus documented instructions for users to build other grammars themselves (with a GitHub issue process for requesting first-class support) would keep the prebuilt artifact count manageable.

WASM via wazero was considered and set aside as too heavy for this use.

SCIP, as a bulk import format, has moved to a neutral `scip-code` org, with Go bindings at v0.10.0 released 2026-09-03 ([scip](https://github.com/scip-code/scip), [crates.io](https://docs.rs/crate/scip/0.10.0)). Every indexer appears to be batch, whole-project, so SCIP fits as a background precise layer rather than a per-edit one (an inference).

## Months of local transcripts could show what Claude actually searches for

Before choosing which commands matter, Claude Code transcripts could show how the agent searches today. **Months of transcripts exist on Mike's Mac.** He recovered them from Time Machine after the default 30-day `cleanupPeriodDays` purge ([settings reference](https://code.claude.com/docs/en/settings-reference#cleanupperioddays)). That default is relevant only as a product-level fact: other Endless users would have about a month of history unless they raise it.

Transcripts are JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`, where `<project>` is the working directory with non-alphanumerics replaced by `-` ([sessions docs](https://code.claude.com/docs/en/sessions.md)). Each worktree therefore lands in its own folder, so they must be mapped back to a repo by path prefix or the `cwd` field (an inference). Subagent transcripts live separately under `<session>/subagents/`, and large outputs under `tool-results/` ([.claude directory docs](https://code.claude.com/docs/en/claude-directory.md)). The record format is internal and changes between versions. Community descriptions of fields (`tool_use` blocks with `name`/`input`, `message.usage` token counts, `cwd`, `gitBranch`, `version`) are unverified ([claude-dev.tools](https://claude-dev.tools/docs/jsonl-format)). Transcripts are unencrypted and can contain secrets, so any output should be counts and categories, not raw text.

Because searches on macOS mostly appear as `Bash` grep/find, an analysis would parse Bash commands for `grep`, `rg`, `find`, `git grep`, `go doc`, `gopls …` and similar. That is heuristic and will misclassify some compound commands. Mining could plausibly answer six questions:

1. How much searching happens per task before the first edit.
2. Whether searches are **symbol-shaped** (Go identifiers, `func \(.*\) Save`), **text-shaped** (error strings, config keys, where grep is already right) or **structural** (runs of searches plus many Reads, suggesting "who calls / what implements").
3. How long the search→Read→refined-search chains get, which is the best estimate of what better tools could save.
4. What share of tokens search consumes. If it is small, better search can only save a little.
5. Which of `def`/`refs`/`callers`/`impls` would see real demand.
6. A rough before/after baseline, though not a controlled one.

The approaches range from parsing JSONL directly (most detail, most fragile), to logging search-type calls into Endless's SQLite from its own hooks going forward (hook input carries `tool_name`, `tool_input`, `session_id`, `cwd`, `transcript_path`, per the [Hooks docs](https://code.claude.com/docs/en/hooks.md)), to OpenTelemetry export with `OTEL_LOG_TOOL_DETAILS=1`, which is probably more infrastructure than warranted ([monitoring docs](https://code.claude.com/docs/en/monitoring-usage.md)). The limits are real. Mining shows what the agent did, not what it needed. Intent classification needs hand-checking. Older transcripts reflect older models' habits. Non-Go and non-Endless sessions need filtering.

## A benchmark design, deferred

Mike is doing early research from an iPad, so benchmarking is deferred. The design is kept compactly for when it becomes relevant. It would use Endless's own repo frozen at one SHA, a pinned model (provider-side drift is a documented confound, per [Jarmak, arXiv 2608.13867](https://arxiv.org/pdf/2608.13867)), and Endless's real flow: a fresh worktree, a headless `claude -p` session, then land or discard. Task types would include localization Q&A, a one-package feature, a cross-package interface refactor, a bug fix from a failing test, and an impact question checked against gopls ground truth. Transcript mining could supply realistic task picks. Candidate arms are plain Claude Code; the gopls-lsp plugin; Endless commands with a SessionStart cheat sheet; the same plus PreToolUse attach-on-search; and optionally cymbal or gosymdb with their own hooks. One harness saw a **±55% token swing** between identical runs ([RESULTS-harness.md, 2026-06-14](https://git.autonomic.zone/recipe-maintainers/agent-orchestrator-benchmark/src/branch/main/RESULTS-harness.md)), and single-run SWE-bench pass rates vary 2–6 points. A credible comparison therefore needs at least 5 and preferably 10–20 runs per arm, after a 20-run pilot to estimate variance. Each run would record dollar cost (caching distorts raw tokens), pass/fail, tool-call breakdown (did Claude call the commands at all?) and injected characters. The earlier suggested bar was a median cost reduction of at least 15% with no drop in pass rate, compared with bootstrap confidence intervals.

## Conclusion

The research reframed the question. It started as "which trending graph tool should Endless adopt" and became "what is the smallest precise thing Claude would actually use." For Go, the precise answer already exists in Go's own toolchain. What is missing is a name-based front door and an index that suits dozens of short-lived worktrees, and a few 2026 tools have each built part of that. The one design element no surveyed tool documents is content-addressed rows shared between main and its task worktrees. It is also the piece most specific to how Endless works, which makes it the most defensible thing to own if anything gets built.

The less obvious takeaway is that delivery will likely decide the outcome more than the engine. The strongest evidence in the whole survey is not about index quality. It is that models skip optional tools and use injected context. A precise `endless refs` that Claude never calls is worth nothing, while a cheap nudge attached to the grep Claude was about to run might be worth more than any graph. That suggests the transcript record of how Claude actually searches today is the most valuable input to whichever decision comes next.
