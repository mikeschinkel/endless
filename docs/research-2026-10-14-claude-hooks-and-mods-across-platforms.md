# Claude Code Settings Hooks and Mods Across CCC, CCD, CW and CM: Where Sessions Execute, and What It Means for Endless

Your hypothesis is mostly right. A session you start in CCC runs only on the machine where CCC is running. CCD, CW and CM can list it, notify you about it, or steer it through Remote Control, but they don't move it. It isn't a complete false alarm, though, for two reasons. First, the same surfaces can start new sessions that run in an Anthropic cloud VM, where your user-level settings hooks, user-scope plugins and mods are absent. Second, CCD local sessions run on your Mac, but users report that settings hooks there silently fail to fire.

**Evidence labels:** **[D]** documented by Anthropic; **[O]** observed in reproducible user reports; **[I]** inferred by me; **[S]** speculative. Unless a date is given, documentation was read on October 14–15, 2026. Anthropic's docs pages are live and carry no publication date.

## TL;DR

- **It is a false alarm for execution, not for configuration drift.** A CCC session executes only on your Mac [D]. It can appear in CCD, CW and CM for two reasons. CCD's `/resume` lists "sessions you started from the CLI on this computer" by reading local history [D].\[1\] Remote Control, if you turn it on per session or set it to connect automatically, registers the session with Anthropic so claude.ai/code, the mobile app and Claude Desktop can view and steer it [D]. iPad notifications come from Remote Control push ("Push when Claude decides" / "Push when actions required"), from Dispatch, or from cloud sessions you started [D]. None of these moves execution. Execution moves off your Mac only when someone explicitly creates a cloud session: Cloud in CCD, a new session on CW/CM, `claude --cloud`, `/autofix-pr`, a routine, or CCD's **Open in > Cloud** [D].
- **Cloud sessions apply different rules, and they break Endless quietly.** They run on a fresh Ubuntu 24.04 x86_64 VM [D]. They read the repo's committed `.claude/settings.json`, including its settings hooks, but only in sessions with a single repository [D]. They also read server-managed settings [D]. They never read `~/.claude/settings.json`, `.claude/settings.local.json`, or MDM/file-based managed settings [D]. Plugins listed in the repo's `enabledPlugins` are **not** installed. The only plugins that reach a cloud session are those synced from your claude.ai account (`name@synced`) and those force-enabled through server-managed settings [D]. Mod hooks run only for those plugins, and nothing a mod draws appears [D]. A committed settings hook that calls Endless's Go binary gets "No such file or directory". By default that is a *non-blocking* error and the session carries on [D].
- **The strongest gate available today is a PreToolUse/UserPromptSubmit command settings hook with `"onFailure": "block"` (Claude Code v2.1.295+).** If the Go binary is missing, crashes, or times out, every tool call or prompt is blocked [D], so it fails loudly on any surface where Endless can't run. Add out-of-band verification: Endless launches the sessions itself, so it can treat a session that never sends a `SessionStart` heartbeat as unmanaged. Restrict Endless to local execution and use Remote Control for viewing and steering. Supporting cloud execution is possible (a synced plugin plus a linux/amd64 binary), but it forces Endless's state off the machine.

## Key Findings

1. **CCC sessions in CCD.** The Desktop docs say "Each keeps its own session list, and you can bring a CLI session into Desktop", using `/desktop` from the terminal or `/resume` in Desktop. With `/resume`, "Desktop lists the sessions you started from the CLI on this computer" and "continues the same session rather than a copy" [D].\[1\] Remote Control is the second route: Trusted Devices covers viewing or steering Remote Control sessions "from claude.ai, the Claude mobile apps, or Claude Desktop" [D].\[2\] Desktop `/resume` for terminal sessions was announced by @ClaudeDevs on August 28, 2026 [D].\[3\]\[4\]\[5\] GitHub #43786 ("[FEATURE] Desktop app sidebar should show CLI-created sessions") showed that the Desktop sidebar didn't automatically show CLI sessions as of v2.1.87. It was labelled on April 5, 2026, and github-actions locked it on April 12, 2026 "since it was closed and has not had any activity for 7 days". It is closed and **stale** [O].
2. **Remote Control is opt-in per session, but it can be made the default.** It "only activates when you explicitly run `claude remote-control`, `claude --remote-control`, or `/remote-control`, unless auto-connect is turned on". Auto-connect comes from `/config`, from `remoteControlAtStartup: true` in user or managed settings, or from Desktop's **Connect new sessions to Remote Control** switch [D].\[1\]\[2\]\[6\] A checked-in project file can switch it off but cannot switch it on (changed in Week 32, August 3–7, 2026) [D].\[7\]\[8\] While Remote Control is connected, "the session transcript… is stored on Anthropic servers", but "Execution and filesystem access stay on your machine" [D].\[2\]
3. **Mobile can now start sessions on your Mac.** Since Week 34 (August 17–21, 2026), any machine running `claude remote-control` shows up as a device card on the phone. Tapping it lets you "pick a directory and start a session there" [D].\[9\]\[10\] Those sessions still run locally, but they are created by server mode, not by Endless. In server mode, global flags such as `--settings` aren't carried over; Claude Code refuses to start and names the flag [D].\[2\]
4. **Settings hooks are documented as universal but observed as unreliable in CCD.** The hooks reference says "Claude Code fires the same hook events wherever it runs: sessions in the terminal, IDE extensions, the Desktop app, and cloud sessions" [D].\[11\]\[12\] #96496 (Claude Code 2.1.267, macOS) reports settings hooks that fire in "claude rc / /rc — the first remote-control session" but not in the CCD Code tab, where its repro says to "run /debug to check for Hooks: Found 0 total hooks in registry", nor in "A new session slot opened within an already-existing remote-control connection" [O]. #97977 (September 28, 2026, Windows) reports that the session transcript shows firing records for "SessionStart:startup, SessionStart:compact, UserPromptSubmit, PreToolUse:Bash, PreToolUse:Skill -- but zero PostToolUse:Edit or PostToolUse:Write records" across dozens of Edit/Write calls in the Code tab [O]. #96496 links both to #87657 ("0 hooks in registry") and #90798 (warm-process reuse) [O].\[12\]
5. **Mods can call your Go binary wherever they run, with limits.** `$.process.run([...])` starts a program without a shell, resolves to `{ exitCode, stdout, stderr }`, and times out after 30 seconds by default (10 minutes at most) [D].\[13\]\[14\] Each mod hook has 10 seconds of its own running time; time spent waiting on a mods API call doesn't count [D].\[13\]\[14\]\[15\] An organization policy mod can refuse any user mod that calls `process.run` [D], and `allowManagedModsOnly` blocks every user mod [D].\[13\]\[16\]

## 2. Settings hook behavior per surface (section B)

**CCD vs CCC (Q6).** The docs say CCD reads the same settings files as the CLI [D].\[1\] User-scope plugins are shared between the terminal, CCD local sessions and VS Code on one computer [D].\[22\]\[23\] The same events and payloads are documented everywhere [D]. One documented difference: for worktree sessions started from Desktop, `${CLAUDE_PROJECT_DIR}` can point somewhere other than you'd expect; the docs refer to "What worktrees share with the main checkout" [D].\[11\] CCD also doesn't inherit your full shell environment. Launched from the Dock, it reads your shell profile for `PATH` and a fixed set of Claude Code variables only [D].\[1\] If Endless's binary or its environment variables depend on `~/.zshrc` exports, settings hooks in CCD may not find them [I]. Beyond the documentation, the silent-failure reports above (#96496, #97977, and #35541 from March 2026, **stale**, which was a Notification-event gap later fixed in the changelog) mean CCD should be treated as "verify per version" [O].\[7\]\[24\]

**Cloud sessions (Q7).**
- *Which settings are honored:* see the matrix [D]. Server-managed settings arrive "when the session starts". MDM and managed files don't, "because the session runs on an Anthropic-managed VM" [D].\[20\]\[25\]\[26\]
- *Do settings hooks follow the same carry-over rules as plugins?* Yes, by file of origin. A settings hook in user settings: **no**. A settings hook in the repo's `.claude/settings.json`: **yes** for a single-repo session [D].\[20\] A settings hook inside a plugin: only if that plugin reaches the session as `@synced` or server-managed [D]. The changelog's fix for "SessionStart hooks from synced plugins not running in new cloud sessions" (v2.1.287, ~October 1, 2026) confirms that synced-plugin settings hooks are meant to run in the cloud [D].\[7\]\[27\]
- *OS, filesystem, network, environment:* "a fresh virtual machine (VM) running Ubuntu 24.04 on x86_64, regardless of your own operating system and CPU architecture" [D], so you need a `GOOS=linux GOARCH=amd64` build. The VM has about 4 vCPUs, 16 GB RAM and 30 GB disk [D]. Setup scripts run as root [D]. The session reports itself through `CLAUDE_CODE_REMOTE=true` and `CLAUDE_CODE_REMOTE_SESSION_ID` (`cse_…`) [D].\[28\]\[29\] A Go toolchain is preinstalled [D].\[20\]
- *Installing the binary first:* a setup script "runs when a new cloud session starts, before Claude Code launches" [D], so it runs before any settings hook. `release-assets.githubusercontent.com`, `objects.githubusercontent.com` and `proxy.golang.org` are on the default Trusted allowlist [D], so `curl` from GitHub Releases or `go install` works at Trusted level [I]. If the setup script exits non-zero, "the session fails to start" [D], which makes it a usable hard gate. Anthropic's "Configure cloud environments" docs say to "keep the script's total runtime under roughly five minutes so the environment cache can build", and that the script reruns "when the cache reaches its expiry after roughly seven days"; Anthropic's own wording is approximate [D]. A SessionStart command settings hook can install the binary too, with a 600 s default timeout [D]. Setup scripts belong to the *environment*, which is personal or shared at the org level, not to the repo [D]. Each Endless user would have to configure one [I].
- *Events and timing:* SessionStart "behave[s] the same in the cloud as locally" except for the multi-repo, network and proxy caveats [D].\[20\] Anthropic-hosted sessions add their own Stop settings hook "that prompts Claude to commit and push its work" [D].\[19\] Per the same cloud-environments docs, "after a few minutes without activity, a session's VM pauses with its files saved. Your next message restores the same VM and starts Claude Code again", and setup scripts don't rerun on restore [D].

**Remote Control (Q8).** Execution, and therefore settings hooks, stay local [D].\[2\]\[17\] There is no documented bypass for remote input. UserPromptSubmit is documented to fire on submitted prompts and on turns Claude Code starts by itself [D].\[11\] #100418 (October 8, 2026) shows a mod `prompt.submit` mod hook receiving a phone-originated prompt with `e.origin.kind === 'bridge'`. That means remote prompts pass through the same pipeline, though the mod's drop reason isn't shown on the phone [O].\[30\] PreToolUse fires before the permission flow, so an approval tapped on a phone can't skip it [I, based on the documented event order]. The exception is extra server-mode slots, where settings hooks were observed not firing at all (#96496) [O].\[12\]

**HTTP settings hooks from the cloud (Q9).** *Current capability:* an HTTP settings hook POSTs JSON. A non-2xx response or a failed connection is a non-blocking error unless you set `onFailure: "block"` [D]. Headers can interpolate environment variables listed in `allowedEnvVars` [D]. `allowedHttpHookUrls` limits which URLs are allowed [D].\[11\] Outbound traffic goes through Anthropic's security proxy and the environment's allowlist (None/Trusted/Full/Custom); your server must be allowed by Full or Custom [D]. Values in environment variables are readable by anyone using the environment [D]. Network secrets (Pro/Max only) attach a key to requests for listed hosts "after each request leaves the session's VM" [D]. **Undocumented:** whether Claude Code's own HTTP settings hook requests pass through the agent proxy that attaches secrets. The docs only say that telemetry export doesn't [D].\[20\] Treat secret injection for HTTP settings hooks as unverified [S].

## 3. Mod behavior per surface (section C)

**Q10, table extended.** The baseline table [D] matches the matrix above.\[17\] Additions: Dispatch and CCD local scheduled tasks run locally under Desktop's bundled Claude Code, so mod hooks should run [I]. Routines and **Open in > Cloud** are cloud sessions, so mod hooks run only for `@synced` or server-managed plugins, with no drawing [D].\[17\] Teleported sessions are ordinary local CLI sessions [I]. Version floors: CLI v2.1.287+, Desktop's bundled engine from v2.1.286 [D].\[17\]\[31\] Anthropic doesn't publish the cloud VM's Claude Code version. One third-party user report (shoraLBRT/ritocode issue #146) observed "Ubuntu 24.04.4, x86_64, 4 vCPU, 15 GiB RAM, ~30 GB free… claude 2.1.285 on PATH; CLAUDE_CODE_REMOTE=true". If that is current, the version is below the CLI mods floor, so check it with the probe below [O]. A cloud changelog fix for "a mod's `session.receive` hook" (v2.1.295) shows mods run in cloud builds [D/I].\[7\]\[27\] Early access used `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS`; v2.1.287+ ignores it [D].\[16\]\[17\]

**Q11, can a mod hook start the Go binary?**
- *Your Mac (CCC or CCD local):* yes. Call `$.process.run(['/abs/path/endless', 'event', …])` [D], with no shell and a 30 s default timeout [D].\[13\] Processes started by a mod run outside Claude Code's Bash sandbox [D].\[14\]\[17\]\[32\]
- *Remote Control:* yes, because the mod runs "in the session on your machine" [D].\[17\]
- *Cloud:* yes, if the plugin reaches the session and the linux/amd64 binary exists on the VM [D/I].\[17\] It can't reach your Mac's SQLite [I].
- *What can block it:* `allowManagedModsOnly` (users' mods don't load, "including… one your organization turns on for its members on claude.ai") [D]; `allowManagedHooksOnly` [D]; `disableAllHooks` [D]; `--safe-mode`, `--bare` [D]; `disableSideloadFlags` for `--plugin-dir` [D]; a policy mod in `prependPlugins` that refuses `process.run` callers [D]; Anthropic's remote rollout switch ("the rollout switch served off") [D]; and the mod worker crashing three times, which unloads all non-built-in mods for the session [D].\[16\]\[33\]\[34\] Network policy covers `$.http.fetch` but not a process the mod starts [D].\[16\]

**Q12, what mods add across surfaces.** `e.surface` reports `terminal` or `desktop` inside `ui.render` and on button presses [D].\[13\]\[35\] `e.origin.kind` identifies the source of messages (`peer`, `task-notification`, `scheduled-trigger`, and others) [D],\[14\]\[36\] and `'bridge'` has been seen for Remote Control prompts [O].\[14\]\[30\] A mod can "fall back to a line in the transcript or a command's text reply where nothing draws" [D].\[17\] Over Remote Control, though, `$.ui.log`, toasts and drop reasons don't reach the phone (#100418) [O].\[30\] Mods can also run before PreToolUse settings hooks from other files and can keep those settings hooks from running by answering a tool call themselves [D].\[15\]\[16\] That ordering risk matters if Endless relies on a user-level PreToolUse settings hook.

## 4. Failure modes and gates (section D)

**Q13, the binary is missing.** A shell-form command settings hook that can't find its script exits with something like 127. That is a **non-blocking error**, and "a mistyped path in `settings.json` means the hook never runs" [D]; the transcript shows a `<hook name> hook error` notice. A timed-out PreToolUse command settings hook "doesn't block the tool call" [D]. With `"onFailure": "block"` (v2.1.295+), being unable to start, exiting with any code other than 0 or 2, an HTTP error, a timeout, or invalid output all block the action [D]. `onFailure` has no effect on Stop/SubagentStop/TaskCompleted/TeammateIdle or on async settings hooks [D]. SessionStart can't block. Exit 2 there only shows stderr [D].\[11\] For mods, a module or mod hook that throws is skipped and "a broken mod can look like one that does nothing" [D].\[37\]

**Q14, hard gates, ranked:**
1. **`onFailure: "block"` on PreToolUse + UserPromptSubmit command settings hooks** [D].\[11\] This fails closed on every surface that reads the file. It is the closest match to "gates over guidelines".
2. **Managed settings.** Managed settings settings hooks can't be turned off by `disableAllHooks` set at user, project or local level [D].\[7\] `allowManagedHooksOnly` blocks everything else [D].\[11\] A managed PreToolUse block "is final" even against mods [D].\[6\]\[15\]\[16\] Cost: an OSS tool would have to write a root-owned managed settings file on the user's Mac. That is intrusive, and it doesn't reach cloud sessions, which only honor *server-managed* settings [D].
3. **Cloud setup script that exits non-zero** if it can't install the binary, which makes the session fail to start [D].\[20\] This only works in environments the user configures.
4. **A policy mod modeled on `sec-default`.** It runs first only if it "counts as your organization's", which requires managed `enabledPlugins` plus a local directory marketplace referenced by absolute path [D].\[16\] That is impractical for an OSS user install [I]. Its `plugin.register` check fails open unless you add `.catch` [D].\[16\]
5. **"Required" plugins:** a claude.ai org can mark a synced plugin as required [D].\[21\] That is Team/Enterprise org policy, not something individual users have [I].

**Q15, detecting the surface and execution location.** Use the documented signals: `CLAUDE_CODE_REMOTE=true` (cloud) [D];\[11\] `CLAUDE_CODE_REMOTE_SESSION_ID` (cloud) [D];\[20\] `CLAUDE_CODE_BRIDGE_SESSION_ID` (Remote Control active, v2.1.199+) [D];\[11\] `CLAUDECODE=1` and `CLAUDE_CODE_CHILD_SESSION` (v2.1.172+) [D]; `CLAUDE_RUNNER_CLIENT_PLATFORM` (only in self-hosted runner wrappers and runner lifecycle scripts, and documented as "not as an authorization signal") [D]; and `e.surface` in mods [D].\[11\]\[19\]\[28\]\[29\] `CLAUDE_CODE_ENTRYPOINT` is **not documented** [I], so don't rely on it. The settings hook stdin payload has no documented surface field [D]. The most reliable test is for the Go binary to check `runtime.GOOS`, hostname, and the presence of its own SQLite. Endless can also check that every session it launched sent a SessionStart with a matching nonce [I].

**Q16, silent off-switches.** `disableAllHooks` (user/project/local, and `--settings '{"disableAllHooks": true}'`) [D];\[11\] `--safe-mode` / `CLAUDE_CODE_SAFE_MODE` [D]; `--bare` ("skips hooks… plugin sync") [D]; `allowManagedHooksOnly`, `allowManagedModsOnly`, `strictPluginOnlyCustomization` [D]; multi-repo cloud sessions [D]; WSL [D]; server-mode refusal of `--settings` [D]; `syncClaudeAiPlugins: false` [D]; and the CCD silent-firing bugs [O].\[7\]\[16\]\[17\]\[25\] Built-in mods aren't stopped by these switches [D].\[17\] **Detection:** Endless can't run code inside a session where it has been turned off. Detect it from outside instead: a session Endless started that produces no SessionStart or heartbeat within N seconds counts as disabled [I]. The `/hooks` menu and `claude --debug` show what loaded [D].

## 5. Options for Endless (section E), ranked

1. **Local-only execution, remote surfaces as viewers and controllers, fail-closed (recommended).**
   - *What works:* Endless launches `claude` in tmux with Remote Control on, using `--remote-control` or `remoteControlAtStartup` [D].\[1\]\[6\] You watch and steer from CW, CM or CCD, and push notifications arrive [D].\[2\] Put PreToolUse/UserPromptSubmit command settings hooks with `onFailure: "block"` in the settings Endless controls, and require v2.1.295+ [D]. Add the out-of-band SessionStart nonce check [I].
   - *What breaks:* extra server-mode slots opened from the phone (no settings hooks observed) [O].\[12\] Have Endless refuse to treat device-card sessions as managed, or tell users not to run `claude remote-control` server mode [I]. Transcripts are stored on Anthropic servers while Remote Control is on [D].
   - *Setup burden:* low.
   - *Support:* Anthropic-supported; Remote Control left research preview in Week 34 [D].\[9\]
2. **Make cloud sessions on Endless-managed repos fail loudly instead of running unmanaged.** Commit a PreToolUse guard with `onFailure: "block"` to the worktree's `.claude/settings.json`, so a cloud session blocks on its first tool call [D/I]. Alternatively, have a tiny committed shim exit 2 with "Endless: cloud execution unsupported" when `CLAUDE_CODE_REMOTE=true` [D/I]. *Tradeoff:* the guard also blocks collaborators who open that repo in the cloud. Keep it to Endless-owned branches or worktrees [I]. Without it, the default behavior is a silent non-blocking error [D].
3. **Treat CCD local as "supported but verified".** Allow CCD-launched or CCD-resumed sessions only when Endless sees the SessionStart nonce. Otherwise flag them, given #96496 and #97977 [O].
4. **Ship Endless as a plugin (settings hooks plus a thin mod) with a Go binary for cloud sessions.**
   - *Works today:* upload the plugin to claude.ai so it syncs as `endless@synced` [D].\[38\] Bundle `darwin/arm64` and `linux/amd64` binaries behind a `uname` shim, or fetch the binary in a setup script from GitHub Releases [D/I]. Its settings hooks and mod hooks run in the cloud [D].\[17\]
   - *Breaks:* Endless's SQLite lives on your Mac, so cloud state must reach a server you run over Full/Custom network access. That breaks local-first [I]. Mod drawing never appears [D]. Multi-repo sessions get no repo settings hooks [D]. Orgs with `allowManagedModsOnly` block the mod [D].
   - *Burden:* high: account upload, per-user environment setup script, network allowlist.
   - *Support:* each piece is documented. The combination is "works today", not a supported product path [I].
5. **Self-hosted environment on the Mac Mini (Team/Enterprise only, public beta since August 6–7, 2026, v2.1.224).** Cloud sessions started from CW/CM would execute on your Mac, and runner-seeded `~/.claude` settings hooks would run [D].\[8\]\[11\]\[19\]\[39\] *Breaks:* plan-gated, beta, and the runner is a separate process model from Endless's tmux sessions [D/I]. Worth an experiment, but not the default.

**Recommendation:** adopt Option 1 + 2 + 3 now. Document that Endless doesn't support cloud execution. Revisit Option 4 only if Anthropic ships user plugins or mods in cloud sessions.

## 7. Open questions and proposed experiments

Build a **probe** containing (a) a command settings hook on SessionStart, UserPromptSubmit, PreToolUse and PostToolUse, and (b) a mod with `session.start`, `prompt.submit` and `tool.call` mod hooks. Both should append to `~/endless-probe.log`: hostname, `uname -sm`, `pwd`, `claude --version`, `env | grep -E 'CLAUDE|ANTHROPIC'`, the stdin JSON, and for the mod `e.surface` and `e.origin`. Install it at user scope, project scope and as a synced plugin, then run:

1. CCC plain; CCC `--rc`, steered from iPad; `claude remote-control` plus a session started from the iPad device card.
2. CCD Local (new, `/resume`d, a worktree session, a Dispatch session, a scheduled task) on the current Desktop build. Repeat after each update.
3. A CW cloud session with one repo, with two repos, and via CCD **Open in > Cloud**. Confirm `Linux x86_64`, the `claude --version` in the VM, and which probes fire.
4. Rename the binary and confirm `onFailure: "block"` blocks the first tool call in CCC, CCD and the cloud.
5. Put `disableAllHooks: true` in managed settings vs. user settings, and run `--safe-mode`. Check whether **managed** settings hooks survive `--safe-mode`; this is undocumented.
6. A cloud HTTP settings hook to your server under Custom network access, with and without a network secret for that host. Does the secret get attached?
7. Run `claude config get remoteControlAtStartup` and `/status` in the sessions that appeared in CCD, and check the logged `CLAUDE_CODE_BRIDGE_SESSION_ID`. That tells you which route surfaced them.
8. A self-hosted runner on the Mac Mini, if you have a Team plan.
