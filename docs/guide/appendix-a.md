# Appendix A — User-focused commands

These are commands a **human** runs interactively at a terminal. An agent reads this appendix only to point a user at the right command — never as part of its own working flow. This is a global appendix: user-only commands from any command group are collected here.

## Session navigation, observation, and history

Interactive commands on the `session` group:

- **`endless session goto <target>`** — switch tmux focus to a task's or session's pane, pushing the current pane onto a per-client back-stack. `<target>` is a task id (`E-NNNN`/`NNNN`) or a session id (`ES-NNNN`, a bare integer, or a Claude UUID prefix); a task id resolves to the most-recently-active live session working it. Prefer `ES-NNNN` — the form `task show` prints under `Created:`/`Sessions:` — since a bare integer matching both a session and a task is rejected as ambiguous. Requires tmux. `--resume` relaunches a target with no live pane in a NEW window (named `E-NNNN` for the task it holds) rather than erroring; on a target whose task is settled (`confirmed`/`assumed`/`completed`) it then requires **`--revisit`** (flip the task to `revisit` and continue work) or **`--no-revisit`** (read the session back, leave the status alone), because those mean opposite things and neither is a safe default. A target whose Claude transcript file is gone is refused **before** the window is created — the defect was a window that came up, died with the claude inside it, and told you nothing — and **`--new-transcript`** is the give-up route: a plain `claude` in the task's worktree, no `--resume`. The new window carries the standard three-pane layout `task spawn` builds.
- **`endless session resume <ref>`** — relaunch a lost session in the CURRENT pane: resolves `<ref>` to a Claude UUID, cd's to its task worktree, and execs `claude --resume`. Unlike `goto`, ended sessions count — recovering the sessions a tmux crash orphaned is what it is for. `<ref>` takes the same forms as `goto`, and `ES-NNNN` is session-**explicit**: it never falls back to task `E-NNNN`'s session. A session that never claimed a task gets a container task (`Auto-resumed task for session ES-NNNN`, claimed straight to `underway`) and its worktree created, so there is somewhere to resume into. `--review`/`--reopen` rebuild a worktree dropped after landing; `--dry-run` resolves and creates everything but declines the launch, printing the resolved target as JSON. Because the exec replaces the current pane, it refuses without **`--force`** when that pane's session is working a task, and points at `session goto <ref> --resume`, which opens a new window instead — unless the target IS that task, since re-entering the task the pane already holds replaces nothing. It also refuses a window holding more than one pane, because it lays the standard three-pane layout out around the pane it takes over. Like `goto --resume` it refuses a gone transcript before launching anything, with the same **`--new-transcript`** route on: the window choice and the give-up choice are independent, so the flag is on both verbs.
- **`endless session end <ref>`** — end a session that is not live: a ghost whose tmux server cannot be reached reads `unknown` and keeps blocking claims on its task, and ending it frees the task. `<ref>` resolves as `resume` resolves it. Refuses a session that reads `live` (exit Claude in its pane instead), and one with activity in the last 10 minutes unless **`--force`**, since a running Claude's hooks keep `last_activity` current even where its pane cannot be seen. Shows the session's task, last activity and liveness and asks y/N; **`--yes`** skips the prompt, and is required with no terminal. An already-ended session is reported and left alone. The transcript is kept: `endless session resume ES-NNNN` undoes it.
- **`endless session back`** — return to the previous pane, browser-style: pops the back-stack `goto` built, skipping panes that have since closed. With an empty stack, returns to the spawning session. Requires tmux.
- **`endless session monitor`** — the live dashboard: loops the `session status` view, redrawing every 2 seconds and repainting only on change. The top-like pane you keep open all day; Ctrl-C exits. Takes the same `--all`/`--tree`/`--show-hidden`/`--only-hidden`/`--show-suppressed` options as `session status`, footer included.
- **`endless session history [session]`** — show the conversation history for a session (current by default).
- **`endless session search <query>`** — search across all session messages.
- **`endless session hide <ids...>`** / **`endless session unhide <ids...>`** — hide sessions from (or restore them to) `session list`. With `--task <id>` (repeatable) they switch senses entirely and hide/restore individual TASK rows in one session's `session status` view — see **Quieting a noisy status view** in `endless guide sessions`.
- **`endless session touch <ids...>`** — put tasks on a session's `session status` list without changing them (relation `touched`); run it from your own shell pane beside the session. `endless touch` and `endless session task add` are aliases.
- **`endless session task remove <ids...>`** — drop a task's association with a session entirely. Distinct from `session hide --task`, which suppresses a row while keeping the association — see **Saying what your session's list holds** in `endless guide sessions`.

## `project status` and `project monitor`

Interactive commands on the `project` group. Where the `session` views above answer *"what is next for the task I am on"*, these show the project's open work as a whole. An interim design: a scrolling TUI is expected to replace it.

- **`endless project status [name]`** — the project's open tasks in three lists, in order and without separators: **urgent** tasks, then **epics** in `now`/`next`, then **every other** `now`/`next` task. Each task appears once, in the highest list it qualifies for — an urgent epic is in the first list only. On a terminal each list wears its own background (urgent red, epics green, the rest yellow, all from your theme's palette); set `project_status.colors` in `.endless/config.json` to change them — see `internal/config/README.md`. Every non-terminal status is included. A row is `session status`'s: action glyph, type letter, id, phase, title — no age column, and none of the glyphs that describe a viewing session (● ↑ ↩). Sessions are never rows, but they are consulted: an `underway` task reads ⟳ while a live session holds it, ⚠ when that session is blocked on a permission prompt, and ◷ once no live session does. Nothing is truncated, so this is the view to grep for a task the monitor has no room for. `--sort updated` (the default) or `--sort id` orders each list, newest first. `--later` shows only `later` tasks instead. `--json` dumps the rows, each carrying its list and action. Defaults to the project enclosing the working directory; name another to read it from anywhere.
- **`endless project monitor [name]`** — the same lists, live: redrawn every 2 seconds, repainting only when a row changes. The urgent and epic lists always render in full; the third list takes whatever height the pane has left and ends with `… N more (project status)` when it is cut. The frame fits the pane it is in, so dragging the pane's divider shows more rows or fewer. Takes `--sort`. Ctrl-C exits.
- **`endless project monitor <name> --tmux`** — the monitor's home: a window named for the project in the `console` session on Endless's console tmux server (see `endless start` in `endless guide reference`), the monitor on top and a bare shell beneath it, focus on the shell. Each run adds a window, even when one exists for the project, so a run always ends with a live monitor; close any window you have no use for. With the console not running it refuses ("Endless isn't running. Run `endless start`"): only `endless start` starts Endless's servers. A terminal is opened onto the console when none is attached (`tmux.terminal`, or a detected terminal); with no way to open one it attaches from a plain terminal, or prints the attach command inside tmux. `--no-switch` adds the window without opening a terminal.
- **`endless project info [name]`** — the project's registration card: metadata, pending notes, dependencies. (This is what `project status` used to be, before that name moved to the command that lists the project's tasks.)

## `correct` — a correcting entry for ledger state

A user-only command. An agent that finds the recorded state wrong tells the user; it does not run this, and both halves of the command refuse it.

The ledger is append-only, and the only other way to put a wrong row right is to replay ordinary transitions through their gates. When a gate was skipped on the way in, that can deadlock — a landed todo task with unapproved plan items could reach `assumed` only through `revisit`, `submitted`, `ready` and `underway` and a fresh reconcile, and those transitions would then sit in its history as if they described real events. Accounting's answer is a correcting journal entry: never erase, post an entry that says what it corrects and why.

The command is `endless correct <target> <operation> [KEY]`: the target and the operation are subcommands, the key is the one positional argument, and everything else is a flag. `--reason` is required on every operation: a correction always records why.

- **`endless correct <target> update KEY --set col=value ... --reason <text>`** — update a row. `NULL` (exactly) is SQL NULL. A `--set` that changes nothing is refused.
- **`endless correct <target> insert --set col=value ... --reason <text>`** — insert a row. It may set the listed columns plus any column the table requires; an `id` is allocated.
- **`endless correct <target> delete KEY --reason <text>`** — delete a row, refused while other rows refer to it. A table that keeps removed rows behind a `removed` column (tasks and decisions) has the row marked `removed = 1` instead, so its id is never minted again. A `session` is never deleted: the operation is refused, because a freed session id would be handed to the next session created while rows still holding the old id name it, and a session that should not be listed is hidden with `--set hidden=1` instead.
- **`endless correct <target> annotate KEY --reason <text>`** — an annotation: a correction entry with the reason and no change, for any target or for `conversation`, `message` and `project_next`, which have no table and take nothing else.

Every run writes a `ledger.row_changed` entry per change — the target, key, operation and values, applied by the executor and the projector alike and triggering none of an existing kind's effects — and then a `ledger.corrected` entry: the reason, the before values, whether gates were skipped, and the byte offset of each change entry in the segment both were written to. The run holds the ledger lock from its first line to its last, so the lines are adjacent, and commits them in one ledger commit whose subject names the correction (`Endless: ledger.corrected E-101 …`), which is never folded with another. `git log -- .endless/db-ledger` is where corrections are read; there is no other display yet.

**Gates** are on by default and only refuse: for a task's status, the transition table for its type and the plan-item approval check; for status and phase columns of any target, the vocabulary. `--skip-gates` bypasses them and is recorded on the entry. The column list, foreign keys, the no-duplicate-key rule and the parent-cycle rule hold either way, and a row of another project is refused so the entry lands in its own project's ledger. A corrected field with a document mirror gets the mirror rewritten; nothing else follows — no worktree or session change, no epic derivation — and correcting an epic's status prints that the next derivation can overwrite it.

## The ledger's write order, `ledger.voided` and `event void`

Every `endless` write goes through `endless-go event emit`, which applies the event and records it in one write transaction, in this order: `BEGIN IMMEDIATE`, run the SQL, append the event's line to the ledger segment, append any `epic.status_derived` lines the apply produced, `COMMIT`, then commit the segment to git. A SQL failure rolls back and nothing reaches the ledger: the command exits non-zero with the apply's error, and re-running it is safe. The write lock is taken before anything is read, so two writers queue on the connection's busy timeout instead of one failing late with `database is locked (517)`; there is no retry loop on top of that wait.

One window remains: the lines are appended and the `COMMIT` then fails. The ledger is then ahead of the database, and an append-only record can only say so with another line. `emit` appends a **`ledger.voided`** entry naming the segment, the byte offset of every line in the run, and the error that stopped the apply; commits the segment; and exits non-zero saying that the ledger holds the entry and its voiding and the database is unchanged — never that nothing was recorded. The command can then simply be re-run. The voiding carries the voided event's actor and entity, and its commit is never folded with another (`Endless: ledger.voided E-101 …`), so `git log -- .endless/db-ledger` shows it.

The projector — `event validate-db`, `event rebuild-db` — reads every `ledger.voided` entry before it replays and skips every line one names, reporting the count as `N skipped as voided`. A voiding is itself a replay no-op.

The segment commit waits up to thirty seconds for another git process to release the index, printing that it is waiting. If git still refuses to commit the segment *after* a successful apply, the change stands: it is in the database and on disk, and a segment is committed whole, so the next ledger commit carries the line. The command exits zero and records `WARN-0038 ledger-uncommitted` in the errors channel (`endless errors show`).

**`endless-go event void <segment> --offset <n> [--offset <n>...] --reason <text>`** writes a `ledger.voided` entry by hand, for a run `emit` itself could not void — a process that died between the append and the `COMMIT`, or a line written before the apply came first. It is user-only (an agent is refused before anything is read), Go-only with no `endless` command, and touches no database. The one positional is the segment's file name; `--offset` is the byte offset at which a line begins, repeatable; `--reason` is required. It also takes `--project`, `--project-root` (the main checkout), `--node-id` and `--actor-id`, as `endless-go correct` does. Every named offset is read back first: one that does not start an event line, or that names a voiding, is refused with nothing written. The entry lands in the current segment, which may be later than the one it names — which is why it names it — and is committed on its own.

`event emit` refuses `ledger.voided` from the command line, as it refuses `ledger.row_changed` and `ledger.corrected`.
