Task status answers "what did we decide about this work". It is routinely read as "is this code on main?" and "is this record still authoritative?", and it answers neither. E-2089 measured the cost: E-1115 sat `assumed` with its fix on an unlanded branch, so the same bug was found and fixed a second time 14 days later as E-1395; and thirteen tasks read `confirmed`/`assumed` while the code they describe had been deleted from main, with nothing recorded to say so until E-2089 added the relations by hand. The same gap has a decisions half — I have repeatedly quoted a task or decision as authoritative without noticing it was obsolete, declined, replaced, or not yet accepted.

Five parts, one problem: the reader cannot see the facts that decide whether to trust the row.

(1) `task show` must STATE landedness for a task in a terminal status rather than imply it by omission. Today the `Landed:` line appears only when a `task_landings` row exists, so "landed before landings were recorded" and "the branch is still sitting there" render identically — as nothing. Three cases, three sentences: `Landed: <ts> <sha>`; `Landed: never — created before landings were recorded (pre 2026-04-22)`; `Landed: never — branch <b> holds N commits not on main`.

(2) Add a "not on main" report — the join nothing does today. Tasks in a terminal status, created on or after the first landing record (2026-04-22), with no landing row OR with a branch holding source commits main lacks. The core is one git call per branch and needs no judgement: `B=$(git merge-base main $BR); git range-diff $B..$BR $B..main`, counting rows whose left side is a commit and right side is `-:`. Drop commits touching only `.endless/`. Use `git range-diff`, NOT `git cherry` — E-2087 asks for a patch-id check, and patch-id is exactly what breaks: `worktree land` rebases, conflict resolution changes the diff, and the branch copy then reads as unlanded forever. Measured on this repo, range-diff clears all four known false-positive branches to zero and still flags E-1115, E-1523 and E-2010; worst case ~1.5s on a 320-commit branch. Mike's framing: this belongs in project status (E-1976), not only in a command run by hand.

(3) Make an excision record what it excises. When a task deletes files another task's landed commits created, emit (or prompt for) the `replaced_by` edge — as E-1449 did by hand for the plan-snapshot deletion and as E-1939, E-2029, E-2074, E-2081, E-1426 and E-1711 did not. `endless task replace <old> --by <new>` already does the right thing once called, including holding shipped work at the status it earned; the gap is that nothing calls it. NOTE: this part needs a recording change first. `task_landings` stores a merge SHA but no base, so the landed commit range cannot be reconstructed, and `task_files` stopped recording 2026-07-11. Persist the landed file set (or the base SHA) at land time and the join becomes exact.

(4) Lead `task show`, `decision show` and their siblings with an IMPORTANT banner when the record is not straightforwardly authoritative: task is obsolete/declined/replaced_by, decision is not yet accepted or has been rejected/superseded. The status line is already on screen and is demonstrably not enough — it is read as provenance, not as a caveat. The banner states the caveat before the content it qualifies.

(5) Say it in the guide, next to (1)'s rendering: a task status answers "what did we decide about this work", never "where is the code".

Scope note: parts 1, 2, 4 and 5 are implementable now. Part 3 is blocked on the recording change named in it; if that makes this task too large, split part 3 out rather than dropping the recording change.
