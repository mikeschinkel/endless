Added case (Claude session, 2026-07-09; proposed, not yet decided):

The `git branch --merged main` test catches only FULLY-merged branches. It
misses the common re-land failure where a branch's commit was `git commit
--amend`-ed AFTER its content had already been landed: the branch is then a
partial duplicate of main plus a new delta — not fully merged — so `--merged`
is false and land proceeds into a source-file rebase conflict.

Proposed gate (reuses task_landings, which already records each landing's SHA):
on a re-land (task has >=1 task_landings row), require the branch HEAD to be a
descendant of the last landed SHA:

    git merge-base --is-ancestor <last_landed_sha> HEAD

A correct follow-up (a new commit stacked on a branch first rebased onto main)
passes, because main contains that SHA. An amend/rewrite of the already-landed
commit fails the check. On failure, refuse BEFORE the rebase mutates anything
and print the accurate cause + recovery (the reset+reapply path detailed on
E-1417) rather than today's misleading E-972 auto-file message.

Concrete repro: E-1750's first commit was landed; a follow-up (a legend
addition) was made by amending that commit instead of stacking a new one; the
next `just land` rebase re-applied the whole change onto a main that already
had it -> CONFLICT in internal/sessionstatuscmd/session_status.go. Recovery was
manual reset-to-main + re-apply-delta. Couples to E-1417 (the diagnosis half).
