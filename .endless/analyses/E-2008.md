Observed on E-1817: an analysis was round-tripped through 'endless task show' output, the sed extraction produced a zero-byte file, and 'task update --analysis-file' wrote it over 3.5KB of existing content and printed a normal success line. The content was only recoverable because the session still had it in context; from a fresh session it would have been gone. Applies to the whole family, not just --analysis-file: --description-file, --text-file, --analysis-file, --outcome-file and the decision equivalents all share the shape. Zero bytes is never a legitimate value for these fields, and an empty file is far more often a failed pipeline than an intentional clear. Suggested behaviour: refuse a zero-byte or whitespace-only file with an actionable error naming the path, and require an explicit flag to clear a field (the inline empty-string form already exists for that). Worth checking whether the inline --analysis '' form should be the only clearing path. Related but distinct from E-999 (field separation for plan vs analysis content).


ESCAPE HATCH — decided against --force (2026-08-20). --force was raised and is the one option to avoid, because of WHO hits this refusal: the guard exists to catch a mistake, and --force is the flag a mistaken caller appends after seeing the refusal. An agent whose extraction produced nothing reads 'refused: empty file', adds --force, and blanks the field anyway — the failure mode restored, now with an audit trail that says it was deliberate. A flag named 'just do it' is reflexively retried; that is precisely the behaviour to design against. Endless already has a house pattern for 'I really mean this' and it is not --force: the absolute-path refusal on task add says 'add --allow-path with a regex matching it' — narrow, named for what it permits, and impossible to add without stating what you mean. Preferred resolution: NO escape hatch on the file flags at all. Inline --analysis '' already clears a field, names which field, and cannot be reached by a failed pipeline; the file flags refuse empty unconditionally and the error points at the inline form. Zero new surface. If a file-based clear is judged necessary, --clear <field> beats --force: it names the field and reads as a deliberate act in the ledger.



RESOLVED (2026-08-20, owner): --clear <field> is the chosen escape hatch, not the fallback. File flags refuse a zero-byte or whitespace-only file unconditionally; clearing is an explicit, field-named act. Implementation should make the refusal error name --clear so the recovery path is discoverable at the moment it is needed, and should treat --clear as mutually exclusive with the same field's --*-file / inline flag rather than letting them silently compete.
