  (`LedgerDirName`, writer.go:29), `MkdirAll`s it, `O_APPEND` one line per `Append`

- **`NewWriter` callers** — all in `internal/eventcmd/event.go`, all passing

  **:470** (`runProjectNextRevise`). `makeDerivedEmitter` (:363) reuses the caller's
  writer to append `epic.status_derived` (:400).
- **`CommitLedgerSegment` callers — four**, each now behind a sandbox guard:
  **:230** (guard :228), **:301** (guard :299), **:410** inside `makeDerivedEmitter`
  (guard :406, early-return form), **:484** (guard :482). Note they still receive
  `projectRoot`, not `ledgerRoot(projectRoot)` — correct, because the guard means the
  call only ever happens in the real-checkout case.
- **`ledgerRoot` (event.go:349)** is the whole routing rule:
  `IsSandboxActive() ? monitor.ConfigDir() : projectRoot`. Tested by

  (`PreAllocateTaskID` / `PreAllocateDecisionID` / `BeginImmediate`, all `BEGIN IMMEDIATE`)

- **`--project-root` is still required** on `event emit` (event.go:122). In sandbox mode
  it is **not used for anything**: the writer root is overridden and the commit is

  It resolves `project_root` from `SELECT path FROM projects WHERE name = ?` against

  still seeded from the real main checkout (`internal/sandboxcmd/seed_worktree.go:66-71`),
  so `--project-root` still names the real checkout in a sandbox — `ledgerRoot` is what
  makes that harmless now.
- **`node_id`** — `_get_or_create_node_id` (event_bridge.py:296) reads
  `<ConfigDir>/config.json` and mints `secrets.token_hex(2)` (4 hex chars) on first use.
  Real node `a7f3`; each sandbox mints its own. See §8 for a **measured collision**.

## 3. Location resolution, end to end

DB location and ledger location are resolved by two mechanisms that now agree by
construction, because the ledger derives from the DB's config dir.

- **DB** = `monitor.ConfigDir()/endless.db` (`internal/monitor/db.go:100`).
  `ConfigDir()` precedence (db.go:61): explicit `--config-dir` (consumed by
  `ConsumeDBContextFlag`, db.go:196, first statement in `cmd/endless-go/main.go`) →
  cwd-self-detected sandbox (`SelfDetectWorktreeSandbox`, db.go:390, E-1368) →
  `XDG_CONFIG_HOME/endless` → `~/.config/endless`.
- **`IsSandboxActive()` (db.go:90)** — true iff `ConfigDir()` resolves under
  `CacheDir()/sandboxes`. This is ED-1528's "sole sandbox switch". Six non-test call
  sites: db.go:118 (`ForceRealDB`) and the five in `eventcmd/event.go` listed in §1.
- **`ledgerRoot` = `ConfigDir()` in a sandbox**, so the sandbox ledger lands at
  `<sandbox>/endless/.endless/db-ledger/` — `ConfigDir()` already appends `endless`, and
  `NewWriter` appends `.endless/db-ledger` to whatever root it is handed. Verified on
  disk, e.g. `~/.cache/endless/sandboxes/e-1853/endless/.endless/db-ledger/db-entries-3b27-000001.jsonl`.
- **The pin split is unchanged and still asymmetric.** `ForceRealDB()` (db.go:117, the
  hook) and `PinMainDB()` (db.go:180, `endless-go tmux`) set `dbPathOverride` only;
  neither touches `ConfigDir()`, so **`IsSandboxActive()` stays true under both**. Any
  future ledger write from a pinned binary would therefore target the sandbox ledger
  while the DB row lands in the real database. No such path exists today — the hook and
  tmux binaries do not import `internal/events` — but the split is latent.
- **Python** mirrors the DB half only: `apply_db_choice` (config.py:495) →
  `set_db_context` (config.py:483) sets `CONFIG_DIR` / `DB_PATH` / `RESOLVED_CONFIG_DIR`;
  `go_db_context_args()` (config.py:566) threads `--config-dir` to Go;
  `sandbox_config_dir` (config.py:427) is `<cache>/endless/sandboxes/<e-NNN>/endless`;
  `require_db_context` (config.py:550) and Go `guardWorktreeDBContext` (db.go:672)
  implement the E-1429 refusal. **Python has no sandbox predicate at all** — no
  `is_sandbox()`, no comparison of `RESOLVED_CONFIG_DIR` against the sandboxes root. Its
  artifact writers branch on `worktree_root_for_cwd()`, which answers a different
  question.
- **ED-1554 has not shipped.** Sandboxes still live at `<cache>/endless/sandboxes/<e-NNN>/`,
  not `<worktree>/.endless/sandbox/`. `sandboxesDir()` (`internal/sandboxcmd/sandbox.go:42`)
  is unchanged.

## 4. Git-commit coupling

**`CommitLedgerSegment` (commit.go:47) → `commitPaths` (commit.go:97)** — four gates,
in order:

1. `ensureGitRepo` (commit.go:137) — `git rev-parse --is-inside-work-tree`; otherwise
   `project root %q is not a git work tree`.
2. `ensureMainCheckout` (commit.go:159, E-1309) — refuses when `--git-dir` and
   `--git-common-dir` differ, i.e. a linked worktree. Its doc comment now records that
   in sandbox mode this guard is never reached at all.
3. `canAmend` (commit.go:191) — **four** preconditions now: HEAD subject equals
   `LedgerCommitSubject` (`"Endless: record ledger entry"`, commit.go:28); HEAD not
   reachable from any ref besides the current branch; **no `refs/heads/task/*` tip holds a
   byte-identical `.endless/db-ledger` tree** (`ledgerTreeSharedWithTaskBranch`,
   commit.go:267 — E-1955 / ED-1553, a content-addressed fork-point test that survives
   history rewrites, measured at 16ms across 145 branches); and a clean index outside the
   exclude glob.
4. `git add` + `git commit -o <paths>` with `--amend --no-edit` or `-m`, under
   `sanitizedGitEnv` stripping the `GIT_DIR` family (commit.go:35).

**`events.CommitDoc` (commit.go:65, E-1747)** is the second entry point into
`commitPaths`, for `.endless/<kind>/<ID>.md`. Same main-checkout enforcement, exclude
glob scoped to the doc's own directory, subject is ID-specific so distinct docs never
amend over each other. Reached from Python via `endless-go event commit-doc`
(event.go:58). **It has no sandbox guard.**

**Third path: `src/endless/main_commit.py:commit_path`** — `git add` + `git commit -o`
with the same env stripping, no amend logic. Used for `.endless/verbs.jsonl` (E-1208) and
`.endless/LESSONS.md` (E-2055), sanctioned by ED-1199's global-config exception. **No
sandbox guard.**

**What depends on the ledger commits:**

- Land **Step 3.7** `_drop_orphan_amendable_commits` (worktree_cmd.py:276) — exists only
  because `canAmend` rewrites main's ledger tip, orphaning branches forked from the old
  SHA (E-1342).
- Land **Step 3.75** (worktree_cmd.py:2441, E-1736) — refuses to land any branch commit
  touching `.endless/db-ledger/`, with the offending SHAs listed. This is the backstop to
  the routing policy.
- Land **Step 3** auto-commit assumes ledger dirt on main is committable.
- The rebase-failure recovery advice still tells the user to
  `git checkout <base> -- .endless/db-ledger/*.jsonl`, which assumes the files are tracked.
- **ED-1551**: the segments must never get a git union merge driver — the envelope
  (`internal/events/event.go:18`) carries no unique id and nothing dedups, so a union
  merge manufactures duplicates that double-apply on replay.
- Multi-dev sync: committed per-node segments are the transport.
- **Not** coupled: `endless db backup` is a SQLite `VACUUM INTO`; `db restore` never
  mentions the ledger; `validate-db` / `rebuild-db` read working-tree JSONL, not git
  history.

**Failure behavior — unchanged, and the stray-line hazard is still live.** Every git
failure propagates (`runGit`, commit.go:225) → non-zero exit → `click.ClickException`
(event_bridge.py:229). `Writer.Append` has already run, so a failed commit leaves the
JSONL line on disk with no commit and no DB mutation. That is E-1665, still `unplanned`.

## 5. Sandbox mechanics

- **Create** — `endless-go sandbox init --mode worktree <e-NNN>` + `sandbox bind`, auto-
  invoked on claim/spawn by `_maybe_auto_sandbox_bind` (worktree_cmd.py:1900) when
  `config.project_is_self_dev`. `Provision` (sandbox.go:74) is a plain `os.Mkdir` under
  `CacheDir()/sandboxes` plus `.sandbox-meta.json`. **There is still no `git init`
  anywhere in `internal/sandboxcmd`** — the sandbox dir is not a repo.
- `seedFromWorktree` (seed_worktree.go:30) creates `<dir>/endless/endless.db` from
  `schema.SQL`, inserts a `projects` row copied from the real main DB (so `path` = the
  real checkout) and a `sessions` row, and writes `<dir>/endless/config.json`.
- `bindCmd` (bind.go:15) writes `XDG_CONFIG_HOME=<sandboxDir>` into
  `<worktree>/.claude/settings.json` and sets skip-worktree on it.
- **Destroy / reap / prune** — `destroy.go:63`, `reap.go:64` (E-1904, wired from
  `cmd/endless-go/main.go` so the worktree reaper takes the sandbox with it), `prune.go:77`,
  all `os.RemoveAll(dir)`, all refusing when `findLiveWriters` sees open files.
  **Since E-1729 this also erases the sandbox's ledger** — which is exactly ED-1525's
  intent ("erased atomically by sandbox destroy"), and also means a sandbox ledger can
  never be recovered or replayed after the sandbox is gone.
- **Isolated today:** the DB, `config.json`, logs, and the ledger. **Not isolated:** doc
  mirrors, `verbs.jsonl`, `LESSONS.md`, and session/pane/channel state (deliberately —
  E-1450 pins those to the real DB).
- **Current scale:** 156 sandbox dirs, 164 MB. 35 carry a `node_id`; 26 hold a local
  ledger.

## 6. Event-sourcing invariants

- **Write contract:** lock → ledger line → commit (real context only) → SQL. A losing
  concurrent writer fails at `BEGIN IMMEDIATE` before writing an orphan line.
- **Replay is ordered solely by kairos TS** (reader.go:44). The envelope has no sequence
  number and **no unique id**, and neither `ReadAllEvents` nor the projector dedups —
  the basis of ED-1551.
- **Entity ids replay verbatim** with no collision handling, and ids are DB-scoped
  pre-allocations, so two DBs freely allocate the same id for different entities. That
  is the mechanism behind every UNIQUE warning in §8.
- **No snapshots, no upcasting.** Projection always replays from event zero; `V != 1` is
  hard-rejected. The upcasting pipeline is still open (E-1671, `submitted`).
- **A second ledger *directory* is still unsupported.** `ReadAllEvents` reads exactly one
  root; there is no cross-dir merge. Sandbox and real ledgers are two disjoint,
  never-merged event streams.
- **`rebuild-db` no longer round-trips.** With `--confirm` refused, "SQLite is a
  rebuildable projection" is currently an aspiration, not a working property, in either
  context. Anything that reasons "the ledger is authoritative because the DB can be
  rebuilt from it" is describing E-799's future state.

## 7. The product-testing case — how ledger/commit machinery is tested today

The pattern set is unchanged in kind; the canonical example is now E-1729's own verify
script.

1. **Throwaway `git init` repo as `--project-root`, temp config dirs, and a fake sandbox
   under a temp `XDG_CACHE_HOME`.** `tests/tasks/e-1729-verify.sh` is the reference
   implementation and states the rule in its header: sandbox detection is
   ConfigDir-under-CacheDir/sandboxes, and `CacheDir` honors `XDG_CACHE_HOME`, so a fake
   sandbox needs no real one. It self-describes as "the E-1596 ad-hoc-prototype shape,
   not a shared harness". `tests/tasks/e-1664-verify.sh` (`make_ledger_repo`) is the same
   shape. **Needs: real git commits on a real repo.**
2. **Go tests with `initRepo`** — `internal/events/commit_test.go`,
   `commit_identity_test.go`, `internal/eventcmd/epic_derivation_test.go`: `t.TempDir()` +
   `git init` + identity + initial commit, covering the amend / pushed / linked-worktree
   matrix. `internal/eventcmd/ledger_root_test.go` covers the routing helper with
   `t.Setenv` alone and no repo at all.
3. **Fabricated JSONL segments, no git** — `internal/eventcmd/event_test.go:writeLedgerEvent`
   hand-writes segment lines for `validate-db` / `rebuild-db`. The read side never touches
   git.
4. **DB-only** — executor-level tests against a `t.TempDir()` SQLite file.
5. **pytest `isolated_env`** (`tests/conftest.py`) — monkeypatches CONFIG_DIR/DB_PATH and
   exports `XDG_CONFIG_HOME` so spawned Go subprocesses share the temp DB.
6. **Real-routing assertions** — verify scripts that drive the actual sandbox/main dirs.

Of 200 task verify scripts, 28 pass `--project-root` and 8 do a `git init`. **No test
relies on a sandbox hosting a committing ledger.** The real-commit need is met
exclusively by throwaway repos, in both Go and shell.

## The decision space, as the facts now stand

Three of the four axes the July map laid out are closed. Naming what is closed matters as
much as naming what is open, because the closed ones keep getting re-proposed.

**Closed — decided and shipped:**

- *Where a sandbox emit's ledger line lands* — sandbox-local, at `ConfigDir()`
  (ED-1525, E-1729). The three alternatives are explicitly rejected in ED-1525's text,
  and the "repoint `projects.path`" option is doubly dead: the seed still writes the real
  path there and nothing consults it for the ledger any more.
- *Commit behavior for a non-real ledger* — skipped, keyed on `IsSandboxActive()`
  (ED-1525, ED-1528). `git init`-ing sandboxes is rejected by name.
- *Who decides the target* — the resolved config dir, implicitly, ED-1528. No flag, no
  env var.
- *The product-testing case* — served by throwaway `git init` repos, never by sandboxes.
  E-1729's own verify script is the worked example.

**Open:**

1. **Explicit resolved value vs re-derived predicate.** ED-1528 makes the path shape the
   answer. The measured consequence: the predicate has 6 non-test call sites, 5 of them
   in one file, Python has none at all, and every writer that does not ask it is
   unisolated silently — which produced a 0-byte `ED-1.md` on main six weeks after the
   ledger was fixed. E-2059 carries this decision; E-2035 cannot be planned without it.
2. **Where the sandbox lives.** ED-1525 (accepted) and ED-1554 (proposed) contradict each
   other on this and are not linked. `ledgerRoot()` returns `ConfigDir()`, so moving the
   sandbox into the worktree moves the ledger into a real git checkout — where land Step
   3.75 would then refuse the branch. That interaction is a fact either answer has to
   absorb.
3. **What exactly E-1730 excises.** §8 gives the per-line split ED-1527 requires:
   1,047 clearly bug-written (11 of them occupying real ids 1034-1039), 18 clearly
   legitimate, 6 needing a call. Node-id excision is measurably unsafe — node `9000` is
   real history, node `86eb` interleaves two real landings with fixtures, and node `3b27`
   is a confirmed collision between a 2026-06 writer and a 2026-08 sandbox.
4. **Whether excision alone is the treatment.** ED-1527 (excise class 3) and ED-1563
   (a shipped bug's damage is repaired by a change file at land) point at the same
   cleanup from different directions, and E-1716/E-1720 hold the tombstone mechanism for
   class 2. Which instrument the 6 ambiguous lines get is unsettled.
5. **What "events-authoritative" means while `rebuild-db --confirm` is refused.** Until
   E-799, the ledger cannot actually be replayed back over the DB in either context. Any
   argument that leans on rebuildability is currently leaning on future work.
6. **The pinned-binary split.** `ForceRealDB` / `PinMainDB` move the DB to main but leave
   `IsSandboxActive()` true, so a pinned binary that ever wrote the ledger would split the
   two. No such path exists today; nothing prevents one being added.
