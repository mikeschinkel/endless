# E-1732 findings — Ledger-target routing (main vs sandbox vs test) and git-commit constraints

Factual map for the follow-on policy brainstorm (which re-plans E-1729). No recommendation is made.
All references verified against worktree `task/1732-research-endless-s-ledger-target-routing` (forked from main a0b3f627).

## 1. Write paths

**There is exactly one ledger writer in the system: the Go `endless-go event emit` path.** Everything else funnels into it.

- `internal/events/writer.go:46 NewWriter(projectRoot, nodeHex)` — ledger dir is a hard-coded join: `<projectRoot>/.endless/db-ledger` (`LedgerDirName`, writer.go:29). Segment files `db-entries-<nodeHex>-NNNNNN.jsonl`, rotated at `DefaultMaxEventsPerSegment = 500` (writer.go:23). `Writer.Append` (writer.go:72) is an `O_APPEND` one-line write; the writer itself is git-agnostic and `MkdirAll`s the dir.
- **All `NewWriter` callers** are in `internal/eventcmd/event.go` (verified by grep; the only other importer of `internal/events`, `internal/sessionquerycmd/session_query.go:134`, is read-only): event.go:192 (create/pre-alloc flow), event.go:268 (update/delete flow), event.go:424 (`runProjectNextRevise`). The derived-emitter closure `makeDerivedEmitter` (event.go:323) reuses the caller's writer to append `epic.status_derived` (event.go:357).
- **`CommitLedgerSegment` has FOUR callsites, not three** — event.go:207, :278, :361 (inside `makeDerivedEmitter`), :436. E-1729's drafted plan says "the 3 CommitLedgerSegment calls"; that count is stale/wrong and the re-plan should absorb the fourth (the epic-derivation one).
- **Write ordering (events-authoritative):** DB write-lock first (`PreAllocateTaskID`/`BeginImmediate` do `BEGIN IMMEDIATE`, `internal/events/executor.go:117-137`), then ledger append, then `CommitLedgerSegment`, then the SQL mutation + `COMMIT`. A commit failure aborts before the DB mutation — but **after** the JSONL line is on disk (see §4).
- **`--project-root` is a required flag on `event emit`** (event.go:62,98-100). The Go side does no resolution of its own; resolution happens upstream in Python.
- **Python `emit_event`** (`src/endless/event_bridge.py:77`) never writes the ledger itself; it shells out to Go (event_bridge.py:204-228) passing `*config.go_db_context_args()` (→ `--config-dir`) **and** `--project-root`. Project root resolution (event_bridge.py:184-198): `SELECT path FROM projects WHERE name = ?` **against whichever DB is active** — deliberately the registered main checkout, not cwd; falls back to `Path.cwd()` only for unregistered projects. Note the routing consequence: a sandbox DB's `projects.path` is seeded from the **main** DB's row by `seedFromWorktree` (`internal/sandboxcmd/seed_worktree.go:44-45`), so sandbox emits resolve the **real** checkout as their ledger root. This single seeded value is what points sandbox ledger writes at the production ledger.
- **`node_id`**: `_get_or_create_node_id` (event_bridge.py:283) reads `config.CONFIG_FILE` = `<resolved config dir>/config.json` and mints `secrets.token_hex(2)` (4 hex chars) on first use. Real node = `a7f3` in `~/.config/endless/config.json`; each sandbox mints its own node id in `<sandbox>/endless/config.json`. 4 hex chars = 65,536-value space (collision odds grow with sandbox count; ~40 sandboxes ≈ 1.2% birthday collision).
- **`worktree land`** (`src/endless/worktree_cmd.py:1478 land_worktree`) has three ledger-adjacent steps: Step 3 auto-commits accumulated dirt matching `AUTO_COMMIT_GLOBS` (worktree_cmd.py:54: `.endless/db-ledger/*.jsonl`, verbs files) as `"Endless: auto-record session activity"` — a plain, non-amendable commit on `main_root`; Step 3.7 `_drop_orphan_amendable_commits` (worktree_cmd.py:258) strips orphaned `"Endless: record ledger entry"` commits at branch base (exists because `canAmend` rewrites ledger-tip SHAs on main, E-1342); Step 6 `_record_landing` (worktree_cmd.py:1434) emits `task.landed` through the normal `emit_event` → Go path.
- **The hook binary does NOT write the ledger** — `internal/hookcmd/` has no `internal/events` import. Hook-attributed events go through Python `emit_event` with `actor_kind="hook"` (`_ATTRIBUTION_REQUIRED`, event_bridge.py:24).
- **The channel MCP does NOT write the ledger** — `internal/channelcmd/channel.go` is an HTTP notify/inbox server; `src/endless/channel_cmd.py` has no `emit_event` calls.

## 2. Read paths

- `internal/events/reader.go:16 ReadAllEvents(projectRoot)` — reads `<projectRoot>/.endless/db-ledger`, globs ALL `db-entries-*.jsonl` regardless of node, merges, sorts by `evt.TS` (kairos; lexicographic = causal). Missing dir → `nil, nil`. **Its only caller is `ProjectToTempDB`** (projector.go:31).
- `internal/events/projector.go:28 ProjectToTempDB(projectRoot)` — replays into a temp SQLite DB at `<projectRoot>/.endless/projection-temp.db`; errors on zero events (projector.go:36-38).
- **Callers, both in `internal/eventcmd/event.go`:** `runValidateDB` (event.go:460) and `runRebuildDB` (event.go:520). Both take a **required `--project-root` flag** for the ledger and resolve the live DB independently via `monitor.DB()` (event.go:486, :550). `validate-db` compares and mutates nothing; `rebuild-db --confirm` ATTACHes the temp DB and **deletes + reinserts the project's entire `tasks`/`decisions`** from the projection (event.go:571-595).
- No Python or justfile caller invokes `validate-db`/`rebuild-db`; they are manual/test-invoked.

## 3. Location resolution, end to end

**DB location and ledger location are resolved by two entirely independent mechanisms.**

- **DB** = `monitor.ConfigDir()/endless.db` (`internal/monitor/db.go:100-105 DBPath`). `ConfigDir()` precedence (db.go:61-70): explicit `--config-dir` (consumed by `ConsumeDBContextFlag`, db.go:196, first thing in `cmd/endless-go/main.go:61`) → self-detected sandbox → `XDG_CONFIG_HOME/endless` → `~/.config/endless`.
  - `SelfDetectWorktreeSandbox()` (db.go:289-313, E-1368): fires only when no explicit context; derives `e-NNN` from the `/.endless/worktrees/e-NNN` cwd marker; requires `projectIsSelfDev(root)` (db.go:319-331 reads `<root>/.endless/config.json` `self_dev`) AND the sandbox dir existing on disk; routes via `setDetectedContextDir` — deliberately weaker than the explicit flag, so `ForceRealDB()` (hook, db.go:107-126) and `PinMainDB()` (channel/tmux, db.go:180-186) still win (the E-1450 split: session/pane/channel state stays on the real DB even in a sandbox; config.json + logs follow the sandbox).
  - `IsSandboxActive()` (db.go:90-97): true iff `ConfigDir()` resolves under `CacheDir()/sandboxes`.
  - Python mirror: `apply_db_choice("main"|"sandbox")` (`src/endless/config.py:248-268`); `sandbox_config_dir` = `<cache>/endless/sandboxes/<e-NNN>/endless` (config.py:204-213); `set_db_context` (config.py:236-245); `go_db_context_args()` → `["--config-dir", RESOLVED_CONFIG_DIR]` (config.py:308-318); E-1513 re-exec into the worktree's Python source for `--db sandbox` (`src/endless/cli.py:200-206`); E-1429 gate `require_db_context` / Go `guardWorktreeDBContext` (config.py:292-305; db.go:404-419) refuses ambiguous DB opens inside a self-dev worktree.
- **Ledger** = `<projectRoot>/.endless/db-ledger`, where `projectRoot` = the `--project-root` flag = Python's `projects.path` lookup (§1). `go_db_context_args()` threads only DB location; **nothing anywhere threads a ledger location** — it is always derived from project root. `--db main|sandbox` therefore moves the DB and leaves the ledger fixed on the real checkout. This is the E-1729 bug mechanism, stated in code at `internal/events/commit.go:135-138` (sandbox routing affects the DB only).

## 4. Git-commit coupling (E-1206)

**What `CommitLedgerSegment` does** (`internal/events/commit.go:43` → `commitPaths`, commit.go:78):
1. `ensureGitRepo` (commit.go:118): `git rev-parse --is-inside-work-tree`; not a work tree → error `"project root %q is not a git work tree"`.
2. `ensureMainCheckout` (commit.go:139, E-1309): `--git-dir` vs `--git-common-dir` differ (linked worktree) → refuse. Auto-commits land on main, never a task branch.
3. `canAmend` (commit.go:169): amend iff HEAD subject == `LedgerCommitSubject` (`"Endless: record ledger entry"`, commit.go:24) AND HEAD not reachable from any other ref AND index clean modulo the ledger glob. Then `git add` + `git commit -o <segment>` with `--amend --no-edit` or `-m`.
4. Runs with `sanitizedGitEnv` (commit.go:258) stripping `GIT_DIR`/`GIT_WORK_TREE`/etc.

**Why it exists:** E-1206 (confirmed) — every ledger write becomes git history at write time (durability; no accumulating dirt between lands); the amend strategy bounds commit count to one rolling ledger commit between feature commits, never rewriting pushed history. E-1206 explicitly decided fail-loudly, including "project root is not a git repo → fail; soften only when beta testers make it concrete."

**What depends on the commits:**
- `worktree land` Step 3.7 orphan-drop (`worktree_cmd.py:258-266`) exists solely because `canAmend` rewrites main's ledger-tip SHA, orphaning branches forked from the old SHA (E-1342).
- Land Step 3 assumes db-ledger dirt is committable (`AUTO_COMMIT_GLOBS`).
- The land rebase-failure recovery message (`worktree_cmd.py:1626-1637`) instructs `git checkout <base> -- .endless/db-ledger/*.jsonl` — assumes ledger files are git-tracked.
- Multi-dev sync: committed segments are how another machine gets the ledger (per-node segment naming exists to avoid git merge conflicts — recorded in the ledger itself, event for E-906).
- NOT coupled: `endless db backup` is a SQLite `VACUUM INTO` (event.go:758); `validate-db`/`rebuild-db` read working-tree JSONL, not git history; `just land` delegates to `worktree land` (justfile:227-247).

**Failure behavior — hard, with a known stray-line hazard:** every git failure propagates (`runGit`, commit.go:225) → emit exits non-zero → Python raises `click.ClickException` (event_bridge.py:229-231). But `Writer.Append` has already run, so **a failed commit leaves the JSONL line on disk with no commit and no DB mutation** — exactly E-1665's observed pollution-by-failed-emit. There is **no code path that skips the commit**; it is unconditional after every append.

## 5. Sandbox mechanics (E-1281)

- **Create:** `just dev-sandbox-init` (justfile:414-439, refuses main checkout) → `endless-go sandbox init --mode worktree <e-NNN>` + `sandbox bind <worktree> <e-NNN>`. Auto-invoked on claim/spawn by `_maybe_auto_sandbox_bind` (`worktree_cmd.py:1285`), gated on `config.project_is_self_dev` (config.py:118-130); failures warn, don't abort.
  - `initCmd` (`internal/sandboxcmd/init.go:10`): modes `empty`|`worktree` only (`seed`/`clone` unimplemented); idempotent unless `--force`.
  - `Provision` (`internal/sandboxcmd/sandbox.go:74`): plain `os.Mkdir` under `CacheDir()/sandboxes` + `.sandbox-meta.json`. **The sandbox dir is NOT a git repo** — no `git init` anywhere in sandboxcmd; `seedFromWorktree` runs only read-only `git rev-parse` to find the main checkout.
  - `seedFromWorktree` (`seed_worktree.go:30`): creates `<dir>/endless/endless.db` with `schema.SQL`, inserts a `projects` row **copied from the main DB (path = real checkout)** and a `sessions` row, writes `<dir>/endless/config.json` from a hardcoded default.
  - `bindCmd` (`internal/sandboxcmd/bind.go:15`): writes `XDG_CONFIG_HOME=<sandboxDir>` into `<worktree>/.claude/settings.json` env block; sets skip-worktree.
- **Destroy:** `destroyCmd` (`internal/sandboxcmd/destroy.go:10`): refuses if live writers hold files open (unless `--force`), then `os.RemoveAll`. **Destroying a sandbox erases its node_id mapping** — the real ledger's leaked segments from destroyed sandboxes become orphan node ids (see §8).
- **What it isolates:** the DB, config.json, and logs (everything under `ConfigDir()`). **Not the ledger** (§3), and deliberately not session/pane/channel state (E-1450 pins those to the real DB).
- **`self_dev` gates:** sandbox auto-provisioning (worktree_cmd.py:1298), Go cwd self-detect (db.go:298), the E-1429 DB-context refusal (db.go:404-419), hook-binary selection (db.go:343-378), self-dev land behaviors (worktree_cmd.py:1338-1352).

## 6. Event-sourcing invariants

- **Events-authoritative write contract:** lock → ledger line → git commit → SQL, per the comments at event.go:145-148/:202/:262/:418 and `executor.go:124-128`. A losing concurrent writer fails at `BEGIN IMMEDIATE` before writing an orphan line.
- **Projection assumptions:** replay is ordered **solely by kairos TS** (reader.go:44-47) — the envelope has no sequence number (`Event`, event.go:17-26). Entity ids are replayed **verbatim with no collision handling** (`projector.go:146 mustParseInt64(evt.Entity.ID)`); ids are DB-scoped pre-allocations, so two DBs (main + a sandbox) freely allocate the same id for different entities — which is precisely why leaked sandbox events collide (UNIQUE/FK noise). `rebuild-db --confirm` assumes ONE complete ledger per project: it deletes and reinserts the whole project from the single projection (event.go:571-595).
- **No snapshots, no upcasting yet:** projection always replays from event zero; `V != 1` is hard-rejected (event.go:274-276). The upcasting pipeline is pending (E-1671); today the projector is leniently hand-coded for legacy shapes (projector.go:129-135, :568-580) because "the events ledger records history and cannot be rewritten".
- **Multi-writer:** one dir, per-node segment files, merged by TS at read. A second ledger *directory* has no support anywhere: `ReadAllEvents` reads exactly one root; there is no cross-dir merge; and `CommitLedgerSegment` refuses roots that aren't the main checkout of a git repo.

## 7. The <1% product-testing case — how ledger/commit machinery is tested today

Five distinct harness patterns exist (no shared harness; the shell ones self-describe as the "E-1596 ad-hoc-prototype shape"):

1. **Throwaway `git init` repo as `--project-root` + separate temp DB via `--config-dir`/XDG** — the pattern for anything that exercises the real emit path, because that path *requires* a committable main-checkout repo. Used by `tests/tasks/e-1719-verify.sh:100-153` (Section C: `mktemp -d`, `git init`, `--allow-empty` commit with pinned `GIT_COMMITTER_DATE`, then `event emit ... --project-root "$REPO" --config-dir "$GODIR"`), `tests/tasks/e-1664-verify.sh:116-151` (`make_ledger_repo`, comment cites E-1309), and Go `internal/events/commit_test.go:26-34` (`initRepo`: `t.TempDir()` + `git init` + identity + initial commit; full amend/pushed/worktree-refusal matrix) and `internal/eventcmd/epic_derivation_test.go:104,189`. **Needs: real git commits on a real repo.**
2. **Fabricated JSONL segments, no git** — `internal/eventcmd/event_test.go:112-127 writeLedgerEvent` hand-writes segment lines for `validate-db`/`rebuild-db` tests. **Needs: only a directory with segment files** (read side never touches git).
3. **DB-only** — executor-level tests against a `t.TempDir()` SQLite file (`internal/events/task_landed_test.go`); no ledger at all.
4. **pytest `isolated_env`** — `tests/conftest.py:13-77` monkeypatches CONFIG_DIR/DB_PATH AND exports `XDG_CONFIG_HOME` so spawned Go subprocesses share the temp DB; stubs the E-1513 re-exec.
5. **Real-routing assertions** — `e-1628-verify.sh`, `e-1368-verify.sh`, `e-1662-verify.sh` drive the actual sandbox/main dirs to assert routing/pinning, no throwaway repo.

**No test today relies on a sandbox hosting a ledger or on sandbox emits committing.** The real-commit need is met exclusively by pattern 1's throwaway repos. E-1665 (open brainstorm) exists because pattern 1 is a convention you can forget — a hand-run `event emit --project-root <real-repo>` pollutes before the guard rejects it (§4).

## Decision space the facts imply (options only — choosing is the brainstorm's job)

The policy question decomposes into four independent axes:

**A. Where does a sandbox/test emit's ledger line land?**
1. Real project ledger (status quo — the bug).
2. Sandbox-local ledger, `ConfigDir()/.endless/db-ledger` (E-1729's draft). Mechanism exists: every read/write already funnels through `internal/eventcmd/event.go`; swapping the root at 3 `NewWriter` + 2 `ProjectToTempDB` callsites re-targets everything.
3. No ledger for sandbox emits (DB-only). Already ruled out in E-1729's draft as incompatible with events-authoritative (`rebuild-db` in a sandbox would wipe sandbox state); recorded here as considered-and-rejected.
4. Re-point via the data, not the code: the ledger root is just `projects.path` in the **active** DB (§1). Seeding the sandbox's `projects.path` to the sandbox dir would re-route emits with zero Go changes — but `path` is also used for other purposes, and the commit path would then hard-fail (sandbox isn't a git repo), so this axis interacts with axis B.

**B. Commit behavior for a non-real ledger.** Facts constraining it: `CommitLedgerSegment` fails hard without a main-checkout git repo (§4); the sandbox dir is not a git repo (§5); nothing downstream (amend/land/recovery/multi-dev sync) cares about a *sandbox* ledger's git history — those dependencies are all about the real repo (§4). Options: skip commits when `IsSandboxActive()` (E-1729 draft); `git init` each sandbox to keep the code path uniform; or make commit-vs-skip an explicit property of the ledger target rather than of sandbox detection.

**C. Who decides the target?** (a) Implicit sandbox self-detection — `IsSandboxActive()` derived from `ConfigDir()` (E-1729 draft: no Python change, hooks/tests inherit it); (b) an explicit flag (`--ledger-root` or similar) making the target a stated input like `--project-root` is today — which is also what every existing test harness effectively does by hand (§7); (c) the DB's `projects.path` (option A4). Fact to weigh: today NO mechanism threads a ledger location anywhere — it is 100% derived — so any explicit option adds a new surface.

**D. The <1% real-commit testing case.** Facts: that case is served today by throwaway `git init` repos via `--project-root`, in both Go tests (`commit_test.go:initRepo`) and shell verifies (§7), and never by sandboxes. So "sandbox skips commits" removes nothing those harnesses use — but E-1665 documents that the throwaway-repo convention is forgettable and the failure mode of forgetting it is exactly this pollution. Whether the fix folds a safe default into the emit path (E-1665's question) or stays a test convention is part of the brainstorm.

**Read-side symmetry (applies to any option):** whatever root emits write to, `validate-db`/`rebuild-db` under `--db sandbox` must read the same root, or sandbox rebuilds replay the wrong ledger (E-1729's draft covers this via the same helper at both `ProjectToTempDB` callsites).

**Cleanup interaction:** E-1730 (excise) vs E-1716/E-1720 (append-only tombstoning) prescribe different treatments for pollution already in the ledger; §8 shows node-id-based excision would clip some real-looking events (`task.landed` 1542/1628, the a7f3-node sandbox) — a fact the cleanup decision needs regardless of the isolation policy chosen.
