# E-1815 — auto-spawn runtime and the monitor window

Brainstorm outcome. Three seed threads: (1) how an eligible task gets spawned
with no user command, (2) whether the selector lives in a Claude-less tmux
window and what that breaks, (3) the UI/UX for observing and intervening.

## The structural resolution: trigger and display are separable

The seed hypothesized a dedicated tmux window hosting both the selector and the
monitor. The conversation split those apart, and they turn out to be justified
by different things.

**The trigger is a registered job**, not a new process. Endless already runs
background work on the E-698 fire-once runner: no daemon, no internal timer,
repetition supplied by whatever fires it. Auto-spawn selection becomes another
registered job on that runner. Nothing new is invented.

**The window is justified by display**, not by trigger. It exists because the
project-scoped attention dashboard needs somewhere to live and ~57 unverified
tasks / many concurrent sessions need managing. Had the window been justified
only as "somewhere the loop runs," it would have been a daemon in disguise.

## Consequence, chosen deliberately: window open == auto-spawn on

Because the monitor window fires the runner, auto-spawn only happens while that
window is open. Accepted for v1 as a feature, not a limitation:

- Closing the window is a physical kill switch requiring no code, no config,
  and no ambiguity about whether the feature is on.
- The user is by construction present-ish when work is initiated.
- It defers the daemon decision rather than inheriting one. Surviving a closed
  window is exactly the point at which a daemon is being chosen, and that
  should be an explicit later choice.

## Focus stealing — the requester's top worry — is one flag

`tmux new-window -d` creates the window without selecting it. No new mechanism,
no dedicated process needed to avoid stealing focus. Folded into E-1814.

## tmux topology

- The dedicated monitor gets **its own tmux session**, two panes: the project
  monitor, and a bare shell for running `endless` commands against what it
  shows. (The bare shell is `agentenv` `unknown`; the CLI fails open there and
  the hook no-ops, which is the desired behavior.)
- Auto-spawned session windows land in the **user's current tmux session**,
  interleaved with manual work. A separate review-batch session was considered
  and rejected: out of sight, out of mind is precisely the failure mode that
  produced the existing unverified sediment.
- Because the selector runs in the monitor's tmux session, `new-window` must
  name an explicit target. Config value, default `active` (the user's session),
  with `monitor` as the other value. More flexible targeting later.
- When no tmux client is attached, `active` resolves to nothing. The selector
  skips the run and records why rather than guessing a session — so auto-spawn
  naturally pauses while fully detached.

## Provenance: no spawner row, no synthetic actor, no third session kind

Three candidates were considered for `spawned_by` on an auto-spawned session:

1. **The filing session.** Rejected. Endless already records it as the
   `surfaced` relation, so this duplicates an existing fact while destroying
   the only place that could record the honest one (that nothing launched it).
   It also points at a session that may not appear in the session list.
2. **A session row for the monitor itself** (a third `sessionkind` beside
   `Tmux` and `Background`). Rejected — both arguments for it dissolve. The
   navigability argument is empty: the monitor window is always reachable
   directly, so a pointer to it buys nothing. The state-recording argument is
   already covered — `endless jobs list` holds last run, next due, run count
   and failures; faults land in the errors table as `ERR-NNNN` with the badge
   on the monitor. (Also noted: `SessionKindBackground` is not mature; real
   limitations in Claude Code's background tasks shelved it.)
3. **Nothing.** Chosen. `spawned_by` stays null, already a valid state for any
   hand-started session. The fact that matters is `auto_spawned`, and it
   belongs as a flag on the *spawned* session, because that is where the
   distinguishing icon renders anyway.

A third session kind may still earn its way in later, but not for this.

## Two governors, both from existing machinery

Cap and throttle are distinct and both wanted.

**Throttle (rate).** Protects against CPU spikes, tmux instability (crashes
have happened), contention, and it provides a reaction window before a batch
leaves the gate. Carried by **the job's own cadence field** — the jobs system
already has per-job cadence and next-due. The monitor fires the runner every
tick; the runner executes the selector only when due; the selector spawns at
most one task per due-run. Rate is therefore a field that already exists, is
inspectable via `jobs list`, and is adjustable without touching the monitor.
No timer to build, and it is decoupled from the monitor's own refresh rate
(2s would be far too fast — Claude takes tens of seconds to start working).

**Cap (backpressure).** Counts **auto-spawned unverified tasks, per project.**

The cap was originally proposed as a WIP limit on total unverified — throttle
the review queue rather than concurrency, since the scarce resource is the
user's review capacity, not CPU or tmux windows. Measurement killed that
formulation: 57 unverified in `endless`, 75 machine-wide, and **71 of the 75
are 30–90 days old** (3 at 7–30 days, 1 in the last week). That is sediment,
not a queue — an 80-day-old unverified task is not awaiting attention, it is
awaiting a decision about whether it is still real. A cap of 3 against a floor
of 57 would never clear and the feature would ship dead on arrival.

Counting only auto-spawned unverified is self-limiting, works at any backlog
size, and scopes the governor to exactly what auto-spawn is responsible for not
burying the user with. The `auto_spawned` flag is the query. If the backlog
ever drops far enough for a total count to be meaningful, switching is a
`WHERE` clause.

Alternatives considered and set aside: counting unverified with unsettled
worktrees (more meaningful in principle, but most of the 57 are landed-and-
unconfirmed so it would read near zero and cap nothing); counting unverified
updated within a rolling window (works, but N cannot be picked correctly on the
first try); draining the backlog first and then using a total count (cleanest
end state, but blocks the feature on a large manual pass — pursued
orthogonally instead, see follow-ups).

**Cap scope is per project.** A machine-wide ceiling is deferred: it is roughly
five lines (the same count query minus the project filter), but with `endless`
dominating so heavily today the number could not be exercised, and an untested
ceiling first binds on the worst possible day. Multi-project is real but not
busy — six projects have unverified work (endless 57, gomion 7, h2pp 6,
go-tealeaves 3, macmail-ext 1, init 1). Add the ceiling the day a second
project gets busy.

**Stalled sessions count against the cap.** A session paused on a permission
prompt is making a claim on the user's attention, and the cap measures claims
on attention — no special case. Sessions pausing on prompts until noticed is
accepted behavior, not something to design around. This is safe only because
the project monitor makes "waiting on you" loud, which is what makes the
attention dashboard load-bearing rather than polish.

## Why the sediment exists

Diagnosed during the session: the 57 accumulated before the session monitor
existed, when there was no good way to keep track of unverified work, and two
tmux crashes took unverified tasks out of sight.

This matters for scoping the cleanup. **Prevention is largely already in
flight** — the session monitor exists, and the project monitor designed here
surfaces unverified first by construction. What remains unbuilt is the
**drain**: working through the existing 57, most of which need per-task
judgment about whether they are still current, superseded, or obsolete. That is
also the single highest-leverage item surfaced in this conversation by ED-1550's
own arithmetic, which names closing as the only fast lever on the file-to-close
ratio.

Existing coverage checked: E-1881 (continuous auto-merge job for
endless-managed worktree commits) and E-1882 (`worktree reconcile` for stale
endless-managed commits) cover *git* currency. Nothing covered *task-status*
currency.

## Named and deliberately not filed

- Auto-verify and auto-land of completed auto-spawned work. Wanted, explicitly
  downstream — a problem worth having once the feature runs.
- Stall detection for sessions that hang. Explicitly a problem the requester
  wishes he had.
- Collapsible tree view and jump-to-session-in-another-terminal in the project
  monitor. Acknowledged as the destination, scope deliberately not taken on now.
- Machine-wide cap ceiling (see above).
- Optimizing prompts so auto-spawned work needs no user questions — being
  discussed in E-1959 alongside Karpathy-style autoresearch. A later
  enhancement, not needed for the initial feature.
- Adding the filing session to `session status`. Raised, then made moot by the
  provenance resolution.

## Standing constraint on the whole feature

Most tasks will not be eligible for auto-spawn. Volume is low by design, which
is what makes the simple governors above sufficient for v1.
