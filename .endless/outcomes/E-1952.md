# E-1952 — Synthesis: `task report` is the wrong shape, not the wrong implementation

## The seed was too small

The task was filed around four render defects in `task report`: all-or-nothing
validation, undiscoverable statelessness, a false `Nothing to report.` at
`unverified`, and the PostToolUse hook firing on `--help`. (The last one
reproduced live during this session: running `task report --help` injected the
full "append the block, unchanged" instruction with no block rendered.)

All four are real. None of them are why the command has failed. The requester
converted this to a brainstorm specifically to widen it past that list.

## What the command was actually for

`task report` was requested out of exasperation at agent verbosity. Its purpose
was never "produce a report" — it was **bound the agent's output**. Three
attempts, three failures:

1. Report replaces the reply → the agent editorialized around it anyway.
2. Report is appended after freeform prose → the block is `Nothing to report.`
   most of the time, and noise the rest.
3. The block's spec grew content the requester never asked for (filed
   follow-ups), which `session status` already renders. That was unilateral
   scope, not a feature.

## The diagnosis

The verify command *existed*. The agent wrote it in prose, then told
`task report` there was nothing to report.

The block is not failing to find content. **The agent is failing to route
content into it**, because the command requires re-stating in a structured
field something already said in freeform. Given two output channels and no
enforcement, everything lands in the cheap one.

The consequence is decisive: **any design where the agent volunteers the
payload fails identically.** Partial success, persistence, better help text —
none of the four seed fixes touch the actual defect. They would all ship, and
the agent would still put the verify command in prose and pass nothing.

Restated: there are two channels and content lands in the wrong one. Every
attempt so far added rules to the block. The alternative is to **delete a
channel**.

## The design the requester proposed

`task report` accepts whatever the agent wants to send. An adversarial agent
aggressively minimizes it. The agent must reply with that output verbatim, and
a hook errors if it does not.

This dissolves the four seed symptoms for free — nothing is rejected, so there
is no all-or-nothing render and no ceremony bounce — but that is incidental.
What it fixes is the enforcer. The spec ("report only what the user cannot
compute themselves") was always right; the agent was the wrong party to apply
it, judging its own output in the same breath as writing it.

### Settled during the session

- **Input is the entire freeform draft reply**, not payload fields. Fields keep
  a second channel alive; the draft *is* the reply.
- **`--draft-file <path>`, plain markdown.** Not JSON/XML, not heredoc, not
  inline arg. Any format requiring the agent to pre-structure or tag the draft
  reintroduces the exact restatement tax that caused the routing failure; and
  escaping failures (backticks, quotes, `$`) become retries. The minimizer
  *extracts* structure; the agent does not mark it up.
- **Every turn**, not just handoffs. The 5000-character task review that
  triggered this was a mid-conversation turn.
- **The objective is "delete what the user didn't ask for," not "make it
  short."** A pure minimizer guts a requested discussion — this brainstorm is
  the counterexample. One objective, no turn-type switch.
- **Enforcement is at Stop**, where the hook can see the final message. The
  same hook must catch "never called it," or that is the trivial bypass.
- **Latency is accepted.** Endless is built for many parallel sessions; the
  requester works elsewhere while a turn is being minimized.

### Escape hatches (requester's three, refined)

1. **Appeal** — bounded hard. One appeal, and the appeal text goes through the
   minimizer too. An unbounded appeal is a second bite the agent will always
   take.
2. **Raw draft persisted and retrievable on demand** — the one that matters.
   With the raw preserved, the minimizer can be maximally aggressive at zero
   risk, because nothing is destroyed, only hidden.
3. **A structured pointer** in the output when the minimizer judges more detail
   exists — nearly free once (2) holds.

## The prompt is the product, so it needs an iteration loop

The requester's expectation is that the minimizer prompt will take substantial
tuning. Two parts with different lifecycles:

- **Invariants** — tables verbatim, code blocks intact, the verify command
  always survives, a direct question gets its direct answer. Few, stable,
  shipped.
- **Anti-puffery / anti-jargon guidance** — *also shipped*, and deliberately so.
  The requester wants "Endless filters out that crap" as a stated product
  benefit, not a personal config file. The user template holds additions.

Both are **guidelines to the adversarial agent, not gates**. A regex gate would
mangle a legitimate quotation of a banned phrase.

A phrase denylist alone never converges (ban "load-bearing", get "does the
heavy lifting"). It needs a generative rule — *delete any sentence that
characterizes the reasoning or narrates the analysis rather than delivering
information the user needs* — with the phrase list as concrete anchors beneath
it. First three entries, all from this session's own output: "the thing that
survives from your instinct", "that reframes the decision", "load-bearing".

### Mechanics

- The template is user-customizable config; editing it needs no task and no
  land. **Ceremony is reserved for promoting a proven override back into the
  `//go:embed`ed default**, which is what the long-lived `underway` task is for.
- **Promotion should be triggered objectively** — the override beats the
  embedded default on the corpus — not by feel.

### The corpus

Every turn yields (prompting user message, raw draft, minimized output). The
triple is **already free**: hatch (2) forces persisting the raw draft, the
minimized text is the command's own stdout, and the user message is at hand.
One extra column, not a capture pipeline.

Prefer this over mining transcripts with a periodic job (cf. E-698): the
persisted triple is exact, where transcript-mining must infer which turns had a
report and reconstruct the draft.

What neither provides is the **label**.

### Labels: a four-word signal vocabulary

Recognized only as the first token of a line, standalone or followed by free
text (`$CUT you dropped the verify command`):

- `$CUT` — you dropped something I needed (show me the raw)
- `$BLOAT` — still too long, or said things I didn't ask for
- `$WRONG` — off-target regardless of length
- `$GOOD` — it worked

The sigil is not decoration. `CUT:` at line start is nearly safe, but `WRONG:`
and `GOOD:` are exactly what a user naturally types as a prose label. One
character buys immunity. `!cut` and `/cut` are unusable — Claude Code already
claims both prefixes.

`$GOOD` is not politeness. A corpus made only of complaints trains the
minimizer toward verbosity, because every recorded failure is a cut the user
resented.

Detection is a **UserPromptSubmit hook**, not the agent noticing — same
argument as everything else here. `$BLOAT` with a quoted phrase can append
straight to the denylist, turning annoyance into config without a round trip.

## Rejected: self-launched subagents and workflows

The requester asked whether the agent's own Agent/Workflow capability could do
the minimizing instead of a command. Recorded as a decision.

The requester's assumption was partly correct — a `fork` agent variant inherits
the parent's context, and `SendMessage` continues an agent with context intact —
but there is no embedding channel; tool I/O is text either way.

Context fidelity was never the problem. The agent chooses whether to call a
subagent, what draft to hand it, and whether to keep its output; the return
value lands in context as editable text. No enforcement point exists. A hook
needs a stable anchor ("the last `endless task report` stdout"); a subagent
result is indistinguishable from any other Agent call unless a marker
convention is invented — at which point the command has been rebuilt, worse and
unversioned. Workflows are a harder no: heavyweight, background, opt-in,
notification-returning.

Not impossible. Unenforceable.

The salvaged half: the command should *call* a model internally. `task report`
already runs a ceremony check over free text — that slot becomes the minimizer.
The bouncer is replaced by an editor.

## Deliberately out of scope

- **Task inflation** (>1 task filed per task completed). Raised here with force,
  but the requester is pursuing it in other sessions. It is not a `task report`
  problem and would have swallowed this one.
- **The four seed defects as standalone fixes.** They are subsumed. Repairing
  them independently would ship four correct patches that leave the actual
  failure untouched.

## Open, not settled

- Whether `task report` should be disabled outright while the minimizer is
  built. The requester weighed it; by his own account the current command
  delivers nothing 9/10 times, so disabling costs nothing — but it was not
  decided.
- The exact wording of the minimizer's objective and the invariant list. Expected
  to be substantial work, and the reason the iteration loop above exists.
- Whether the block/minimized output ever carries anything the user did not
  request (the filed-follow-ups mistake suggests: no, by default).
