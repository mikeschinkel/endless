# Outcome — the minimizer corpus needs no human read surface; it needs an optimizer

## The question as filed, and how it moved

Filed as "does a human viewer over the eval corpus earn its keep?" The answer is
**no**, but not because the corpus is worthless — because the reviewer is the
wrong species. The corpus exists to drive an automated optimization loop over
the minimizer prompt, in which the human appears only as a source of ground
truth, never as a step the loop waits on.

That reframing came from the requester and it invalidates most of E-1953's
planning-session decisions, which were all contingent on a viewer being built:
the side-by-side renderer, the `task report log` subcommand restructure, and the
seven-call-site rename that restructure implied. **Those lapse.** Nothing in
them survives except a much smaller thing (below).

The governing constraint is ED-1550 and the 70+ live tmux sessions behind it:
work that lands on the requester's plate does not scale, and a design that asks
them to review prompt diffs is a design that will not run.

## What was wrong with the premise

Two facts corrected mid-discussion:

1. **Zero labels is not evidence the label channel is dead.** The gate is off in
   this repo, so no one has had the chance to label. The count was read as
   signal; it was an artifact of configuration.

2. **The shipped minimizer does the wrong job.** `report_prompts.py` instructs
   *"you are deleting, not rewriting"* (l. 123-125) and *"YOUR OBJECTIVE IS NOT
   TO MAKE IT SHORT"* (l. 60). Neither was the requester's intent, and neither
   was a decision they made — both were written by an agent in a prior session
   and then cited back to them as if authoritative. The intent was always
   rewriting for succinctness.

The corpus corroborates the defect. Keep-ratio by draft size: 512-1k → 0.67,
1k-2k → 0.62, **2k+ → 0.86**. The longest drafts are cut least, which is
backwards. Deletion-only explains it: on a short draft the junk is isolated in
removable sentences; on a long one it is diffuse, spread through every sentence,
and unreachable without rewriting.

## The minimizer's actual objective

Replaces the shipped instruction. Ships as a change, not as an experiment — it
is a build defect, not a hypothesis:

> Remove things the user can ALREADY see in `session status`; things ALREADY
> written in the task plan or analysis or anywhere else they will have to review
> anyway; replace jargon with clear English; remove or greatly minimize puffery;
> remove anything that is the agent "showing its work."

The novel half is **deduplication against what the user already has access to**,
which the shipped prompt never considered. It is also the half the loop cannot
score from the triple alone — see "fetch policy" below.

## Design of the loop

### Ground truth: two channels, both in the flow of work

- **Labels**, written into the requester's ordinary replies. Cost is a token in
  a message they were writing anyway.
- **Paired A/B**: on a sampled fraction of turns, produce two minimizations and
  let the requester pick. This is the strongest idea in the discussion — it
  yields a real counterfactual, live, which no single-variant turn can. It is
  also the exact judgment the promotion decision requires ("B beats A"), which
  an absolute label does not supply.

A/B sample rate is tuned **in-band**: each A/B presentation asks "want to see
these more often or less often?" No config knob; the only seat that can judge
the annoyance-vs-value trade sets it.

Doubling the minimizer call on sampled turns is accepted. Cost for real value is
acceptable; cost for no value is not.

### Labels are free-form and span-scoped

**No fixed vocabulary.** Per the Bitter Lesson, a hand-picked set of six labels
is exactly the hand-crafted feature to avoid. Fix the *mechanism*, leave the
*vocabulary* open:

    $TOKEN "quoted span"

The requester writes whatever is natural; the taxonomy is discovered from what
they actually type. A label invented once and never reused costs nothing.
Candidates raised and now subsumed rather than mandated: `$RESTORE`/`$KEEP`
(over-cut), `$CUT` (under-cut), `$BLOAT`, `$PUFFERY`, `$JARGON`, `$WRONG`,
`$GOOD`.

**Span-scoped is the upgrade.** Turn-level labels ("this turn was bloated")
train almost nothing; span-level ("this exact sentence was bloat") trains a lot.
Every label may carry the offending text.

Extraction is a regex over the reply (`^\$([A-Z]+)`); *grouping synonyms* across
a drifting vocabulary is the judge's job, not string equality's. Parsing must
not fire on a label token legitimately quoted inside a reply — the same hazard
`report_prompts.py:32-34` already records for the denylist.

The requester need not attribute a label to drafter-vs-minimizer. That is
mechanical from the raw/minimized pair.

**Consistency is leaned on, not enforced.** A consistent vocabulary produces
better results, but a vocabulary the requester cannot recall in the moment
produces *no label at all* — and label supply is upstream of everything else in
the loop. So short-term scoring noise from drift is an accepted trade while the
requester learns to identify things better. The pressure is an in-band nudge:
when a new token clusters near one used before, the loop asks whether to merge,
and the requester may answer or ignore. Drift becomes observable rather than
silent. Same channel as the A/B frequency question.

### The judge, and what calibrates it

An LLM judge scores every turn, labelled or not, reading
`(user_prompt, raw, minimized)`. Dense, paired, unlimited — the only thing that
can evaluate a prompt variant over the corpus.

The human labels do **not** score prompts. They **calibrate the judge**. The
judge commits to a prediction *before* seeing the requester's reaction — on an
A/B turn it predicts which the requester will pick; on any turn it predicts
whether they will flag it. Rolling agreement between prediction and outcome is
the number that says whether the judge still predicts which output the requester
will prefer.

**Low agreement raises the A/B sample rate; it never halts the loop.** A loop
that silently stops improving while the requester keeps labelling is worse than
useless — it lets them believe their input is doing something when it is not.
Losing the requester's preferences is answered by asking them more often.
Whatever the loop does, it says so in-band, in the reply channel they already
read.

### Scoring: vetoes, not a weighted sum

Three tiers, deliberately not summed:

1. **Mechanical invariants** — free, exact, no model call. Did every fenced code
   block survive byte-for-byte? Every table? Every command the user must run?
   These catch the catastrophic failure deterministically. NOTE: the
   deletion-only invariant (minimized ⊆ raw as a subsequence) **dies with
   deletion-only**; rewriting is now the objective, so subsequence checking is
   no longer available and the surviving mechanical checks are the byte-exact
   ones on protected content.
2. **Fidelity** — the judge.
3. **Compression** — free, saturating.

A variant buying compression at the cost of one invariant violation is not
better. A weighted average will happily make that trade; vetoes will not.
Adding a self-scored compression target to the prompt (the requester's
suggestion) is a legitimate variant precisely *because* the invariants are
enforced separately.

### Monitoring vs. deciding

Two different instruments, not to be conflated:

- **Monitoring** — rolling metrics over live traffic. Answers "are we drifting?"
  Confounded by corpus drift. Alarm, not verdict.
- **Deciding** — paired replay of variants over a frozen corpus. Item difficulty
  cancels. This is the only thing that may gate a promotion.

Explicitly rejected as a score component: **label count / label rate**. It
measures the requester's engagement, not the prompt. Turning the gate on will
raise it while quality is unchanged.

### The search space: three axes, per task type

Variants are **generated by the optimizer, not hand-written by an agent**,
seeded from known compression grammars and free to diverge: ASD-STE100, Attempto
Controlled English, Plain English Foundation Standards, CNL-P, RICECO/ICC, PDL,
plus orthogonal style axes (all-bullets vs. prose).

Jointly optimized:

1. **Prompt text**
2. **Fetch policy** (below)
3. **Bypass threshold** — the length under which a reply skips the minimizer
   entirely. Latency and cost are a big factor. 256 chars was a guess; the
   shortest draft in the corpus is 396 and *zero* of 23 passed through
   untouched, so there is currently no evidence at all about behavior below the
   threshold.

Prompts are **split by task type now**, not later — variants keyed
`(task_type, hash)`. Coordinating a follow-up task later costs the requester
more than splitting up front, and sample volume is not a constraint worth
designing around.

### Fetch policy — why the corpus row must grow

The dedup objective ("already visible in `session status` / the task plan")
cannot be scored from the triple. Two options were on the table and they turn
out to be one mechanism:

- Grow the corpus row to capture surrounding context, **and**
- Let the minimizer *fetch* what it wants (`task show E-nnnn --text`, etc.)

A tool-using minimizer is nondeterministic in its **inputs**, which breaks
replay: A/B over a frozen corpus is meaningless if each run re-fetches live
state that has since changed. So the corpus row records **what was requested and
what came back**, and replay serves it from the record rather than re-fetching.
#2 forces #1; they are the same mechanism.

The set of things it *may* fetch is therefore large and declared, and **what it
actually fetches is a JSON policy document the optimizer maintains** — a third
tunable dimension. "Give it everything on every turn" fails on cost and latency,
not on principle, and that is exactly what makes the policy worth optimizing
rather than fixing.

This is not backfillable. Corpus rows written before it exists can never gain
the context.

## What survives of a human read surface

One command: **dump the raw draft for a turn, verbatim, no diff, no columns.**
The requester will have the minimized text in an adjacent tmux pane, so the
comparison is done by the eye, not by a renderer.

This replaces E-1953's side-by-side renderer entirely, along with the wrapping
problem it inherited (tables and fenced blocks are exactly what column layout
breaks, and exactly what the invariants protect).

## Storage and versioning

- **Corpus stays in the ledger DB for now.** The concern was duplicated copies
  of the same text, not the table's existence. Versioned history of discussions
  is wanted. Revisit later if secrets leaking into a version-controlled ledger
  becomes the operative worry — that, not bloat, is the reason it would move.
- **No embedded git repo for prompt versioning.** Content-address the variants —
  `(hash, text, parent_hash, created_at, note)` — because every eval run must
  reference its variant inside the store regardless, and adding git creates two
  identities for one object plus a sync problem. `parent_hash` supplies the only
  thing git was providing (lineage); diff is computed at read time. Rollback of
  a bad auto-promotion is a pointer move, which is what makes removing the
  approval step safe.

## Config

- `report_gate` → **`minimizer`**, as an object: `{"enabled": true,
  "optimizer": true}`. The old name is cryptic inside-baseball; the object
  admits the second switch the loop needs.
- **`enabled: true` in this repo**, as part of the work. The original reason for
  the exemption — a session tuning the prompt should not be governed by the
  prompt it is editing — weakens once tuning is automated rather than hand-done.

## Scheduling

Rides the **existing fire-once job runner**. A dedicated scheduler is a later
question, if ever.
