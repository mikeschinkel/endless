# How worktree branches survive a rewrite of main's history

Decided: **ED-1553** — identify a fork point by ledger *content*, not by SHA.
Implemented by: **E-1955**.

## The finding that reframed the task

The prior analysis reported two harness verdicts (no-pull → clean;
pull+amend → conflict) out of four scenarios run. Re-running the harness with
the missing scenarios changed the shape of the problem:

    S1 no pull, ledger events (guard)     guard=APPEND (saw task/900)   land=OK
    S2 pull --rebase, ledger (guard)      guard=AMEND                   land=CONFLICT
    S3 pull --rebase, NO further ledger   guard=-                       land=OK
    S4 pull --rebase, ledger FORCED append guard=APPEND                 land=OK
    S5 pull --merge, ledger (guard)       guard=APPEND                  land=OK
    S6 no pull, NO further ledger         guard=-                       land=OK

    S7 pull --rebase, append once, +5 more guard-driven events   land=OK
    S8 pull --rebase, guard only,  +5 more guard-driven events   land=CONFLICT
    S9 pull --rebase, append once, +20 more guard-driven events  land=OK

S3 and S4 are the ones that had not been reported, and they are decisive.

**The rewrite alone is harmless (S3).** `pull --rebase` orphans every fork
point, and the land still succeeds: rebase drops commits patch-equivalent to
upstream, and a rewritten-but-unamended ledger commit is patch-identical to
its old copy.

**The rewrite plus continued ledger activity is still harmless (S4)**, so long
as the first post-rewrite event appends rather than amends. So the amend is
not a co-factor. It is the entire converter from "survivable" to "broken."

**One append per rewrite is enough, permanently (S7, S9).** After a single
append, main's tip is a commit no branch holds; 5 and 20 subsequent amends all
proceed and the land stays clean. The suppression needed is one append per
history rewrite — not one per event, and not one per live branch.

S5 confirms `pull.rebase=false` masks the defect entirely, which is why it
surfaced only after that setting was changed on 2026-08-10.

## Why the guard fails, precisely

`canAmend` (`internal/events/commit.go`) is not bypassed and does not error.
Its precondition 2 asks "is HEAD reachable from any ref besides the current
branch" via `git for-each-ref --contains HEAD`. That is a SHA-level question.
`git pull --rebase` reassigns every local SHA, so a task branch forked from
main's ledger tip stops "containing" main's HEAD. The guard answers a question
the rewrite made meaningless, returns "safe to amend," and the next amend
diverges main from every task branch's base.

This generalises past `pull.rebase`: interactive rebase, a hand
`commit --amend` on main, and a force-pull after someone rewrote origin all do
the same thing. The task's title was already the right framing.

## The decision

Add a second, content-level reason to refuse the amend: before amending a
ledger tip, compare the `.endless/db-ledger` tree hash at HEAD against every
`refs/heads/task/*` tip. If any branch holds a byte-identical ledger tree,
that branch's base is content-identical to the commit about to be amended —
append instead.

A tree hash is content-addressed, so no history rewrite can change it. That is
the durable fork-point identity the SHA test lacks, and it is the first of the
three options the task description named.

Three properties made this the choice rather than a compromise:

- **It is cheaper than what it supplements.** 16ms across 145 task branches
  and 130 worktrees, via a single `git cat-file --batch-check` process.
- **It self-releases.** Once one append has occurred the test stops matching
  and amending resumes (S7/S9). Amend's flood-suppression value is preserved
  in full; the measured cost is one extra commit on main per rewrite.
- **It is additive, not a replacement.** Precondition 2 is retained. The
  content test scans only task branches, so it is structurally blind to a
  ledger commit already pushed to `origin/main` or carrying a tag — cases the
  reachability test gets right. The two are OR'd.

## Rejected

**A `git patch-id` scan.** Answers the same question and is equally
rewrite-immune, but costs **71s per ledger event** (measured; 34s even when
restricted to ledger-touching commits). Its cost scales with the size of the
rewrite it is looking for, because a rewrite pushes every branch's merge-base
back behind it — so it is slowest exactly when it matters. Disqualifying for a
check that runs on every event.

**"Any task branch exists → append."** Considered and priced wrong at first.
It would suppress amend on essentially every event, reinstating the commit
flood amend exists to prevent.

**A sidecar record of main's tip SHA.** Detects the rewrite directly and is
O(1), but requires stored state and forces an append that the content test
shows is unnecessary in most cases. Strictly worse than a content test that
costs 16ms and needs no state.

**Land-side detection as the primary gate.** A detector keyed on "was this
branch's base rewritten" would refuse S3, S4, S7 and S9 — four false alarms
against one true positive. An honest land-side gate has to be keyed on
divergence rather than on the rewrite, which needs a rebase rehearsal to
answer. Prevention at write time is both cheaper and more accurate.

**A union merge driver on the ledger segments.** Struck in the prior analysis
and still struck: `Event` carries no unique id and neither `ReadAllEvents` nor
the projector dedups, so union's duplicate lines would double-apply on replay.

## Repair: not needed

The aggregate figure — 195 ledger commits carried by task branches that main
lacks — is noise, not damage. Scanning all 109 unmerged task branches with
`git cherry`:

- The large live branches carrying 100–150 inherited ledger commits
  (`task/1889`, `task/1929`, `task/1934`, …) are **clean**. Rebase drops every
  inherited commit as patch-equivalent and replays only their 2 real work
  commits, neither touching the ledger.
- 29 branches have a non-patch-equivalent ledger commit. Every one has
  **exactly one** replaying commit, it is a single `Endless: record ledger
  entry`, and it touches nothing but `.endless/db-ledger/*.jsonl`. Zero real
  work is at stake — these are spent plumbing whose work already landed.

So no live branch with pending work is at risk, and a repair path would exist
only to rescue branches that are disposable. The widened orphan-drop that was
under consideration (extending `_drop_orphan_amendable_commits` past its
contiguous-at-base limit) is therefore not filed: with prevention in place, no
branch carrying real work can acquire the condition.

Worth keeping: across all 29, there are **zero** commits touching both the
ledger and real source. The mixed-commit hazard that E-1342's docstring backs
away from does not occur in practice.

## Deliberately not filed

`worktree land --dry-run` does not simulate the rebase, so it cannot predict
the failure it exists to preview. Named in E-1943's analysis as evidence
pending the framing choice. The framing is now settled, and the gap turns out
to be independent of it — a dry-run that does not simulate the rebase cannot
predict *any* conflict, ledger or ordinary. It is a separate defect with a
separate root cause and should be filed on its own merits, not as cleanup
of E-1943.

## Correction to the prior analysis

Its closing note warned that commit counts mislead. That holds, and this
session found the sharper form: `git cherry` distinguishes "ahead by 326
commits" from "ahead by 2 commits and 324 patch-equivalent copies," and the
difference between those two readings is the difference between a branch that
lands clean and one that does not.
