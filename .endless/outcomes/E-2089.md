# Tasks that reached a terminal status with code that never landed

Measured 2026-08-30 against main at `228f56ef`. Nothing was changed — no
status edited, no branch touched, no relation recorded.

---

## The short answer

**Two tasks** in a shipped-terminal status (`confirmed`/`assumed`/`completed`)
still hold source commits on their own branch that are not on main: **E-1115**
and **E-1643**. One of them cost real work — the bug E-1115 fixed was
rediscovered 14 days later and fixed a second time as E-1395.

**Eleven more** are terminal while the code they describe has been *deleted
from main* by a later task, with no relation recorded to say so.

Everything else that a mechanical check flags is one of three false-positive
classes, each explained below. The premise of the task holds; the population is
small and the causes are distinct.

---

## Population

572 tasks are in `confirmed`, `assumed` or `completed`. 48 are
research/brainstorm/epic, whose deliverable is an outcome text, not code. The
code-bearing population is **524** (`todo`, `bugfix`, and two untyped).

Of those 524, **111 have no row in `task_landings`** — but that number is almost
entirely an artifact of when landings started being recorded (first row
2026-04-22):

| Task created | Shipped-terminal | No landing row | No landing *and* no attributed commit |
|---|---|---|---|
| 2026-04 | 162 | 102 | 85 |
| 2026-05 | 145 | 8 | 5 |
| 2026-06 | 82 | 1 | 1 |
| 2026-07 | 61 | 0 | 0 |
| 2026-08 | 74 | 0 | 0 |

**`worktree land` records reliably.** Since July, every code-bearing task that
reached a terminal status has a landing row. The gap is historical, and the nine
post-April exceptions are enumerated below, each with a cause.

## Group 1 — Code still sitting on the branch (2 tasks)

Of 154 `task/*` branches, 55 hold at least one commit main lacks by patch-id.
Those 55 contribute 109 commit-rows, but only **13 rows — 7 distinct commits —
touch a file outside `.endless/`**. Everything else is ledger and plan-mirror
noise.

Of those 7 commits, three belong to tasks E-2084 already dispositioned
(E-1523, E-1653, E-2010 — all `unverified`, so not terminal), two are the
false-positive pair in Group 4, and two are these:

### E-1115 — `assumed`, code on the branch, bug fixed again 14 days later

*Fix `endless session use` sibling-pane lookup in same tmux window*

`802141000699904f` on `task/1115-session-use-pane-lookup` teaches
`_tmux_window_pane_ids()` to pass `-t "$TMUX_PANE"` to `tmux list-panes`. The
commit was written 2026-05-02, the task was set to `assumed`, and the branch was
never landed.

On 2026-05-16 the same bug was observed again — a claim from window `@84` bound
to a session in window `@83` — filed fresh as **E-1395**, fixed again in
`e2124228` ("Fix E-1395: scope `_tmux_window_pane_ids` to TMUX_PANE's window"),
which *is* on main. The two fixes are the same change.

Neither task references the other. There is no `duplicates` relation between
them. E-1395 is still `unverified`; E-1115 still reads `assumed`. This is the
reported defect in its most expensive form: the terminal status said the work
was done, so nobody looked at the branch, and the bug was paid for twice.

### E-1643 — `completed`, verify script never landed

*Explore guarding against alt-worktree proliferation*

`5fc4562629f07b` carries `tests/tasks/e-1643-verify.sh` (137 lines). That file is
absent from main; 201 other verify scripts are present. The task is `research`,
so its primary deliverable — the outcome text — did land (it is in `tasks.outcome`
and mirrored under `.endless/outcomes/`). Only the ancillary script is stranded.
Milder than E-1115, same shape.

## Group 2 — Landed, then deleted from main, and never corrected (11 tasks)

448 shipped-terminal tasks have at least one attributed source commit on main.
For **19** of them, *not one file they touched still exists on main*. Eight of
those 19 are path renames (Group 4). The remaining **11 were genuinely excised**:

| Removed by | Tasks still reading `confirmed`/`assumed` |
|---|---|
| **E-1939** — excise the web dashboard and its build stack | E-448, E-686, E-687, E-712, E-755, E-795, E-879, E-880, E-881 |
| **E-1426** — retire `.endless/sessions/*.json` companion files | E-1033 |
| **E-1248** — restructure the guide into multi-section form | E-713 |

The list understates the class. It only catches tasks whose *entire* footprint
vanished; a task that touched one surviving file alongside four deleted ones does
not appear. Other excisions with the same exposure and no recorded supersession:
**E-2029** (the channel command), **E-2074** (background-agent support),
**E-2081** (the session-navigation trail), **E-1711** (drift detection),
**E-1906** (session-recap machinery), **E-1582** (pivot-gate infrastructure).

**The mechanism to record this exists and is used exactly once.** `task_deps` has
73 `replaces` rows. Eleven of them belong to **E-1449** (delete the plan-snapshot
feature), which named every task whose work it removed — E-984, E-1091, E-1093,
E-1095, E-1096, E-1097, E-1205, E-1275, E-1354, E-1362, E-1374 — and moved each
to `obsolete`.

E-1939, E-2029, E-2074, E-2081, E-1426 and E-1711 recorded **zero** relations of
any kind against the work they deleted. E-1697 is the same story from E-2084 §3:
superseded by E-1700, still `assumed`, no relation.

(E-1449's own remedy is now partly disallowed — E-1956 refuses `obsolete` on work
that shipped, on the grounds that it reads as "never happened". So the relation is
right and the status move it used is not; see the proposals.)

## Group 4 — What a mechanical check flags that is not a defect

Anyone building a "not on main" report will hit these first. All three are
measurement artifacts.

**Patch-id drift after rebase.** `worktree land` rebases before fast-forwarding,
so a landed commit reaches main under a new SHA and its branch copy reads as
unlanded forever. Four branches — **E-1803, E-1864, E-1865, E-1929** — carry the
same two commits (E-1832's README rewrite). Both landed: `98bb7b24` → `785fe07b`,
`4e611073` → `a8bfccff`, identical subjects, different SHAs. E-1832 is
`confirmed` and its work is on main. This is E-2087's finding; E-2084 reset five
branches for it and left these four.

**Path renames read as deletion.** Eight of the 19 "footprint gone" tasks moved
rather than vanished: `cmd/endless-*` → `internal/*cmd` (E-1367 collapsed seven
binaries into `endless-go`), and `sql/schema.sql` → `internal/schema/schema.sql`.
Affected: E-892, E-1130, E-1154, E-1172, E-1187, E-1253, E-1255, E-1258. All
verified present on main under the new paths.

**The pre-convention era.** 85 of the 91 no-evidence tasks were created between
2026-04-14 and 2026-04-24, before worktrees, before landing records, and before
the commit-naming convention. Attribution rate of source-touching commits on main:

| 2026-04 | 2026-05 | 2026-06 | 2026-07 | 2026-08 |
|---|---|---|---|---|
| 67% | 96% | 96% | 95% | 94% |

Spot-checked eight of them against main — E-499 (`--description` on `task add`),
E-717 (`task next`), E-723 (verb-first title validation), E-842 (verb validation
on `--title`), E-845 (`hook.log`/`channel.log`), E-925 (`--parent` filter),
E-959 (explicit `--status` overriding the terminal exclusion), E-1150 — and every
one is on main. The work landed; only the attribution is missing. **This cohort
is not worth chasing**, and any report should scope itself to tasks created on or
after 2026-04-22, the first landing record.

## Why status cannot answer "is this on main?"

Three facts, each verifiable:

**1. The status write never consults landing state.** E-2018's guard
(`internal/events/status_transition.go`) validates two things: that the edge is
legal for the task's type, and — for `underway` and `unverified` — that the
acting session has standing. `ValidateStatusActor` refuses `unverified` when no
session ever claimed the task, on the stated grounds that it "would report
implementation nobody did". There is no equivalent check on `confirmed`,
`assumed` or `completed`, and nothing in `internal/` or `src/` reads
`task_landings` before a status write.

**2. It should not.** The handoff makes the *spawning* session own landing, so a
task legitimately reaches `unverified` → `confirmed` before its branch lands.
Landedness is not a precondition of the status and cannot be gated as one. This
is why the fix has to be a report, not a guard.

**3. `task show` signals landedness only by omission.** E-2084 renders
`Landed: 2026-08-30 10:16 pm 421726c`. E-1115 renders nothing — the line is
simply absent, exactly as it is absent for all 102 April tasks whose code is on
main. The reader cannot tell "landed before we recorded landings" from "the
branch is still sitting there". That ambiguity is the whole defect at the
surface a person actually reads.

Meanwhile the data exists and is already surfaced separately: `task landed`
(E-1478) answers "what reached main", `task unsettled` (E-1865) answers "what
hasn't and why". **Nothing joins either one to status.**

## Proposals — for discussion, not implemented

**P1. Make `task show` state landedness rather than imply it.** For a task in a
shipped-terminal status, always print a landing line. Three cases, three
sentences: `Landed: <ts> <sha>`; `Landed: never — created before landings were
recorded (pre 2026-04-22)`; `Landed: never — branch task/1115-… holds 1 commit
not on main`. Absence-as-signal is what let E-1115 sit for four months. Cheap:
`task_landings` plus the existing unsettled probe.

**P2. Add the join nothing does today — a `task unlanded` report.** Tasks in a
terminal status, created on or after the first landing record, with no landing
row *or* with a branch holding source commits main lacks. It must compare by
patch-id (E-2087) and ignore `.endless/`-only commits, or it drowns in Group 4.
Run monthly this would have caught E-1115 in May, before E-1395 was filed. This
subsumes duplicate detection — no separate mechanism needed.

**P3. Make an excision record what it excises.** When a task deletes files that
another task's landed commits created, that is computable at land time from git
plus `task_files`. Prompt for (or auto-record) `replaces` edges, as E-1449 did by
hand and E-1939, E-2029, E-2074, E-2081, E-1426, E-1711 did not. Then `task show`
on E-687 can say "replaced by E-1939" and answer "is this on main?" honestly
without rewriting the fact that the work happened.

**P4. Decide what status a shipped-then-deleted task should carry.** E-1449 used
`obsolete`; E-1956 later refused that on shipped work because it reads as "never
happened", and named `replaces` as the fact to record instead — but left the
status question open. Today those tasks keep `confirmed`/`assumed`, which is
true about the past and misleading about main. **This is the one open design
question in this survey.** Options as I see them: leave the status and let the
relation carry it (P3 alone, minimal); or add a distinct terminal status meaning
"shipped, since removed". I lean to the first — the status describes a decision
about the work, and the relation describes where the code went — but it is your
call.

**P5. Say it in the guide.** A task status answers "what did we decide about this
work", never "where is the code". Two sentences in `endless guide tasks`, next to
P1's rendering, so the next reader does not have to derive it from a survey.

## Method, and what it cannot see

Four independent probes, cross-referenced: `task_landings` rows; commits on main
whose message names a task and touches a file outside `.endless/`; `git cherry
main <branch>` per branch, with each unlanded commit's file list; and the survival
on main of every file a task's attributed commits touched.

Known limits:

- **Commit-message attribution over-credits.** A commit that mentions another
  task in its body is credited to it. E-1048 is credited to `ee784570`, which is
  E-1047's commit citing E-1038 and E-1048 in passing.
- **The footprint check is one-sided.** It flags a task only when *every* file it
  touched is gone, so a partially-excised task is invisible. Group 2 is a floor,
  not a total.
- **Branches deleted after landing leave nothing to measure.** Only 76 of the 524
  shipped-terminal tasks still have a branch; for the rest, branch evidence
  cannot be gathered either way.
- **`git cherry` compares patch-ids**, so conflict resolution during a rebase
  makes a landed commit read as unlanded. Every Group 1 finding was hand-verified
  against main's current source for this reason.

The one number here with a shelf life is main itself. Re-measure before acting.
