# What must land and what must move before the Go port starts

Measured 2026-08-28, revised 2026-08-30 after review. Nothing has been landed,
reset or discarded. Task-graph edges recorded so far are listed under
**Recorded** at the end; everything else is a proposal.

---

## 1. The worktree backlog is a measurement artifact

`endless task unsettled --all` reports 86 unsettled worktrees. The figure is
real but it does not mean 86 pieces of work are pending.

`git cherry main <branch>` matches commits by patch-id rather than SHA.
`worktree land` rebases before fast-forwarding, so a landed commit reaches main
under a new SHA while the branch keeps the original — which then reads as
unlanded forever. The large counts are that, and nothing else:

| Branch | Reported unlanded | Actually not on main |
|---|---|---|
| E-1934 | 314 | 2 |
| E-1844 | 223 | 4 |
| E-1785 | 198 | 2 |
| E-1853 | 182 | 6 |
| E-1537 | 122 | 2 |

**Of 86 unsettled rows, 14 carry any commit not already on main. Of those 14,
four hold nothing but a stale README rewrite. Ten hold work of their own, and
five of those touch `src/endless/*.py`.**

### Action

`unsettled` is answering "does this branch differ from main?" when the useful
question is "does this branch hold work main does not have?". A patch-id check
would collapse the 86 to 14 at the source. Filed as **E-2087**.

Until that lands, the survey command overstates the backlog by roughly 6×, and
any plan built from its raw output will be sized wrong.

## 2. The `internal/monitor/db.go` patch in 37 worktrees

37 worktrees carry a byte-identical uncommitted edit to
`internal/monitor/db.go`, self-labelled "E-1972 compat sweep (2026-08-26)". It
teaches `ProjectIDForPath` to try both the absolute and the home-relative
spelling of a project path.

**The patch was correct and necessary when applied.** E-2011 (landed
2026-08-20, `adefd87`) changed `projects.path` to home-relative storage — all
52 project rows are now `~`-prefixed. A binary built from pre-E-2011 source
compares only the absolute spelling, matches nothing, walks off the end, and
falls through to `ensureAutoRegisteredProject` — silently registering the
worktree as its own project. Reverting the source and rebuilding would
reintroduce exactly that.

Three facts change what to do about it:

1. **Main already has the real fix, and a better one.** `ProjectIDForPath` now
   queries `homeRelative(check, home)` directly — it converts the walk path to
   the `~` spelling rather than trying two spellings per rung. The hand patch
   is a strict subset of it.
2. **The patched binaries already contain the fix.** In every worktree checked,
   `internal/monitor/db.go` and `bin/endless-go` carry identical mtimes — the
   sweep patched and rebuilt in one pass. Reverting the source does not break a
   running hook; it only matters at the next rebuild.
3. **Committing it is the one option that does not work.** The patch would then
   have to land, and it conflicts with main's implementation of the same fix.
   There is nothing to contribute — main got there first.

### Action

Rebase (or `git reset --hard main`) is both the fix and the cleanup: it brings
main's `homeRelative()` and makes the patch redundant in the same step. So the
disposal is not a separate chore — it falls out of the rebase each branch needs
before it can land anyway.

- **25 worktrees** are unsettled *only* because of this patch and hold no
  unlanded commits at all. `git reset --hard main` in place settles them
  outright. Nothing to review, nothing to land.
- **7 more** carry the patch plus metadata-only commits. Same treatment.
- **5** carry the patch and real work; they get a `git rebase main` as part of
  the landing sequence in §4.

Do not reset a worktree with a live session in it. E-1934 is `underway`, and
E-1643 and E-1653 have sessions on record.

## 4. Proposed landing sequence

Every branch is 11–2200 commits behind main and needs `git rebase main` in
place first. That rebase also dissolves the E-1891 concern (a worktree whose
stale binary predates the status registry cannot run the CLI): afterwards each
branch runs main's code against main's schema. E-1360 and E-1643 have no
`bin/endless-go` and need `just build`.

### Land — Go-only, cheap, no Python risk

| # | Task | State | What it is |
|---|---|---|---|
| 1 | **E-1523** | unverified | `8402f8fa`. `GetActiveTasks` scans four columns and `continue`s on error, so a NULL description silently drops the row. Still exactly that on main. Two files. |
| 2 | **E-1697** | assumed | `a9b4c05d`. DB-context resolution from a worktree cwd. Same area as the §2 patch — landing it is what stops the hand-patching recurring. |
| 3 | **E-1643** | completed | `b29e63e6`. One verify script. |

### Land — touches Python the port will delete

| # | Task | State | What it is |
|---|---|---|---|
| 4 | **E-1653** | unverified | `cd27fe0a`. Migrates tasks stranded on E-1252's retired status slugs. Carries a schema change plus `cli.py` and `task_cmd.py`. A data migration — must land regardless of language. |
| 5 | **E-1680** | confirmed | `bc96b58e`. The `esu e-NNNN` resolution from §3. |
| 6 | **E-2081** | unverified | `a9c7758b`. Drops the session-navigation trail: schema drop, `internal/navvia`, `internal/tmuxcmd`, plus `cli.py` and `session_cmd.py`. `navvia` is still on main, so this is entirely undone. |
| 7 | **E-2010** | unverified | `0001aefe`. 51 files, 19 Python, adding `removed` columns for sessions/decisions/projects — neither table has one on main. The largest Python-touching branch by a wide margin. |

**Order: E-1523 → E-1697 → E-1643 → E-1653 → E-1680 → E-2081 → E-2010.**
Go-only and trivial first, so rebase mechanics are proven on cheap branches;
Python-touching in ascending size, so each later branch rebases over settled
ground. E-2010 last — it touches the most Python, and anything landing after it
would have to resolve against its 19-file rewrite.

E-1646 is dropped from the sequence per above.

### Do not land — landing these would regress main

- **`98bb7b24` / `4e611073`** on E-1537, E-1785, E-1844, E-1934. A README
  rewrite superseded by E-1832 (`confirmed`); main's README is a later rewrite
  with a different tagline, and `tests/tasks/e-1832-verify.sh` is on main.
  **On all four branches these two commits are the only unlanded content** —
  there is nothing to salvage and nothing to edit. `git reset --hard main` in
  place is the whole disposal.
- **E-1853** `422b2b1a` / `d72305cf` — fixes the verb gate's handling of
  classifier failure. E-1658 removed the verb gate; `src/endless/session_gates.py`
  is gone from main. The bug no longer exists.
- **E-1360** `af35f4b6` — docstrings in a file main no longer has.
- **E-1310** — task is `obsolete`; content already equals main.

### No action — 40 branches whose only unlanded commits are `.endless/` metadata

Ledger entries and plan mirrors. Landing them replays bookkeeping and nothing
else. With the 25 from §2, this is the bulk of the 86 and none of the risk.

### Checked and clear: the ledger and the projection agree

The absence of a `task.deleted` event for E-1361 initially read as a
ledger-to-projection gap. It is not, and the wider check is worth recording so
nobody re-opens it:

"Missing tasks" — it does **not** list E-1361. Replaying all 8,849 committed
ledger events gives 1,262 distinct task ids with a `task.created`. Of those,

accounted for:

- **82** are task-era decisions since migrated to the `decisions` table —
  E-1361 among them, from the era its own sibling E-907 records ("decisions are
  temporarily stored as task type until…").
- **96** are E-1 … E-96, test fixtures ("Implement m-ready-1", "Coordinate
  blocked-revisit epic") written by other nodes — the known pre-rollout
  baseline that E-1717 already proposes to filter out of validate-db's output.

No unexplained residue. E-1710 checked the opposite direction and found no loss
there either.

## 10. The one open question this survey does not answer

E-1063's description carries it already: once there is one user-facing binary,
does internal plumbing stay visible in `--help`?

Today the split is invisible to users because the binaries are separate.
`endless` is what a person types — `task`, `worktree`, `session`, `decision`,
`phrase`, `guide`. `endless-go` is what Endless types to itself, and its
subcommand list is `event`, `hook`, `sandbox`, `tmux`, `session-query`,
`spawn-window`, `spawn-launch`, `template`, `markdown`, `task-status`, `jobs`,
`errors`. One is literally labelled `(internal)`.

After the port those merge into one binary named `endless`, and `endless --help`
becomes the union — roughly nine machinery subcommands sitting beside six a
human would ever run. That is the first screen a new user sees, and it makes
Endless look considerably more complicated than it is.

The options are to hide them behind a flag, group them under a visible
"plumbing" heading, or leave them flat. It is a product decision about what
someone else's first five minutes with Endless look like, not a finding this
survey can produce.
