No id that anything outside its own row refers to is ever reused. 'Refers to' means stored in another table — whether or not a foreign key enforces it — or handled by a human or agent: typed, or written into a plan, commit subject, branch name, or path. That covers tasks, sessions and decisions. Ids that are purely internal row handles, a surrogate primary key nothing else stores and nobody types, may be reused freely, so deleting a junction-table row is unrestricted. The FK test alone is insufficient: session_tasks.task_id has no foreign key and still refers to a task, which is the bug surface E-1926 was filed about. Enforcement: removing a covered entity sets removed=1 rather than issuing a DELETE, making re-mint impossible by construction; the cost is that every read path must filter on removed, since reads that today drop dangling references via inner join start matching the retained row. Full rationale in E-1926's outcome.
