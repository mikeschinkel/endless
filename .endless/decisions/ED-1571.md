Scope: self_dev only. There a candidate binary and an installed binary coexist against one real ledger, so during the pre-land window nobody may migrate it -- the candidate must not (ED-1567), and the installed binary does not carry the unlanded migration. Land-time migration therefore runs from a separate executable built from the landing branch, carrying the migration set and nothing else. Every other project has one installed binary and no land at all, so it carries and applies its own migrations under ED-1570; no separate executable exists there. The migration executable performs migration steps in FULL -- DDL plus the DML those migrations define: enum seed rows, backfills, the INSERT ... SELECT of a table rebuild. schema.sql already seeds session_kinds, process_kinds and task_types, so a DDL-only rule would leave a migrated database unusable. What it excludes is application runtime: it never serves a hook, never runs a task command, never touches business data outside a migration.
