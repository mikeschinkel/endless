Whenever something comes in kinds (task types, statuses, lanes, harnesses, project kinds, any future category), each kind declares the attributes behavior depends on, and code branches on those attributes, never on the kind's name: ask whether a task type has a landed deliverable, not whether it is todo or bugfix. A check naming kinds hides its reason and goes quietly wrong when a kind is added or changes; a check on an attribute states its reason, and a new kind behaves correctly by declaring its attributes. Mike saw the failure in code from a military client he had taught Clipper: it chose behavior by which base a record was for, not by the attributes that base had.
