Refines ED-1472. schema.sql is exec'd on EVERY monitor.DB() connect — including the one 'endless db apply-change' opens BEFORE dispatching to the change script — so a new schema.sql always meets the OLD, pre-migration DB first and must survive it, or the change deadlocks its own rollout. SQLite splits schema objects by when they resolve column names: CREATE VIEW resolves at PREPARE time (safe), while CREATE INDEX, CHECK constraints and generated columns resolve at CREATE time and fail immediately. Only the lazy kind may name a column that populated DBs receive via a change file. Nor can such an object be moved into the change file alone — that leaves fresh and migrated DBs with different shapes, the drift ED-1472 exists to prevent; it has to be dropped, or the column has to reach populated DBs another way. Found by E-1929, where an index on tasks(removed) aborted the land with 'no such column: removed'. Pinned by TestSchema_AppliesToDBPredatingItsNewestColumn.
