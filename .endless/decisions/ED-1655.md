No code deletes a session row, and `session` is not a delete target for `endless correct`. Sessions are infrastructure, not records anyone manages: nobody files one, none is wrong the way a mis-filed task is, they are not ledgered, and they live in the machine database, so nothing accumulates that a deletion would relieve. Deleting one costs something real: fifteen INTEGER columns outside sessions hold a session id and only four declare a foreign key, while sessions.id is a rowid alias allocated as max(rowid)+1 — so deleting the highest session hands that id to the next one created, and eleven undeclared references then name the wrong session while reading as correct. Sessions therefore need no removed column or live_sessions view: the cheapest way not to reuse an id is never to free one. A session that should not be listed is hidden, which is reversible, rather than removed. This leaves open whether sessions.id should gain AUTOINCREMENT, which would defend against a hand-typed DELETE that no decision binds.
