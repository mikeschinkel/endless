Fresh databases are built by replaying goose migrations. schema.sql survives only if it can be generated from those migrations, as a readable snapshot of the full schema for a human studying it. Generated or not, no binary applies it. This removes a class of defect visible today: e-1929-add-tasks-removed.go creates the live_tasks view and schema.sql creates it again, so a populated DB is correct only because an author remembered to write the same DDL twice. The comment block above the view in schema.sql -- CREATE VIEW resolves lazily, CREATE INDEX eagerly, so an index there would deadlock its own rollout -- shows how subtle keeping the two in sync by hand is.
