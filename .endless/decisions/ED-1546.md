task_deps and decision_relations carry no foreign key on their task endpoint — SQLite cannot express an FK whose target table varies by row — so a task delete leaves its relation rows behind, and reused task ids resurrect them as computed fact (E-1911's report claimed an unrelated E-1914 as a follow-up it filed). Enforce in application code, by REFUSING the delete and naming the unlink that clears each row. Deny rather than cascade: a severed relation is unrecoverable, a refusal costs one command. No per-type exemption — relates_to included; one rule that always holds beats a judgment call at the boundary. The guard belongs at every task-deleting verb, not only the one that prompted it: task remove was guarded first, and task import --replace was found orphaning rows the same way. reconcile() also repairs already-orphaned rows, but only while the freed id is unused — which is why prevention is primary. Governs relation rows only; the FK-free history tables are E-1926's question.
