More than one binary version can open one database, so removing a schema object in the same step that introduces its replacement leaves any binary on the other side of that step reading or writing something that is not there. Expand first: add the replacement and leave the existing object working. Contract only after the expand migration has landed and the binary depending on it is installed, so no binary still able to open the database reads the removed object. The two halves are therefore always separate lands, never one. This holds whatever the current ratio of additive to destructive migrations happens to be, and applies equally to renames, which are an add, a backfill, and a later drop.
