Defines the term "primed session". The process was agreed in E-1994; its name was settled on 2026-10-12, while planning E-2291. A primed session is a task's implementation session that Endless starts before anyone asks for it. It starts either from the prime job, when a project opts in with prime.enabled, or from endless task prime <id>. It reads the task in, drafts a plan when there is none, asks the questions it cannot answer, and ends its read-in with endless session primed. That sets the session state primed, and the session holds there until its user resumes it or spawns the task (E-2306). The resumed session's task claim is what starts the work: until then the task stays pre-work (unplanned, submitted or ready) while the session owns it through sessions.task_id. Primed names a session's state, not a task's status: a task status is never 'primed'. Priming is meant to be invisible to the user: a primed task is started the same way as any other.
