Under ED-1568 every migration is additive except the deliberate contract ones, so compatibility is not arbitrary pairwise data: a binary at version B works with a DB at version V iff no contract boundary lies strictly between them. The out-of-band map reduces to the set of breaking version numbers. It is DERIVED, not declared -- a hand-maintained compatibility assertion is the class of artifact ED-1566 eliminated, and being wrong in it produces a silent runtime failure carrying a stamp of approval, which is worse than no map at all. SQL migrations classify mechanically: only ADD COLUMN and CREATE ... IF NOT EXISTS are additive; any DROP, rename or table rebuild opens a contract boundary. goose Go migrations are not statically analyzable, so they must declare. The range governs the DB-AHEAD direction only -- a DB behind a binary is never compatible regardless of boundaries, since the binary needs DDL that is not there.
