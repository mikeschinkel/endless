When a binary opens the database, the two schema versions must agree exactly, and a binary no longer applies migrations automatically each time it opens one. If the DATABASE IS BEHIND, it lacks DDL the binary needs: an installed binary applies the missing migrations itself -- unconditionally in a non-self_dev project, which has only one binary -- while a candidate binary built inside a worktree refuses, because unlanded code may never migrate the real ledger; that is the failure E-1944 records. If the DATABASE IS AHEAD, the binary stops and must be upgraded before it runs again. No compatibility window is derived or maintained: an older binary writing a newer database is unsafe even when a migration only added columns, because those columns exist to be filled by newer code, so the rows it writes are permanently incomplete and no upgrade recovers what was never written. Rollback is restoring a pre-upgrade backup (E-1942). A branch carrying an unlanded migration has its candidate hook degraded until it lands.
