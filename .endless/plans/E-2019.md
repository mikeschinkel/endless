# Plan

Mechanism only. E-2019 changes HOW the schema is defined and applied; it does
not change WHEN. At the end of this task `monitor.DB()` still brings a database
up to date on connect — it just does it by replaying goose migrations instead of
exec'ing `schema.sql`. E-2020 changes the semantics.

That split is what makes E-2019 landable on its own: the only new artifact in a
migrated database is goose's version table, which every existing binary ignores.
No older binary breaks, so this land does not need E-1972 or E-2088.

## Increment 1 — goose, and one baseline migration

- Add `github.com/pressly/goose/v3`. It is used as a LIBRARY against an existing
  `*sql.DB`, never as a CLI. Confirm at implementation time that
  `goose.SetDialect("sqlite3")` drives a `modernc.org/sqlite` connection — the
  project has no cgo and must keep it that way.
- `internal/schema/migrations/00001_baseline.sql`, embedded with `//go:embed` +
  `goose.SetBaseFS`, so the set ships inside the binary with no file dependency.
- **The baseline is the CURRENT shape and nothing else.** Migrations are forward
  looking from this point. No file under `internal/schema/changes/` becomes a
  migration; that directory served land-time application and is not a schema
  history. This is the decision that makes the whole task tractable — see the
  note at the end of the plan for what it discards.
- Generate the baseline from the live schema rather than by hand-copying
  `schema.sql`: dump `sqlite_master` from a database built by the current
  `schema.sql`, so what goose replays is provably what the code produces today.
  `schema.sql`'s `INSERT OR IGNORE` enum seeds go into the baseline too — a
  schema without `task_types`, `gate_kinds`, `process_kinds` and `nav_via_kinds`
  rows fails the integrity gates on first connect.

## Increment 2 — every database creation path moves to goose

- `monitor.DB()`: replace `Exec(schema.SQL)` with goose's up-to-latest against
  the same connection. Same timing, same effect, different source. The
  E-1818 schema-passive guard stays exactly as it is — E-2020 removes it.
- `internal/sandboxcmd/seed_worktree.go:61` does the same.
- `src/endless/db.py` `_init_schema` no longer reads `schema.sql`. Python does
  not gain a migration runner; it shells out to Go, matching how
  `apply-change`, `backup` and `restore` already work.

## Increment 3 — tests build from a hashed template

45 Go files and the Python suite currently `Exec(schema.SQL)` per test. Replaying
the migration set per test is the honest thing and also the slow thing.

- One helper builds a database at the latest version ONCE per run, writes it to
  a template file, and every test copies that file.
- The template's filename carries a hash of the embedded migration set, so a new
  migration produces a different name and the stale one is never reused. That is
  the whole staleness defence; without it a cached fixture silently runs old
  schema against new code.
- Go and Python get the same helper shape, keyed on the same hash, so neither
  suite can drift from the other.

## Increment 4 — delete what goose replaces

- **`db.py`'s migrator goes entirely**: `_migrate`, `_migrate_v2`, `_migrate_v3`,
  `_migrate_v5`, `_migrate_v6`, `_should_auto_migrate`, the `ENDLESS_AUTO_MIGRATE`
  environment variable, and the `_has_table`/`_has_column` helpers that serve
  only them. It has been dead for a while and says so: its docstring reads
  "Once Go's framework (internal/monitor/migrate.go, E-863) owns the schema, this
  function becomes a no-op. Slated for removal in E-894 Phase 5", and
  `internal/monitor/migrate.go` was deleted by E-1459. It short-circuits at
  `PRAGMA user_version >= 6`; the real database is at 12.

  It is not entirely inert, which is the other reason to remove it: 98 sandbox
  databases sit at `user_version 0` and 59 at `5`, so they DO enter the ladder,
  where the DDL steps no-op against a `schema.sql`-built database but
  `_backup_db()` runs first, on every Python connect.

- **`internal/schema/changes/` and the `_schema_version` table go**, along with
  `endless db apply-change`, `event_bridge.apply_change`, the runner package
  (`internal/schema/changes/runner`), and `worktree land`'s apply step. Land-time
  schema application becomes E-2088's migration executable; until E-2088 lands,
  a branch carrying a migration is applied by whatever E-2020 defines. Sequencing
  note: this increment must not land before E-2088 exists, or a self_dev land has
  no way to apply anything. If E-2088 is not ready, stop after Increment 3 — the
  earlier increments stand on their own.

- `schema.sql` itself stays put and keeps being committed. E-2021 turns it into a
  generated artifact; this task must not leave it deleted and unreplaced.

## Increment 5 — baseline the databases that exist

- **The one real database** (`~/.config/endless/endless.db`) is stamped at the
  baseline version without replaying it. It already has the shape.
- **The 158 sandbox databases** under `~/.cache/endless/sandboxes/` are deleted
  and rebuilt lazily. They are cache — the directory says so — and rebuilding
  makes fresh-database-by-replay the path every sandbox exercises, rather than a
  branch taken only by new installs. Baselining them instead would mean stamping
  "this database is at the baseline" onto 98 databases at `user_version 0` whose
  real shape is whatever `schema.sql` looked like when they were made, which may
  not be true.

  A rebuilt sandbox is built at the latest version, so a worktree whose branch
  predates that version will find its sandbox ahead of its own binary. That is
  correct and is the signal, not a bug to accommodate: the worktree rebases onto
  main before it can use its sandbox again. Nothing here builds a sandbox at an
  older version to spare it that.
- Backups under `~/.config/endless/backups/` are not touched. A backup is a
  restore source, and restoring an old one produces a database behind the
  binary — which is exactly the case E-2020's direction rules handle.

# Verification

`.endless/tasks/e-2019/`, run only through the runner — `just verify E-2019`
(which routes `--db sandbox`, so the gate exercises the CANDIDATE binary rather
than main's) or `endless task verify E-2019`. Never executed directly: `_guard.sh`
refuses a direct run, because a direct run carries your real `HOME`.

Shape: a `verify.toml` whose first `[[check]]` is a `gotest` runner over the
migration unit tests — the fail-fast half — plus a `verify.sh` for the
end-to-end assertions that need a built database. The script sources
`_harness.sh`, opens with the DO-NOT-EDIT header naming E-2019, uses `section` /
`assert_eq` / `assert_contains`, and calls `summary` last. Any fixture it ships
is read from `$ENDLESS_VERIFY_DIR`, never a typed path.

The runner supplies the isolation — a temp `HOME` and `XDG_CONFIG_HOME` — so
nothing here passes `--config-dir` to keep writes off the real ledger.

A suite here is a land-time gate for one task at one moment and nothing re-runs
it afterward, so coverage that must outlive the land is mirrored into the
durable suites: assertions 1 and 2 below are the schema's own invariants and
belong in `internal/schema`'s Go tests as well as here.

1. A fresh database built by replaying migrations is schema-identical to one
   built by the current `schema.sql`: compare normalised `sqlite_master` dumps.
   This is the assertion that the baseline is honest, and it must run against a
   `schema.sql` copy pinned in the test, not the live file, so a later edit to
   `schema.sql` fails the test rather than silently redefining the baseline.
2. Enum seed rows survive the replay: `task_types`, `gate_kinds`,
   `process_kinds` and `nav_via_kinds` all pass their `VerifyIntegrity` gates on
   a freshly replayed database.
3. Stamping is not replaying: a database already carrying the current shape is
   stamped at the baseline and no DDL runs against it.
4. The template is hash-keyed: change the embedded migration set, and the test
   helper builds a new template rather than reusing the old one.
5. `db.py` no longer creates or alters any schema object — assert by opening a
   database with an intentionally missing column and confirming Python surfaces
   an error rather than repairing it.
6. `_schema_version`, `internal/schema/changes/` and `endless db apply-change`
   are gone, and nothing references them.
7. No cgo: `CGO_ENABLED=0 go build ./...` succeeds.

# End of plan

What follows explains a choice that would otherwise look like an omission.

## Prior change files are not converted, deliberately

The obvious reading of "convert internal/schema to versioned migrations" is that
the 34 files under `internal/schema/changes/` become 34 goose migrations, with
the 12 `.go` ones becoming goose Go migrations. That is what E-2019's
description says, and it is not what this plan does.

Those files were written to be applied once, at land, to one database. They are
not a schema history and cannot be replayed as one. Measured on the real
database: `_schema_version` holds 46 rows — 12 legacy `vNN-` names from the
pre-ED-1472 framework plus 34 change basenames — while disk holds 34 files, and
the two sets do not agree in either direction. `e-1542-session-gates` is on disk
and was never applied; `e-1653-migrate-status-data` is applied and its file no
longer exists. Several files also rebuild tables into shapes that later files
rebuild again, so replaying them in order reconstructs a sequence of historical
schemas nobody needs and gets to the same place `schema.sql` describes now.

Converting them would mean auditing 34 files to determine which were ever
applied where, then writing a baselining scheme that maps a SET of basenames
onto a LINEAR version — for a history whose only surviving consumer is the one
database that already has the end state.

So the baseline is the current shape, migrations run forward from here, and the
change files are deleted rather than translated. The cost is that a database
older than the baseline cannot be migrated forward by goose. There is no such
database: there is one real database and it is current.
