# Problem

A session's belief about a task's status goes stale. Mike changes a task from the
CLI (`endless task update E-1234 --status revisit`), then says something to Claude
in the same session. Claude answers from the status it learned N turns ago, and the
two of them proceed on different facts until Mike notices and corrects it. That
correction costs a round trip and a pile of tokens, and it recurs constantly.

Today the only per-turn task signal is a single line composed in
`handleUserPromptSubmit` (`internal/hookcmd/claude.go:379`):

    Active task: E-1234 — <title>.

It carries the ID and the title. It carries nothing that changes.

# Approach

Re-assert current state every turn rather than deliver change events once.

This is the central design decision and it is deliberate. An event/notice queue —
a `session_notices` table appended to on mutation and drained into
`additionalContext` — is delivered exactly once. If that delivery lands in a turn
the agent skims, or the conversation is compacted past it, the stale belief is
never corrected again, because the correcting fact has been consumed. A
current-state line is idempotent and self-healing: every turn re-asserts the truth,
compaction cannot permanently lose it, and there is no delivery, ack, retention, or
per-session dedup semantics to build. It also does not depend on the agent
reliably acting on any single injection — the weakest link in the event design.

## Arm 1 — enumerated fields, current value, every turn

Extend the existing per-prompt line to carry the mutable enumerated fields of the
active task:

    Active task: E-1234 (underway · tier 2 · now) — <title>.

Fields: status, tier, phase. Add others only if they demonstrably change
mid-session. Cost is a few lines in the existing code path; no new table, no new
command, no new hook event.

When a value differs from what was injected on the previous turn, and only then,
annotate the transition so the change is visible rather than merely current:

    Active task: E-1234 (status: ready → underway · tier 2 · now) — <title>.

The arrow form appears for one turn; the plain form is the steady state. This needs
a per-session record of the last-injected values — a small `session_task_state`
row, not a growing notices log.

## Arm 2 — freeform fields, staleness marker, sticky until cleared

Per Mike: do not inject the changed text, only that it changed. Model it as
staleness rather than as an event:

    ⚠ E-1234 description edited since you last read it — re-run `endless task show E-1234`.

Derived by comparing the task's `updated_at` (or a per-field version) against a
per-session "last read this task" timestamp, stamped by `task show`. Sticky: it
persists on every turn until the session actually re-reads, so a skimmed turn is
recoverable. Clears automatically on re-read — no ack command.

Applies to description, text/plan, analysis, notes.

## Arm 3 — suppress self-caused changes

Requirement the original proposal did not name, and the one that decides whether
this helps or becomes noise. Sessions change task fields constantly (`task claim`
sets `underway`, `task update --status unverified` at completion). Telling a
session about a change it just made is pure noise, and noise is what trains an
agent to skim the line that matters.

Record the mutating session on each change and suppress the transition annotation
(Arm 1) and the staleness marker (Arm 2) when the mutator is the receiving session.
The steady-state current value still renders — it is cheap and always correct.

# Scope

Active task only, at least initially. "All tasks in `session status`" multiplies
the line count on every turn for tasks the session is not touching; the failure
Mike actually hits is on the task in hand. Widen later only on evidence.

# Non-goals

- No `session notice append` CLI. Changes are detected from the tasks table by the
  hook; a hand-append path would be a second, divergent source of truth. The
  concurrency concern that motivated in-SQL append ("don't lose existing content
  with competing writes") only exists if notices are a mutable text blob; rows —
  or, here, derived state — do not have it.
- No new hook event. Arms 1 and 2 compose into the existing UserPromptSubmit
  response.

# Acceptance

- Change a task's status from another terminal mid-session; the next turn's
  injection shows the new value with an arrow, and the turn after shows it plain.
- Edit a task's description from another terminal; the marker appears and persists
  across turns until `task show` is run, then disappears.
- Run `endless task update --status unverified` from inside the session; no arrow,
  no marker — only the updated steady-state value.
- The per-turn injection remains one to three short lines.

# Open question for Mike

Whether the arrow-transition annotation (Arm 1, second half) earns the
`session_task_state` row it costs, or whether the plain current value alone is
sufficient. Plain-current-value is the whole self-healing win and is nearly free;
the arrow is the part that requires state. Arm 1a alone may be the right v1.
