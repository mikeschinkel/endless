# E-1917 — Notify a session on its next turn when a task it holds changes

## Context

A session's belief about a task's status goes stale. Mike changes a task from the
CLI (`endless task update E-1234 --status revisit`), then says something to Claude
in the same session; Claude answers from the status it learned N turns ago. The two
proceed on different facts until Mike corrects it by hand — a round trip and a pile
of tokens, recurring constantly.

It is not limited to the claimed task. The common case is a task Claude *filed*
earlier in the session, whose status Mike then changes.

Today the only per-turn task signal is one line in `handleUserPromptSubmit`
(`internal/hookcmd/claude.go:379`): `Active task: E-1234 — <title>.` It carries the
ID and title and nothing that changes.

**Outcome:** when a task a session holds changes, that session is told once, on its
next turn — without adding per-turn context bloat.

## Governing decisions

- **ED-903** — Go is the single writer for SQLite; Python shells out for writes and
  retains display reads. All notice writes and the actor stamp are Go.
- **ED-1472** — `internal/schema/schema.sql` is the single source of truth
  (`CREATE ... IF NOT EXISTS`, exec'd per connection); one-off changes live in
  `internal/schema/changes/<e-NNN-slug>.sql`, applied at land via
  `endless db apply-change`.

## Design

Two mechanisms covering two different sets, plus a log to make it observable.

### Arm 1 — one-shot change notices for every session task

When a watched field changes, write one notice row per session holding that task;
deliver it once, on that session's next turn.

One-shot is deliberate. Re-asserting state every turn costs tokens forever, and
repeated hook content degrades outcomes. A missed notice costs exactly the status
quo (Mike corrects by hand, as today), so any delivery rate above zero is a strict
improvement bought without bloat.

**Membership:** `session_tasks` (`schema.sql:522`) already records tasks a session
touched, including a `surfaced` row for tasks created inside the session
(`src/endless/task_cmd.py:6337`). That is the recipient set — no new registration.

**Written by a SQLite trigger.** The rule is "changed → notify; unchanged → don't."
A trigger guarded on `OLD.<f> IS NOT NEW.<f>` fires exactly when a value moved and
cannot be bypassed by a mutation site that forgot to compare. `schema.sql:221`
already establishes this pattern with `tasks_updated_at`, alongside five other
triggers.

### Row shape — one row per (session, update event)

A single `task update` may change status, tier and description at once; that is one
edit and should render as one line, flip `notified` once, and be queryable as one
event.

`{id, session_id, task_id, changes, changed_at, changed_by_session, notified}`

`changes` is TEXT holding JSON keyed by field, each value an object with `before`
and `after`:

```json
{"status": {"before": "ready", "after": "revisit"},
 "description": {"before": "…", "after": "…"}}
```

**Named keys rather than a two-element array.** This was a genuine coin-flip;
recorded so it is not re-litigated:

1. *The query path has no workaround.* `json_extract(changes,'$.status.after')` vs
   `'$.status[1]'` — ad-hoc SQL months later should not require recalling which
   index is which.
2. *Extensibility, already needed.* The `…` sentinel below collides with a field
   whose literal value is `…`; the natural fix is a third key (`"elided": true`),
   which an array cannot carry without a parallel convention or a breaking change.
3. *Heterogeneous values.* `before`/`after` each carry real strings, JSON `null`,
   `""`, and the sentinel. Named fields disambiguate what a `null` means.

The case for the array is real — more scannable raw, and `[before, after]` is a
near-universal diff convention. It loses because it optimizes reading-the-raw-line,
which the `jq` pipe already solves, while the object optimizes querying, which has
no equivalent workaround.

**Enumerated fields** (status, tier, phase) carry real values.

**Freeform fields** (description, text/plan, analysis, notes) carry an elision
sentinel instead of content, so the four meaningful transitions stay distinguishable
without reproducing text:

```json
{"description": {"before": null,  "after": "…"}}   // added
{"description": {"before": "…",   "after": null}}  // cleared to NULL
{"description": {"before": "…",   "after": ""}}    // emptied
{"description": {"before": "…",   "after": "…"}}   // edited, both non-empty
```

The sentinel is the single character `…` (U+2026), stored literally, as a named
constant. A field whose literal value is `…` is indistinguishable from it —
harmless, since the notice's only job is to say the field changed, and it still says
that correctly. If it ever matters, add `"elided": true` (see above).

JSONB is a later optimization once the shape is settled; TEXT for now.

**Rows are immutable snapshots.** Values captured at change time, never re-read from
`tasks` at delivery — by then the task may have moved again, losing intermediate
transitions and making `ready → revisit` unrenderable. Same reason an order carries
its own shipping address rather than joining to the customer's current one.

Per-session rows so `notified` is correct with multiple live sessions, and so there
is an audit trail of what was shown to whom. A session that adds a task *after* a
change needs no backfill — it reads current state the first time it sees the task.

**Building the JSON in the trigger:**

```sql
SELECT json_group_object(f, json(v)) FROM (
  SELECT 'status' AS f,
         json_object('before', OLD.status, 'after', NEW.status) AS v
   WHERE OLD.status IS NOT NEW.status
  UNION ALL
  SELECT 'description',
         json_object('before', <elide(OLD.description)>,
                     'after',  <elide(NEW.description)>)
   WHERE OLD.description IS NOT NEW.description
  ...
)
```

`json(v)` is required — without it the nested object is embedded as a *string*
(`{"status":"{\"before\":…}"}`). Verified against both runtimes.

Both are SQLite **3.51.3** (Python's bundled module; `modernc.org/sqlite v1.48.2`),
confirmed by direct test. This matters because the trigger executes on whichever
connection issues the UPDATE, so `json_group_object` must exist in both.

A `WHEN` guard on the trigger keeps a no-op update from writing an empty-`changes`
row.

### Suppressing self-caused changes

A session should not be told about a change it just made.

Attribution is easy in application code — Python `_current_endless_session_id()`
(`task_cmd.py:3002-3033`), surfaced as `endless session id`
(`session_cmd.py:1514`); Go equivalents at `internal/monitor/session.go:405` and
`internal/sessionquerycmd/session_query.go:634`. It is only hard *inside a trigger*,
which runs in SQLite and cannot call any of it.

**Solution: Go writes the actor into the UPDATE it is already issuing.** Add
`tasks.last_changed_by_session`, set on every task mutation. The trigger reads
`NEW.last_changed_by_session` natively:

```sql
AND st.session_id IS NOT NEW.last_changed_by_session
```

No temp table, no registered SQL function, no connection-pool hazard. Under ED-903
there is exactly one writer, so there is no cross-language "both must remember"
risk — a single Go path sets it.

Rejected: registering a custom SQL function in both runtimes. Any connection
reaching the DB without it registered would make every `UPDATE tasks` hard-fail.

NULL actor (Mike in a bare terminal) suppresses nobody, which is correct — that is
the case this feature exists for.

**Delivery:** on `UserPromptSubmit`, select this session's `notified = 0` rows,
render one line each, mark `notified = 1`.

```
FYI — E-1234 status: ready → revisit
FYI — E-1250 description edited
```

### Arm 2 — current state on the active-task line

`Active task: E-1234 (underway · tier 2 · now) — <title>.`

Stateless — reads current values off `tasks`, no prior value, no table, ~8 tokens on
a line that already ships every turn. Deliberate redundancy with Arm 1, justified
narrowly by compaction: notices are one-shot, so a compaction discards any already
delivered and nothing re-tells the session afterward; the re-injected line survives.
Active task only — most likely still under discussion after a compact, most
expensive to be wrong about.

### Arm 3 — a delivery log

Validation of the delivery half is necessarily manual (it happens on a real turn in
a real pane), so make it observable: `.endless/logs/session-notices.jsonl`,
gitignored, `tail -f`-able while working.

**The hook writes it, and only the hook.** The event worth recording is the
*notification*; a write that never reaches an agent is a tree falling in an empty
forest. The write side is already durably recorded in `session_notices` itself, so
logging it again would be redundant with a table that can simply be queried.

JSONL because `changes` is already JSON and it composes with `jq`, matching the
`session-log.jsonl` precedent in `~/.claude/logs/`. Name matches the table.

```
tail -f .endless/logs/session-notices.jsonl \
  | jq -r '"\(.at) s=\(.session) E-\(.task) \(.changes)"'
```

`logs/` not `log/`, matching `~/.claude/logs/`.

No rotation in v1. Expected rate is one line per *task change delivered*, not per
hook event — orders of magnitude below the 491MB `~/.claude/logs/hook.log` that
motivates the concern. Revisit if that estimate proves wrong.

## Non-goals for v1

- No `session notice append` CLI — the trigger is the only producer. Add a command
  when a second producer exists.
- No JSONB — TEXT until the shape is settled.
- No log rotation.
- No new hook event — all arms compose into the existing `UserPromptSubmit`
  response.

## Verification

One command: `esu && ./tests/tasks/e-1917-verify.sh`, covering:

- Status changed by another actor → one row, `{"status":{"before":…,"after":…}}`.
- One `task update` changing three fields → exactly one row, three keys.
- Update setting a field to its existing value → no row.
- Description added / cleared / emptied / edited → the four sentinel forms.
- A session-authored change → no row for that session, rows for other holders.
- NULL actor → rows for every session holding the task.
- Two sessions holding one task → both get rows; one marking notified does not
  consume the other's.
- Active-task line renders current status/tier/phase.
- Delivery appends one JSONL line; a write with no delivery appends none.

The DB half is fully automatable. The last mile — the FYI line actually appearing on
Mike's next turn — is manual, once, after landing; the log is what makes that
observable rather than inferred.

Plus the project-wide regression (tests, lint, build), run by me and reported in one
line.
