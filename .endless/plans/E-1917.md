# E-1917 — Notify sessions when their tasks change

## Context

A session's belief about a task's status goes stale. Mike changes a task from the
CLI (`endless task update E-1234 --status revisit`), then says something to Claude
in the same session; Claude answers from the status it learned N turns ago. The
two proceed on different facts until Mike corrects it by hand — a round trip and a
pile of tokens, recurring constantly.

It is not limited to the claimed task. The common case is a task Claude *filed*
earlier in the session, whose status Mike then changes.

Today the only per-turn task signal is one line in `handleUserPromptSubmit`
(`internal/hookcmd/claude.go:379`): `Active task: E-1234 — <title>.` It carries the
ID and title and nothing that changes.

**Outcome:** a session is told, once, when a task it holds changes — without adding
per-turn context bloat.

## Design

Two mechanisms covering two different sets. Not alternatives.

### Arm 1 — one-shot change notices for every session task

When a watched field changes, write one notice row per session holding that task;
deliver it once, on that session's next turn.

One-shot is deliberate. Re-asserting state every turn costs tokens forever, and
repeated hook content degrades outcomes. A missed notice costs exactly the status
quo (Mike corrects by hand, as today), so any delivery rate above zero is a strict
improvement bought without bloat.

**Membership:** `session_tasks` already records tasks a session touched, including a
`surfaced` row for tasks created inside the session (`src/endless/task_cmd.py:6337`).
That is the recipient set — no new registration.

**Written by a SQLite trigger, not application code.** The rule is "changed →
notify; unchanged → don't." Application code must remember to compare old against
new at every mutation site across both the Python CLI and the Go binaries, and a
site will eventually forget, silently. A trigger guarded on `OLD.<f> IS NOT NEW.<f>`
fires exactly when a value moved and cannot be bypassed. `src/endless/db.py:139`
already establishes this pattern for `updated_at`.

One `AFTER UPDATE ON tasks` trigger; one statement per watched field:

```sql
INSERT INTO session_notices (session_id, task_id, field, old_value, new_value, changed_at)
SELECT st.session_id, NEW.id, 'status', OLD.status, NEW.status, <now>
  FROM session_tasks st
 WHERE st.task_id = NEW.id
   AND OLD.status IS NOT NEW.status;
```

`IS NOT` rather than `!=` so NULL transitions compare correctly. A no-op update
writes nothing.

**One row per (session, update event), not per field.** A single `task update` may
change status, tier and description at once; that is one edit and should render as
one line, flip `notified` once, and be queryable as one event.

`{id, session_id, task_id, changes, changed_at, changed_by_session, notified}`

`changes` is TEXT holding JSON, built by the trigger:

```json
{"status": ["ready", "revisit"], "description": null}
```

A two-element array is `[old, new]` for enumerated fields (status, tier, phase). A
`null` means a freeform field (description, text/plan, analysis, notes) changed
without carrying values. `json_extract` / `json_each` make it queryable. JSONB is a
later optimization once the shape is settled — TEXT for now.

**Rows are immutable snapshots.** Values captured at change time, never re-read from
`tasks` at delivery — by then the task may have moved again, losing intermediate
transitions and making `ready → revisit` unrenderable. Same reason an order carries
its own shipping address rather than joining to the customer's current one.

Per-session rows so `notified` is correct with multiple live sessions, and so there
is an audit trail of what was shown to whom. A session that adds a task *after* a
change needs no backfill — it reads current state the first time it sees the task.

**Building the JSON in the trigger:**

```sql
SELECT json_group_object(f, json(v)) FROM (
  SELECT 'status' AS f, json_array(OLD.status, NEW.status) AS v
   WHERE OLD.status IS NOT NEW.status
  UNION ALL
  SELECT 'description', json_quote(NULL)
   WHERE OLD.description IS NOT NEW.description
  ...
)
```

`json(v)` is required — `json_group_object(f, json_array(...))` embeds the array as
a *string* (`{"status":"[\"a\",\"b\"]"}`). Verified.

Both runtimes are SQLite **3.51.3** (Python bundled module; `modernc.org/sqlite
v1.48.2`), confirmed by direct test. This matters because the trigger executes on
whichever connection issues the UPDATE, so `json_group_object` must exist in both.

### Suppressing self-caused changes

A session should not be told about a change it just made.

Attribution is easy in application code — Python `_current_endless_session_id()`
(`task_cmd.py:3002-3033`), surfaced as `endless session id`
(`session_cmd.py:1514`); Go equivalents at `internal/monitor/session.go:405` and
`internal/sessionquerycmd/session_query.go:634`. It is only hard *inside a trigger*,
which runs in SQLite and cannot call any of it.

**Solution: the app writes the actor into the UPDATE it is already issuing.** Add
`tasks.last_changed_by_session`; every mutation sets it alongside the fields it
changes. The trigger reads `NEW.last_changed_by_session` natively:

```sql
AND st.session_id IS NOT NEW.last_changed_by_session
```

No temp table, no registered SQL function, no connection-pool visibility hazard.

Rejected alternative: registering a custom SQL function in both runtimes. It works
(modernc supports it), but any connection reaching the DB without it registered
makes every `UPDATE tasks` hard-fail. The column has no such failure mode. Its own
risk — a mutation site forgetting to set it, leaving a stale actor — is mitigated by
funneling writes through one path per language, plus a test asserting a
session-authored change produces no row for that session.

NULL actor (Mike in a bare terminal) suppresses nobody, which is correct: that is
the case this feature exists for.

**Delivery:** on `UserPromptSubmit`, select this session's `notified = 0` rows,
render one line each, mark `notified = 1`.

```
FYI — E-1234 status: ready → revisit
FYI — E-1250 description edited
```

### Arm 2 — current state on the active-task line

`Active task: E-1234 (underway · tier 2 · now) — <title>.`

Stateless — reads current values off `tasks`, no prior value, no table, ~8 tokens on
a line that already ships every turn. Deliberate redundancy with Arm 1, justified
narrowly by compaction: notices are one-shot, so a compaction discards any already
delivered and nothing re-tells the session afterward; the re-injected line survives.
Active task only — most likely still under discussion after a compact, most
expensive to be wrong about.

## Arm 3 — a log to watch it work

Validation of the delivery half is necessarily manual (it happens on a real turn in
a real pane), so make it observable: `.endless/log/notices.log`, gitignored,
`tail -f`-able while working.

A trigger cannot write files, so log at both ends:

- **Write side** — after commit, the mutating command queries the rows the trigger
  just inserted and logs one line each.
- **Delivery side** — the hook logs what it rendered and to which session.

```
2026-08-07T14:32:10 WRITE    session=1048 task=1234 actor=NULL changes={"status":["ready","revisit"]}
2026-08-07T14:32:44 DELIVER  session=1048 task=1234 status: ready → revisit
```

The pairing is what makes a failure diagnosable: written-but-never-delivered is a
different bug from never-written, and one line each says which.

`.endless/log/` rather than `.claude/log/` — neither directory exists today, so
there is nothing to consolidate; the question of moving other log producers under
`.endless/log/` is a separate task, not this one.

No rotation in v1 — the file grows unbounded.

## Non-goals for v1

- No `session notice append` CLI — the trigger is the only producer. Add a command
  when a second producer exists.
- No JSONB — TEXT until the shape is settled.
- No log rotation.
- No new hook event — all arms compose into the existing `UserPromptSubmit`
  response.

## Files

- `src/endless/db.py` — `session_notices` table, `tasks.last_changed_by_session`
  column, and trigger, following the ALTER-if-missing / `CREATE TRIGGER IF NOT
  EXISTS` pattern at :129-142
- Mutation paths in `src/endless/task_cmd.py` and the Go equivalents — set
  `last_changed_by_session` on every task UPDATE, resolved via the existing
  session helpers
- `internal/hookcmd/claude.go` — `handleUserPromptSubmit` (:359) composes and logs
  notices; active-task line (:379) gains current fields
- `internal/monitor/` — query + mark-notified helpers, alongside existing
  `GetTaskTitle` / `GetActiveSession` accessors

## Verification

One command: `esu && ./tests/tasks/e-1917-verify.sh`, covering:

- Status changed by another actor → one notice row carrying `["old","new"]`.
- One `task update` changing three fields → exactly one row, three keys in `changes`.
- Update setting a field to its existing value → no row.
- Description edited → key present with `null` value.
- A session-authored change → no row for that session, rows for other holders.
- NULL actor → rows for every session holding the task.
- Two sessions holding one task → both get rows; one marking notified does not
  consume the other's.
- Active-task line renders current status/tier/phase.
- Both ends write to `.endless/log/notices.log`.

The DB half is fully automatable. The last mile — the FYI line actually appearing on
Mike's next turn — is manual, once, after landing; the log is what makes that
observable rather than inferred.

Plus the project-wide regression (tests, lint, build), run by me and reported in one
line.
