# Plan — an explicit DB context, and an answer that says which one

Two halves of one omission: the context can be GUESSED, and the answer never
says which one it used. Half 1 removes the guess; half 2 states the answer.

## 1. endless-go stops guessing

`monitor.SelfDetectWorktreeSandbox()` and its unconditional call in
`cmd/endless-go/main.go`'s startup path are DELETED, not gated. With no caller
left, `setDetectedContextDir` goes with it, and `dbContextFromFlag` collapses
into `dbContextDir != ""` — every context is a flag's now, so the
two-variable split that existed to tell a flag from a guess has nothing left to
tell apart.

`guardWorktreeDBContext` is unchanged. It already refuses when no explicit
context exists inside a self-dev worktree, and it already sits at the single
`DB()` entry point, so it covers every binary that opens the database
including future ones. It stopped firing because detection satisfied it; with
detection gone it fires again. Nothing about the gate was wrong.

`worktreeDBContextRefusal`'s wording changes: it currently says 'Invoke
through the endless CLI with --db main|sandbox, which threads --config-dir to
this binary', which stops being true once endless-go takes --db itself.

## 2. What `--db` means on endless-go

`--db main|sandbox`, consumed before any subcommand body, replacing
`ConsumeDBContextFlag`'s `--config-dir`.

  - `main` → the main config dir.
  - `sandbox` → this worktree's sandbox dir, refused when cwd is not inside a
    self-dev worktree, exactly as Python's `apply_db_choice` already refuses it.

The subtle part, stated so it is not re-litigated later: `--db sandbox` still
reads cwd, because cwd is what says WHICH worktree's sandbox. That is not the
guess coming back. The flag grants permission to open a database; cwd supplies
the address of the one permitted. What is being removed is cwd granting the
permission.

Subcommands that open no database — `task-status`, `session-state`,
`markdown`, `template` — do not accept `--db`; an unknown flag there is a
usage error, as today.

## 3. `--config-dir` retires

Every current caller moves to `--db`, and the ones that genuinely target a
throwaway directory move to `--db-dir <path>`, which keeps an escape without
keeping a second spelling of the normal case.

Note while auditing: `main_config_dir()` is `Path.home()/.config/endless`, so
it FOLLOWS $HOME even though it deliberately ignores $XDG_CONFIG_HOME. Any
caller that already runs under a temp HOME — the verify runner does — is
therefore served by plain `--db main` and needs no escape at all. Decide
per call site rather than converting them all to `--db-dir` by reflex; the
escape is for callers that must name a directory WITHOUT owning the process
environment, chiefly Go tests using `t.TempDir()`.

## 4. Every read AND WRITE states what answered it

One rule, so the three cases below are a rule and not a list:
ANNOUNCE WHAT THE INVOCATION RESOLVED, WHEN IT COULD HAVE RESOLVED OTHERWISE.

  - The DATABASE, in a self-dev project: ALWAYS. Either database could have
    been right on any invocation, so there is no case where the answer was
    never in doubt.
  - The PROJECT, downstream (non-self-dev): ONLY when the resolved project is
    not the one enclosing cwd — a `--project` flag, a session binding, or a
    cwd outside any registered project. With one database and usually one
    project, always-on is repetition, and repetition where nothing varies is
    how a line stops being read.
  - PINNED-IN-CODE contexts: NEVER. See §5 — a pin is not a resolution.

Surfaces:

  - MACHINE formats (`--json`, `--tsv`): a field in the payload. Per-row for
    array payloads (non-breaking — `list-live`'s rows already carry
    `project_id`), once at top level for object payloads.
  - The AGENT-FACING output mode and HUMAN output: in-band on stdout. Where a
    header already names the project — `session list`'s
    `Sessions — project: probe` — the database joins it there rather than
    taking a line of its own. (That mode's flag is `--llm` at the time of
    writing and is being renamed to `--agent` by a concurrent task; this plan
    depends on the mode, not on its spelling. Use whichever name is in the tree
    when this is implemented.)
  - WRITES announce as well as reads. E-1429's founding incident was a WRITE —
    a test `endless task add` that landed in the real ledger as E-1425 — and a
    write to the wrong database is the damaging case, where a wrong read only
    misleads. A mutating command names the database alongside what it changed.

NOT on stderr, deliberately, departing from `rowcap.echo_footer`: that footer
is prose COMMENTARY ABOUT an answer and would corrupt a payload, whereas the
store a result came from is DATA ABOUT THE RESULT and belongs in it. The
analysis records why stderr loses against an agent specifically.

## 5. The exemption

Contexts PINNED IN CODE announce nothing: the hook (`ForceRealDB`), and
`tmux`, `session-status` and `project-status` (`PinMainDB`). If the caller
could not have influenced the choice there is nothing to disambiguate, and the
tmux status line has no room for it. This is §4's rule, not an exception to it.

## 6. Verification

`.endless/tasks/e-1668/verify.sh`, sourcing `_harness.sh`:

1. Fail-fast unit: `internal/monitor` (the gate and its truth table),
   `internal/sessionquerycmd`, and the Python suite.
2. THE INCIDENT, as a regression test. From inside a worktree, using main's
   binary: `endless-go session-query list-live --project-root <main>` with no
   `--db` must REFUSE, naming the remedy. The same call with `--db main` must
   return main's rows. That single pair is the whole of half 1 — it is the
   exact command that silently answered from the sandbox.
3. `SelfDetectWorktreeSandbox` is absent from the tree; no call site remains.
4. No `--config-dir` survives outside the `--db-dir` escape.
5. Provenance, reads: a `--json` read carries the database and project; the
   same read under `--db main` and `--db sandbox` reports different values,
   from a seeded throwaway pair so the difference is checkable rather than
   asserted.
6. Provenance, writes: a `task add` against a seeded sandbox names the
   sandbox in its confirmation. This is E-1425's incident, inverted into a test.
7. The downstream rule: with a single non-self-dev project, a read from inside
   its checkout prints NO project line, and the same read with `--project`
   naming another does.
8. The exemption holds: the tmux status line's bytes are unchanged.

## 7. Not in scope

  - Python's `--db` requirement. It already refuses without the flag inside a
    self-dev worktree; this task changes nothing there.
  - E-1429's gate design. It was right; it was defeated.
  - Renaming the agent-facing output flag. A concurrent task owns `--llm` →
    `--agent`; this one consumes whatever it lands.
## 8. Decided during implementation

Three departures from §4 as written, recorded here so a reviewer meets them in
the plan rather than discovering them in the diff.

**`--tsv` carries nothing.** §4 said machine formats carry a field, naming
`--json` and `--tsv`. `endless sql` is the only `--tsv` surface, its rows are
the columns of arbitrary SQL, and it emits no header row — so the only thing a
"field" could mean there is a trailing column on every row, which silently
changes what every `cut -fN` and `while read` consumer sees. §4's own
justification for putting the trace in the payload was that doing so is
NON-breaking; for TSV it is not. Owner's call, 2026-09-16.

**The in-band line is one trailing line from one choke point, not folded into
each command's header.** §4 illustrated the rule with `session list`'s
`Sessions — project: probe`, the database joining it there. The trace is instead
written by the root group's result callback, so every command has it and a new
one cannot omit it. Where §4's both-ends intent does apply — the agent-facing
renders — a matching leading copy is emitted at the top of each, byte-identical
to the trailing one, on E-2097's rule.

**The Go layer announces the DATABASE only; the PROJECT half lives in Python.**
§4's project bullet fires downstream, and downstream `endless-go` is Python's
helper rather than anything a user types. Threading a resolved project name
through every internal verb would have put the fact where nobody reads it.

### Known limitation, from §4's own shape rule

An ARRAY payload carries the field per row, so a `--json` render of ZERO rows
carries no provenance at all — and "no rows" is exactly the shape the founding
incident took. The alternative is an envelope, which is the breaking change
per-row injection was chosen to avoid. Left as-is; an object payload and every
non-empty array are covered, as is the in-band line on the human and agent
surfaces.
