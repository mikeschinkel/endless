# Plan — Make per-worktree sandboxes universal by moving them into the worktree

Design settled in E-1958's brainstorm; implementation notes are in this task's
analysis. This plan covers only what the analysis left open: how existing
worktrees get there.

## Decisions taken (Mike, 2026-09-01)

1. **Migration is a one-shot command you run**, not a lazy rename inside the
   resolver. A path-resolving function must not mutate the filesystem, and two
   sessions on one worktree would race. One command gives one observable moment
   and a report.
2. **Nothing provisions a sandbox on miss.** Migration is the last moment a
   missing sandbox is expected. After it, an absent sandbox means something
   unanticipated happened, and the resolver must say so rather than quietly
   build one — a silent recovery hides the anomaly and risks acting on a
   half-understood state. (This reverses an earlier answer in the same planning
   pass, which had provision-on-miss run the project's hook. The reversal is
   what makes migration responsible for the legacy worktrees in step 3b.)
3. **Migration reports orphans and deletes nothing.** Deleting directories is
   not something this change does on its own authority.

## The 26 sandbox-less worktrees, which the analysis does not cover

All 26 are legacy: their directories were created before sandboxes existed, and
nothing has provisioned one since. Checked by directory birth time rather than
by the `created_at` field in `.endless/worktree.json`, which a revisit rewrites
— e-1115 reads `2026-09-01` there while the directory itself dates to
2026-05-02.

They are not a live leak. Worktree-create provisions correctly today; these
simply predate it.

**Measured, because the risk was worth confirming rather than assuming:** the
E-1429 gate holds in a sandbox-less worktree. A bare command is refused with the
"requires an explicit --db value" error; `--db main` resolves to the main
database, which is what it asks for; `--db sandbox` provisions on demand and
creates nothing until asked. So these worktrees are not silently writing to
main today.

Two exposures remain and belong in the implementation's thinking:

- Hook and tmux traffic pins main unconditionally by design (E-1450), sandbox or
  not, so nothing here changes that.
- The gate is keyed on cwd. This task's analysis already records a case where
  `XDG_CONFIG_HOME` beat cwd silently (the E-1904 evidence). Removing the
  injection closes that; until then, the gate is the only thing standing between
  these 26 and main, and it is one mechanism deep.

## Order of work

Steps 1, 2, 4 and 5 are unchanged from the analysis. This plan replaces step 3.

### 3a. Migrate what exists

`endless sandbox migrate`, run once, idempotent, reporting what it did.

For each directory under the old sandbox root:

- **Worktree still exists, no sandbox in it yet** → rename it in. Same
  filesystem, so a rename.
- **Worktree still exists and already has one** → leave both, report the
  collision, exit non-zero at the end. Do not merge or overwrite; a
  hand-inspected case is better than a guessed one.
- **No surviving worktree** → report as an orphan. Delete nothing.

### 3b. Provision what never had one

The same command then walks the worktrees and, for each with no sandbox,
creates the directory, writes the self-ignoring `.gitignore`, and runs the
project's `post-worktree-create` hook — exactly as worktree-create does.

This is not optional and not a separate command. Decision 2 removes every later
opportunity: if migration does not fix the 26, nothing ever will, and each one
becomes a worktree whose every command refuses.

A hook failure here is non-fatal and loud, matching worktree-create: the
directory stays, and the report names the script and how to re-run it. Report
these separately from the renames — "23 moved, 26 provisioned, 3 hook failures"
is the line that tells you whether to look at anything.

### 3c. The report

Moved, provisioned, skipped, collided, orphaned, with the space the orphans
hold. `--dry-run` does everything but the renames, creations and hook runs, so
the report can be read before anything changes.

The command survives after migration rather than being deleted: a worktree
restored from a backup, or a machine that skipped a release, arrives in the same
state.

### 3d. The resolver refuses on miss

When a worktree has no sandbox, the single resolver fails loudly — naming the
worktree, saying a sandbox is missing where one is expected, and pointing at
`endless sandbox migrate`. It does not create one.

Say plainly in that message that this is unexpected after migration, so whoever
hits it treats it as a finding rather than a chore.

## Boundaries

- Does NOT delete the old sandbox root, or any orphan. That stays a separate,
  human-run step.
- Does NOT add a schema-version stamp. The analysis names it as the residual
  once relocation lands; it is its own task if drift still bites.
- Does NOT fold in E-1963's ephemeral `run`/`enter`/`prune` decision.

## PRODUCT

The relocation is what makes sandboxes universal rather than self_dev-only, so
every consumer project's worktrees gain isolation they do not have today. The
migration command is one-shot for this machine but ships as a normal verb: any
installation with sandboxes under the cache root needs it exactly once, and any
project with worktrees predating its own adoption needs 3b.

## Verify — .endless/tasks/e-1964/verify.sh

1. Fail-fast unit gate: the Go and Python tests this task adds.
2. `--dry-run` changes nothing on disk, and its report matches what a real run
   then does.
3. A fixture worktree with an old-location sandbox: migrated by rename, contents
   byte-identical, old path gone.
4. A fixture worktree with sandboxes in BOTH locations: neither is touched, the
   collision is reported, exit non-zero.
5. An orphan: reported, still on disk afterwards.
6. A fixture worktree with NO sandbox: provisioned, `.gitignore` ignores
   everything, and the project's hook ran.
7. A worktree whose hook FAILS: directory kept, warning names the script, the
   run still reports the other outcomes and does not abort.
8. Migration is idempotent — a second run moves, creates and changes nothing,
   and exits zero.
9. THE ONE THIS MUST NOT GET WRONG: after migration, a worktree whose sandbox is
   deleted by hand makes the resolver REFUSE, naming the worktree and the
   command. It must not silently rebuild one.
10. A non-self_dev project gets a sandbox at worktree-create — the ungating in
    step 2 actually fires.
11. After the injection is deleted, `_guard.sh`'s isolation arm still refuses a
    hand-run suite (see the analysis's note on that consumer).
