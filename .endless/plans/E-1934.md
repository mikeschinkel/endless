# Plan — E-1934

Design rationale lives in this task's analysis; this is the build order. Part 2
(widen ED-1073) is already done and is not in scope.

## 1. The predicate

New helper beside the existing path helpers in the CLI module, next to
`_is_absolute_path`, `_is_path_shaped` and `_absolute_path_tokens`. It returns
the offending tokens in content, matching:

- `<name>.<ext>:<digits>` where `<ext>` is in the effective extension set
- the same with a range suffix (`-<digits>`)
- the same with a column suffix (`:<digits>`)

It skips any token preceded by a scheme separator or an at-sign, or beginning
with a www prefix, so a host and port is never mistaken for a citation. That
guard is load-bearing, not decoration: many source extensions are also ccTLDs.

It does NOT match a bare leading-colon number.

## 2. Where it runs

In `_resolve_content_flag`, on the RESOLVED content — both the inline branch and
the file branch — not inside `_guard_inline_content`.

This is the one structural decision in the task. `_guard_inline_content` sees
inline values only; the resolver's own docstring says file content "is otherwise
trusted and never gated". A plan citing line numbers throughout is exactly the
thing E-1934 exists to stop, and a plan is long-form, so it arrives by
`--text-file`. Gating inline only would leave the motivating vector open.

Rule 2 stays inline-only. Its contract does not change here.

Because every long-form field on task add/update, decision add/update, epic and
the status-transition verbs funnels through this one resolver, description, text,
analysis and outcome are all covered by construction. No per-flag wiring.

## 3. Configuration

Read through the project config module, following the shape
`project_minimizer_config` already uses for a nested block with defaults.

- built-in default extension set (see analysis)
- `content.extensions.block` — adds
- `content.extensions.unblock` — removes
- an extension in both is refused at config load, not silently resolved
- a switch disabling this gate; give Rule 2 its own switch at the same time.
  Rule 1 is NOT covered by either switch: it catches a mis-passed file path,
  which is a mistake, not a house style.

## 4. Guide wording

In the tasks guide source, the `text` row still reads "Full implementation plan,
including approach, file paths, verification steps", and nothing in that guide
mentions line numbers. Rewrite to say file and function names, and state the
rule. Re-run the guide index generation afterwards.

## 5. Tests

Suite at the task's verify path, first statement sourcing the shared harness.
Read the tasks CLAUDE file before writing it. Cases: each of the three matched
shapes; the bare-colon non-match; clock time, host and port, and a ratio all
passing; a URL containing a source extension passing; block and unblock each
taking effect; both-lists refusal; gate disabled; and the file-loaded path
refusing, which is the regression that proves decision 2.

## Open questions — answer before building

Q1. Section 2 is a recommendation, not a settled fact. Gating resolved content
means `--text-file` starts refusing documents that load fine today. Confirm, or
say inline-only and accept that plans bypass the gate.

Q2. The default extension set is roughly eighty entries. Ship that, or start
with a smaller core and let projects add?

Q3. Should the disable switch be per-project only, or also per-invocation?
There is no escape hatch by decision, and a per-invocation switch would be one
in all but name — so the recommendation is project config only.
