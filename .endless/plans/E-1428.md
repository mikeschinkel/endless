# Rework `task claim` output: hide the sandbox path, align labels, purge the `eswt` ghost

## Problems

### 1. The output instructs users to run a command that does not exist

Current output:

```
Updated E-1424 (Test foo):
• Status: needs_plan -> in_progress
• bound to session 1

• sandbox provisioned: ~/.cache/endless/sandboxes/worktree-e-1424
• worktree created: ~/Projects/endless/.endless/worktrees/e-1424

  To work on this task, choose one:
    1. Delegate to a fresh Claude session:
         endless task spawn E-1424
    2. Do it yourself (edit, run tests, etc.):
         eval "$(endless shell-init)"  # Adds eswt shell helper func
         eswt E-1424                   # Changes to Git worktree dir
```

`endless shell-init` defines exactly three helpers: `esu`, `esp`, `esf`. There is no `eswt`. The comment "Adds eswt shell helper func" is false, and `eswt E-1424` produces "command not found." The correct helper is `esu` (= `endless session use`), which cd's into the worktree AND exports `ENDLESS_SESSION_ID` — exactly the intended action.

### 2. The sandbox cache path is presented as if it were a cd target

The output lists `sandbox provisioned: ~/.cache/endless/sandboxes/worktree-e-1424` as a parallel line to `worktree created: ...`. Users scan for a path and cd into the first one — the sandbox cache dir — which is never where they should be. Subsequent endless commands then fail with `Error: Not in a registered project directory` because the cache dir is not a project. Hit by Mike 2026-05-19.

The sandbox path has no routine user-facing purpose (only a rare SQL-client-debug case). It should not appear in default output.

## Deliverables

### A. Hide the sandbox path from default output
Remove the sandbox cache path line. Add a dedicated command to retrieve it on demand:

> `endless worktree sandbox [E-NNN]` — prints the absolute sandbox cache directory path for a worktree's task, for the rare SQL-client-debug case. Matches the existing pattern of small print verbs (`endless session id`, `endless session cd`). With no arg, resolves from cwd if inside a worktree.

### B. Rewrite claim's output against what it actually prints

The original deliverable here was "adopt the aligned-label format", and its
sample was a two-option "To work on this task, choose one:" menu. That menu no
longer exists — E-2106 deleted it, along with the broken `eswt` line inside it,
and replaced it with one outcome per caller. So the old sample proposed a
format for output that is gone. What survives from it is the discipline it was
arguing for, and that is what this deliverable keeps: aligned labels,
scannable, and no path printed that is not a cd target.

#### What claim prints today

```
Updated E-1424 (Test foo):
• Status: ready -> underway
• bound to session 1                        (only when a session resolved)

• sandbox provisioned: ~/.cache/endless/sandboxes/worktree-e-1424
• worktree created: ~/Projects/endless/.endless/worktrees/e-1424
```

then exactly one of the four outcomes E-2106 gave it:

| caller | tail |
|---|---|
| inside a Claude session | `/cd <abs worktree>` |
| a shell that bound a sibling | `E-N is bound to session ES-1 … endless session goto ES-1` |
| a shell that bound nothing | `Started Claude on E-N in window 'E-N'` + the switch line |
| `--unattended` | nothing further |

#### The target

```
Updated E-1424 (Test foo):

  • Status:       ready -> underway
  • Git worktree: ~/Projects/endless/.endless/worktrees/e-1424

  /cd <the worktree, absolute>   # point Claude's working dir at the worktree

```

Aligned labels, the sandbox line gone (deliverable A), and the caller's one
outcome below them — not a menu, because E-2106 established that the caller
never had a choice to make.

#### The session id is NOT a labeled row

Settled here rather than left open. The `Session:` row the old sample proposed
does not exist, and neither does the `bound to session N` line it was replacing.
The id is printed exactly once, as `ES-N`, and only on the path where it is
news: a shell that bound a Claude session in ANOTHER pane, in the
`endless session goto ES-N` line E-2106 already prints there.

Why not a row:

- It prints a BARE INTEGER. `session_id_display` exists because sessions and
  tasks are separate id spaces that both rendered as `E-NNN` (E-1261), and
  `session goto` refuses a bare integer matching both — so the row spells an id
  in the one form the navigator rejects. On the sibling path the same number
  now appears twice, four lines apart, in two spellings.
- On the dominant path — a Claude session claiming its own task — it restates
  the caller's own identity.
- It sits ABOVE the worktree line and the next step, which are the only lines
  anyone acts on.

Why print it at all, on the one path:

- Since E-2106 the binding is no longer always "me": claim binds this session,
  binds a sibling in another pane, or starts a new one. Binding to a sibling
  you did not mean is what seeing the id catches, and under ED-1560
  `sessions.task_id` is write-once, so a wrong binding cannot be undone.

The other three paths print no id, and correctly: on a self-claim you ARE the
session, a launched session has no id yet (its window name is its identity),
and `--unattended` bound nothing.

### C. Apply the same labeling discipline to sibling commands
`endless task spawn` and `endless task release` have analogous multi-line output. Audit and bring them to the same aligned-label format. Verify their work-instruction blocks reference real helpers (no `eswt`-style ghosts).

### D. Purge `eswt` from the guide (absorbed from E-2124)

Deliverable C says "verify their work-instruction blocks reference real helpers
(no `eswt`-style ghosts)". The guide is the other place Endless tells a user how
to get into a worktree, and it carries the same ghost: the shell-helpers table
in `docs/guide/orchestration.md` calls `eswt` "(Planned, not yet shipped.)",
while `docs/guide/index.md`, `docs/guide/help/_topics.md` and
`docs/guide/help/shell-init.md` list it beside `esu` as if a reader had it.
Find every site with `grep -rn eswt docs/`.

That framing is now wrong rather than premature. Mike settled it on 2026-09-08
— "We don't want `eswt` anymore. `esu` is sufficient" — and E-1180, which
proposed shipping it, is obsolete, as is E-1254 (which wanted claim's `eswt`
line changed to `esu`, and whose subject E-2106 deleted). Remove the references;
where a reader is being pointed at a worktree, `esu` is the answer.

One task rather than two, per ED-1550: the broken helper reference in claim's
output and the same helper in the guide are two symptoms of one cause — `eswt`
was proposed, documented, and never shipped.

## Verification

1. `endless task claim E-NNNN` from main checkout → output uses the aligned format and shows no sandbox path.
2. Every command line the output prints can be pasted into a shell and runs — no helper that `endless shell-init` does not define, and no path that is not a cd target.
3. `endless worktree sandbox E-NNNN` → prints the sandbox cache path, exit 0.
4. `endless task spawn` / `endless task release` outputs → same aligned format, no broken helper references.
5. `grep -rn eswt docs/ src/` → no hits.
6. Claim from a Claude session, from a shell beside a Claude pane, from a shell alone, and with `--unattended` → the session id appears in exactly one of the four, as `ES-N`, in the `session goto` line; no `Session:` row and no `bound to session N` in any of them.

## Grown scope (recorded during implementation)

Three things folded in rather than filed, each cheaper to make than a task row
describing it would be:

1. **The re-claim-by-the-owner path.** `claim_item`'s "already active in
   session N" branch is a fifth output shape the plan's four-caller table does
   not name, and it had both defects the plan argues against: a BARE INTEGER
   session id — the caller's own — and no aligned block. It also returned
   without printing any next step, so a Claude session re-claiming its own task
   was handed a worktree and no `/cd`. It now reports in the same aligned shape,
   names no session, and ends on `_echo_claim_next_step` like every other path.

2. **`task bind`'s session ids.** Deliverable C names spawn and release; bind is
   the fourth verb in that family and the one claim's own refusal routes people
   to (`endless task bind E-<id>`). It printed the session as a bare integer in
   three places — the exact spelling `session goto` refuses, and the exact
   argument the plan makes for dropping claim's `bound to session N` row. Now
   `ES-N`, via the existing `session_id_display`.

3. **A red Go test, pre-existing on main.**
   `TestEventBackup_EnforcesTieredRetention` seeded two backups as "six days
   back" and "six days and ninety minutes back" and asserted they shared a
   DAILY bucket. Buckets are calendar periods, so that holds only when the
   suite runs after 01:30; before then the older one falls into the previous
   day and survives the sweep. It was failing at 00:44. The production
   retention code is correct — the fixture now anchors both stamps inside one
   calendar day. Repaired here because this task cannot report the project-wide
   suite red.

`task release` was audited under deliverable C and needed no change: it is a
tombstone whose whole output is a refusal in the established
prose-then-indented-command shape, and both commands it names exist.

## Observation, not filed

`task bind` still prints "bound to session ES-N **for display**", which
contradicts its own docstring — E-2093 rewrote that docstring specifically to
say the "display only" framing "understated the verb by a wide margin", since
bind sets `sessions.task_id` and under ED-1560 that column IS the ownership
record. Left alone: rewording it is a claim about what bind means, not output
discipline, and belongs to whoever decides that.
