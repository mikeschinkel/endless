# Plan — Gate task type against verb category (replace `completable`)

Blocked by E-1659 (task→todo, bug→bugfix). This lands after the rename, so
write against the final slugs `todo`/`bugfix` throughout.

## Model

- Each verb gains a `category`: `action` | `investigation`. Genuine duals
  (e.g. `design`, `document`) carry both as a set.
- Each task type declares `accepts: [categories]`:
  - `todo`, `bugfix` → `[action]`
  - `research`, `brainstorm` → `[investigation]`
  - `epic` → exempt: the gate is skipped entirely (epics are containers, never
    title-verb-gated; preserves the ED-1511 exemption).
- Validity(verb, type) = `type.accepts ∩ verb.category ≠ ∅`.

## Creation gate

- At task create, block when the title's lead verb carries no category the
  task's `--type` accepts. Error names the verb, its category, and the type's
  accepted categories.
- Also enforced on `task update`: when `--title` or `--type` is being changed,
  re-gate the effective (title, type). Closes the create-as-`todo`-then-flip-to-
  `research` bypass, which would otherwise strand a task in an un-terminable
  state (an action-verb title under an investigation type: research forbids
  `confirmed`/`assumed`/`unverified` and the completed-gate rejects the action
  verb). Fires only on an explicit title/type edit, so an unrelated update to a
  pre-existing invalid row is not retroactively blocked.
- No `--justification` bypass — give a genuinely dual verb both categories
  rather than an escape hatch (bypasses get taken).
- This replaces `is_completable_verb` / `_require_completable_verb_for_completed`.

## Migration — mechanical, NO ledger upcasting

`.endless/verbs.jsonl` is a resolved cache read directly; there is no `verb.*`
event kind, so it is NOT the WAL. The schema change is a file/reader rewrite,
not an upcast.

Note the resolution order stated here as "project > machine > defaults" is
aspirational, not what `_resolved_verbs` does today — it returns the FIRST
source that is non-empty rather than layering them. See "Resolver fix" below;
that must be corrected as part of this task.

- Every current `completable:true` verb → `category:[investigation]`; every
  other verb → `category:[action]`.
- Then hand-audit the duals (`design`, `document`, …) and give them both
  categories. Selection test for a verb's category: does a task led by it
  deliver knowledge/findings/a decision (→ investigation) or changed
  behavior/an artifact (→ action)?
- Rewrite `.endless/verbs.jsonl` and `DEFAULT_VERBS` in matchers.py to the new
  schema; drop the `completable` field.

## Resolver fix — absorbed from E-2079

`matchers._resolved_verbs()` returns the first non-empty source (project, else
machine, else `DEFAULT_VERBS`) instead of layering them. Auto-registration
(`add_verb`, reached from `validate_title` when haiku confirms an unknown lead
word is a verb) writes `{value, definition}` into the project's
`.endless/verbs.jsonl`, creating it if absent. So on a fresh tracked project the
FIRST auto-registered verb produces a one-entry file that shadows all 78
defaults.

This is why it belongs to this task rather than standing alone: today the
shadow only reaches `is_completable_verb`, so the damage is a task stuck at
completion time. This task moves the gate to creation time, which turns the same
shadow into a front-door lockout. Verified by replaying this branch's
`verb_categories()` and `_require_verb_category_for_type` against a simulated
fresh project:

    --- fresh project, before any auto-registration ---
      verb_categories('research') = {'investigation'}
      verb_categories('audit')    = {'investigation'}

    --- after ONE auto-registered verb ('anchor') ---
      project verbs.jsonl holds 1 entry
      verb_categories('research') = {'action'}
      verb_categories('audit')    = {'action'}

    --- creation gate on that fresh project ---
      task add 'Research how sessions expire' --type research
         -> REFUSED: Title verb 'research' is an action verb, but a
            'research' task accepts only investigation verbs.

The refusal message is also false on its face — it reports `research` as an
action verb — so a new user has no path from the error to the cause.

Fix: make `_resolved_verbs()` layer the sources instead of picking one.
Concatenate project + machine + `DEFAULT_VERBS` and take the first entry per
`value` (case-insensitively), which is the semantics `load_all_verbs()` one
function above already uses for project + machine. Two open points for whoever
picks this up:

- Whether a higher layer overrides a whole entry or only the fields it
  specifies. Field-wise merge matters if a verb that is already a default ever
  reaches auto-registration — possible, because `_ensure_default_seeds()` only
  writes the machine file when it does not exist, so a default added after a
  machine was seeded is invisible there and would be auto-registered
  category-less into both files. Whole-entry override would then cement it as
  `action` permanently. Mike has not chosen; do not assume.
- Whether `load_all_verbs()` should fold into the same resolver so there is one
  resolution path rather than two. It would be a no-op on a seeded machine.

Not in scope here: adding a mechanism that refreshes an already-seeded machine
`verbs.jsonl` when `DEFAULT_VERBS` gains entries. That gap is real but separate;
file it rather than widening this task.
