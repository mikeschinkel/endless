# Spawned session's `active_task_id` ends up NULL → `tmux status-line` shows "claim a task"

## Symptom
A spawned worker session's tmux window shows `tmux status-line` = "claim a task"
(the `PaneStatusNoTask` hint), even though the task is spawned, the worktree
exists, and the session is actively working it. `esu` still works.

Concrete case: E-1699 spawned into window `@141` (pane `%308`), session **845**.

## Confirmed facts (live main DB + code)
- In **main**, session 845 (pane `%308`, uuid `906e5f2f`, state `needs_input`,
  kind tmux) has `active_task_id` = **NULL** — a single clean row, no duplicates.
- The window markers are all correct: `@endless_spawned_by=835`,
  `@endless_task_id=1699`.
- `tmux status-line` → `GetActiveTaskForPane` keys strictly on
  `sessions.active_task_id` (`internal/monitor/tmux_lookup.go:104`); NULL →
  "claim a task". `esu` resolves via the session→worktree mapping + `session_tasks`
  (the `845→1699` link exists), so it works — hence the split.
- **Not sandbox-vs-main:** everything is in main; the association is in main.
- **Not a general spawn-bind failure:** sibling spawned sessions are correctly
  bound — 844→1695 and 843→1698 both carry their `active_task_id`. 845 is the lone
  outlier.
- There is **no `task.claimed` event** for 1699. Spawn only emits
  `task.status_changed → underway` (under the coordinator session 835). The
  session↔task `active_task_id` binding is done hook-side, not by a claim event.
- The `session_tasks 845→1699` link is relation=**revisit** (created when 845 set
  the task to `unverified`), never a **goal/claim**.

## Mechanisms in play (code)
- `active_task_id` is **set** by `monitor.BindSessionToTask` (session.go:53), called
  from the SessionStart hook's spawn-auto-bind (`hookcmd/claude.go:210`) and the
  cwd fallback `autoBindFromCwd` (claude.go:238).
- `active_task_id` is **cleared to NULL** by `monitor.StartChatSession`
  (session.go:125-133) on a "chat takeover."

## Two candidate root causes (fix-owner to disambiguate via the hook trace)
1. **Bound-then-cleared:** 845 was bound at start (active_task_id=1699), then a
   later hook event classified it as a chat takeover and ran `StartChatSession`,
   which upserts `active_task_id=NULL`. The `StartChatSession` conflict-clause
   unconditionally nulls the column, so a mis-fire of chat detection on a
   task-bound session would wipe its binding. (844/843 didn't hit it.)
2. **Never-bound race:** the SessionStart spawn-auto-bind ran before the tmux
   markers / worktree companion were readable (empty `TMUX_PANE` at hook time),
   both `BindSessionToTask` and `autoBindFromCwd` no-op'd, and no later event
   re-bound. 845 lost a race its siblings won.

Distinguish by pulling session 845's hook execution trace (did `StartChatSession`
run after a successful bind, or did the bind never run?).

## Fix direction (depends on which cause)
- If (1): `StartChatSession` must not clear `active_task_id` for a session that
  already has a task bound (only genuine chat-only sessions should be NULL); or
  chat detection must not fire for a spawned/task-bound session. (The lifecycle
  test at `session_lifecycle_test.go` around "chat takeover didn't clear" suggests
  this guard is intended — verify it covers the spawn path.)
- If (2): the spawn-bind needs to be race-proof — re-bind on a later hook event
  (PreToolUse/UserPromptSubmit) when the pane/markers become readable and
  `active_task_id` is still NULL for a session whose window carries
  `@endless_task_id`.

## Verify
Spawn a task, let the worker run and finish (task → unverified), then check
`sessions.active_task_id` for the worker's row and `tmux status-line` in its
window — both should still reflect the task until the session actually ends.
