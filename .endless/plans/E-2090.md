# Plan — prepend a shared guard to every existing verify suite

Blocked by E-2023, which relocates the suites to `.endless/tasks/e-NNNN/verify.sh`,
adds the runner marker, and creates `_harness.sh`. This task is deliberately
separate so a ~200-file CONTENT edit is reviewable and revertible independently
of E-2023's ~200-file MOVE. Doing both in one task would make a bisect unable to
tell a relocation problem from a guard problem.

## 1. `_guard.sh` — one file, two callers

`.endless/tasks/_guard.sh`, sourced (not executed), refusing in two cases:

- **No runner marker.** The suite was started directly rather than through
  `just verify` / `endless task verify`. Refuse, naming `just verify E-<id>`.
- **The caller may not run this suite.** Landed, and not this session's active
  task — the rule from E-2023 and E-1916.

`_harness.sh` sources `_guard.sh` as its first act, so a suite using the shared
harness gets the guard transitively and nobody has to remember both lines.

### The landed/active test must not be re-derived here

The guard checking landed-ness itself is the point of this task — a suite should
refuse on its own merits however it was started. But bash re-deriving "landed AND
not active" would be the same rule implemented a second time, and two
implementations drift.

So expose the DECISION, not its inputs: a single command that answers "may this
session run task N's suite?" with an exit code and a one-line reason. The runner
calls it; `_guard.sh` calls it. One implementation of the rule, two call sites.
E-1916's plan already names `session-query task-report --id N` as the landed-ness
source; this is a thin verb over that plus the active-task comparison, and it
belongs beside it rather than in either caller.

Without this the task still works and is still worth doing — it just reintroduces
the drift E-2023 was careful to remove.

## 2. The prepend

One line at the top of every existing suite script, before anything else runs —
in particular before any `cd`, since the guard locates itself relative to the
script.

- Mechanically uniform, so the sweep is scriptable and the result greppable:
  every suite either has the exact line or is a finding.
- Idempotent: re-running the sweep must not add a second copy.
- Not an edit in the sense the guide forbids. That rule governs ordinary work,
  not an explicit restructuring of the suites themselves, which is what E-2023
  and this task are. No assertion, fixture, or message is touched.

Suites that already source `_harness.sh` (E-2023's exemplars) get the guard
transitively and must NOT also get the direct line — one path in, or the refusal
message doubles.

## 3. Locating the guard

The suite must find `_guard.sh` before it has done anything, from any invocation
spelling (`./x`, `bash x`, `sh x`, an absolute path). Settle one mechanism and
use it everywhere rather than per-script cleverness; whatever is chosen has to
survive a suite being run with a cwd other than its own directory, which several
existing suites do deliberately.

## Boundaries

- Does NOT convert suites to use `_harness.sh`'s assertion helpers (ED-1534).
  This is a prepend, not a port.
- Does NOT change any suite's behaviour when it is invoked correctly. A suite run
  through the runner by the session that owns it must produce byte-identical
  output to before, which is the main regression risk and the main thing to test.
- Does NOT retire E-1916's Arm 2. That arm is retained deliberately as a backstop
  for the cases an in-file guard cannot cover: a suite from a checkout predating
  the guard, and one hand-authored without it.

## Verify

1. Every suite script carries the guard exactly once — directly, or transitively
   via `_harness.sh`, never both.
2. Running a suite through the runner as the session that owns it succeeds, and
   its output is byte-identical to the same suite before the prepend.
3. Running a suite directly refuses, names `just verify E-<id>`, and exits
   non-zero — for a suite that sources the guard directly and for one that gets
   it through `_harness.sh`.
4. A landed, non-active task's suite refuses even WITH the marker set, proving
   the second check is real and not decoration.
5. The task's own reopened suite still runs: landed, reopened, re-claimed,
   verified from its own worktree. Same regression E-2023 guards against.
6. The decision command has exactly one implementation: neither the runner nor
   `_guard.sh` contains its own landed-or-active comparison.
7. Re-running the prepend sweep is a no-op.
