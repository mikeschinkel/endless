# Plan — E-2023: one front door for verify suites

Governed by ED-1534 (verify suites are land-time tests; mass-porting them to
`verify.toml` is not pragmatic). Complementary to E-1916, which enforces the same
rule at the PreToolUse hook; this task enforces it at the runner, where the task
id is known for certain rather than parsed out of a command string.

## What this task became, and why

Filed as "add a guard inside each script". That is no longer the shape. Three
things moved:

- **A runner already exists and already isolates.** `endless task verify <id>`
  runs a per-run temp `HOME` + `XDG_CONFIG_HOME` (internal/verifycmd/env.go).
  Because Go's `PinMainDB` resolves through `os.UserHomeDir`, even a script that
  drives the hook binary writes into the temp home rather than the real database.
  That is containment an in-script guard cannot provide.
- **The runner knows the id.** Own-task-only becomes structural. A command-string
  predicate cannot extract an id from a glob loop over the script directory, and
  that exact shape is what caused the E-2071 incident.
- **ED-1534 forbids the bulk retrofit** an in-script guard would have required
  across ~200 landed scripts — which the guide separately forbids editing.

The rule is unchanged. The enforcement point moved from 200 places to one.

## 1. Move the scripts beside the manifests

`tests/tasks/e-<id>-verify.sh` becomes `.endless/tasks/e-<id>/verify.sh`.

Two reasons, and the second is why this belongs in THIS task rather than a later
one:

- `tests/` is too strong a signal. It reads as a suite you maintain and re-run,
  which is what makes `just test`, a glob, or "run the tests before handing off"
  reach them. A land-time artifact does not belong beside a regression suite.
- One directory per task, holding whichever form that task uses. `verify.Discover`
  already walks `.endless/tasks/<id>/`, so the script fallback below becomes
  "same directory, other filename" instead of a second search path — and a task
  that later grows a manifest keeps its script beside it rather than across the
  repo.

`git mv` per script so history follows. Directory ids are lowercase by
convention but `verify.NormalizeTaskID` already compares normalized, so either
casing resolves — do not add a second casing rule here.

`_harness.sh` (section 3) lands at `.endless/tasks/_harness.sh`. Discovery
iterates directory entries looking for per-task dirs, so a plain file alongside
them is skipped; add a test pinning that rather than relying on it.

Update the live references: the guide, the justfile, and the pytest files that
name the old path.

E-1916's plan carries a predicate table naming the old path. It is not amended
here — a plan records what was true when it was written, and rewriting another
task's plan to match work that has not landed puts a claim in it that nothing
verifies. Whichever of the two lands second reconciles against the tree it finds.
Worth knowing when E-1916 is picked up: this move SIMPLIFIES it, because both
suite forms end up under the single `.endless/tasks/<id>/` segment its predicate
already keys on. Its carve-out for `.endless/verify.toml` at the project root is
unaffected.

## 2. The runner falls back to the script

`internal/verifycmd.run` currently fails when `verify.Discover` finds no manifest:

    endless-go verify: no verification suite found for task

Add a fallback ahead of that error: if the task's directory holds `verify.sh`,
run it as a single raw check under the same isolation the manifest path uses, and
normalize its output the same way. Only when the directory holds neither does the
error stand — naming both filenames it looked for.

Both filenames are product-controlled constants beside `verify.SuitesDir`, not
literals at the call site, so a downstream project laying suites out differently
is a config change rather than a fork.

## 3. The refusal, and the marker

Before running anything, refuse when the requested task is **landed AND is not
this session's active task** — E-1916's predicate exactly, reusing the same
`session-query task-report --id N` `landed` bool rather than inventing a second
notion of landed-ness. One rule, two enforcement points, no divergence: a session
must never get different answers from `just verify` and the hook.

Bare `endless task verify` with no id resolves to the session's own active task
(src/endless/verify_cmd.py already does this) and is always allowed — that is the
pre-land gate doing its job.

**A task may always verify itself again, landed or not.** The conjunction is what
makes this work: a task that landed and was then reopened is the claiming
session's ACTIVE task, so `not active` is false and the refusal does not fire.
Re-verifying and re-landing your own reopened work is the documented path when
shipped work turns out wrong (`endless guide orchestration`: "Re-verify with the
suite that already exists"), and E-2071 exercised exactly that — landed, reopened
to `revisit`, extended, landed again. Nothing here may narrow that. A predicate
keyed on landed-ness ALONE would break it, which is the reason for the second
conjunct, not an incidental detail of E-1916's wording.

The refusal names what to do instead rather than only saying no, and says why a
landed suite's result is meaningless (ED-1534: its fixtures were pinned to that
task's moment).

Then, absorbed from E-1623's half 1 (declined in favour of this task):

- Extract the duplicated `report_*`/`assert_*`/`section`/`summary` block into
  `_harness.sh`, emitting TAP so a sourcing script's assertions are normalizable
  with no rewrite. This is E-1623's design, unchanged.
- The runner exports a marker into the suite's environment. `_harness.sh` refuses
  when the marker is absent, so running a script directly exits non-zero with a
  message naming `just verify E-<id>`.
- The marker is set by the runner only. It is NOT documented as a user-settable
  escape: an override an agent can set is an override an agent can rationalize,
  which is the failure this task exists to stop.

Per ED-1534 the existing scripts are NOT bulk-retrofitted to source the lib. New
scripts source it, plus a few converted exemplars to prove it. **Stated
limitation:** a script that does not source the lib stays directly runnable, and
for those the only guard is E-1916's hook. That is a deliberate boundary, not an
oversight — recorded so nobody reads "refused unless run through the runner" as
universal.

## 4. `.endless/tasks/CLAUDE.md` — the reasoning, at the point of contact

A directory-level CLAUDE.md stating the rules for suites in that tree: land-time
gate not regression suite, do not run another task's, do not edit a landed one,
bit-rot is expected (ED-1534), coverage that must survive belongs in the
project's own suite, and `just verify E-<id>` is how you run one.

Its job is to be the explanation the refusal points at — an agent working in that
directory meets the reasoning before it acts, instead of having to go find it in
`endless guide orchestration`. Refusals in section 3 should reference it by path
so the "why" is one read away from the "no".

**It ships with every project.** `register_project` (behind both `project init`
and `project register`) already scaffolds `.gitignore`, `.endless/tmp/` and the
output style; the file joins that list, written idempotently the same way, so a
newly-registered project has the rules in place before it has any suites. A file
that exists only in this repo would teach nobody.

It is explicitly NOT counted as a defense. It is prose, and prose is the layer
this task's own description records as having failed — read, understood,
paraphrased into "not required", and broken. It also only reaches Claude Code
(E-1962), so it does nothing for a downstream project on another harness. The
enforcement is the runner refusal and E-1916's hook; this file explains them.

## 5. Documentation

`docs/guide/orchestration.md` "One suite per task" and "The one-command handoff
contract" both name direct invocation of the old path. Change the handoff to:

    just verify

This is the point of routing through the runner: the command a session hands back
is identical whether the suite is a script today or a manifest later, so the
handoff contract never needs rewriting again.

### `just verify [E-NNNN]` resolves its id the way `just land` does

The id is accepted but not required, using `just land`'s existing chain so the
two verbs behave alike and neither needs explaining twice:

1. an explicit argument;
2. else `endless-go tmux active-id`, the DB-backed source, which works from any
   cwd as long as the pane's session holds a task;
3. else the cwd path pattern for a task worktree, the cheap fallback outside
   tmux;
4. else a usage error naming `just verify [E-NNNN]`.

Echo the derived id, as `land` does — a verb that picks a target silently is the
same class of problem as a listing that truncates silently.

Today's recipe forwards an empty argument and lets the Python wrapper fall back
to the session's active task. That covers case 2 only: it has no cwd fallback and
says nothing about what it chose. Move the resolution into the recipe so the
chain is shared with `land` rather than a second, thinner one.

The recipe does what `esu` was doing by hand. Having resolved the task it cds
into that task's worktree and runs the suite through the WORKTREE's endless, so a
pre-land gate exercises candidate code rather than main's — the reason `esu` was
in the handoff at all. It does not need to export anything into the caller's
shell, which is the only part of `esu` a recipe cannot do and the only part this
does not need. So the documented handoff is one word:

    just verify

with the explicit `just verify E-NNNN` reserved for running a suite from
somewhere else.

**Scope note (Mike, at planning time):** `just` is the endless-dev ergonomic
wrapper, not the product surface — a downstream project has no justfile. The
shipped verb is `endless task verify`, and everything in sections 2 through 4
lives there; the recipe only resolves an id and picks a directory. Making the
product's own runner sufficient for a downstream user is deliberately deferred
until there are users to shape it around, and is NOT in this task.

Also correct the guide's claim that a suite "builds its own isolated environment"
— under the runner that is now provided, and a suite that additionally builds its
own is belt-and-braces rather than the requirement.

## Boundaries

- Does NOT port scripts to `verify.toml` (ED-1534). The move is a relocation and
  a rename, not a conversion.
- Does NOT bulk-retrofit the existing scripts to source `_harness.sh` (ED-1534).
  The guide's "don't edit a landed suite" rule is not the reason: that rule
  governs ordinary work, not an explicit restructuring of the suites themselves,
  which is what this task is. The reason is ED-1534's — churn with little value
  across ~200 land-time artifacts.
- Does NOT implement E-1916's hook. That task stands; this one does not block it
  and is not blocked by it. Either alone is an improvement; together the hook
  refuses early with a teachable message and the runner refuses structurally.
- Does NOT perform E-1623's land-time-corpus audit. E-1623 is declined: buckets
  1a and 2 were conversion scaffolding and die with the port, and buckets 1b/3
  do not justify reading 200 scripts on their own. A specific coverage gap gets
  filed on its own evidence when it surfaces.

## Risks worth naming

**Isolation changes behaviour.** Running an existing script under the runner's
isolation means `--db main` inside it resolves to the temp home's empty database.
Any script that silently depended on the real database will behave differently.
That dependency already violates the documented contract (a suite "never touches
your real config or the main database"), so a break is a finding, not a
regression — but pick the exemplar conversions to surface it early rather than
late.

**The move is the largest mechanical step.** ~200 `git mv`s plus a directory per
task. Do it as its own commit, separate from the runner change, so a bisect can
tell a relocation problem from a behaviour problem.

## PRODUCT

Nothing here is Endless-specific. Any project using Endless accumulates per-task
suites that look like a regression suite and rot. The layout, the front door, the
refusal and the marker all belong in shipped scaffolding, and the
worktree-to-task lookup is the same call in `self_dev` and downstream modes. The
CLAUDE.md is the one piece that does not travel — a downstream project on another
harness still gets the refusal, just not the explanation in that form.

## Verify — `.endless/tasks/e-2023/verify.sh`

1. Fail-fast unit gate: the Go tests this task adds to `internal/verifycmd` and
   `internal/verify`.
2. Every script moved: nothing remains under the old path, each task directory
   holds its `verify.sh`, and `git log --follow` on a sample still reaches its
   pre-move history.
3. A task with a manifest still verifies exactly as before (no regression on
   E-1603 / E-1758), and a task holding BOTH forms resolves deterministically to
   the documented one.
4. A task with only a script verifies through `just verify E-<id>`, and its
   pass/fail and exit code match running that script directly before the move.
5. A task with neither names BOTH filenames in its error.
6. The refusal fires: a landed, non-active task's suite is refused with non-zero
   exit, whichever form it takes; the session's own active task is not refused;
   bare `endless task verify` is not refused.
7. The marker works: an exemplar sourcing `_harness.sh` passes under the runner
   and refuses a bare direct run, naming `just verify`.
8. The glob shape that caused E-2071 is unreachable: iterating the suite
   directory and executing what it finds refuses at the first landed foreign
   suite.
9. `_harness.sh` sitting beside the per-task directories does not confuse
   discovery, and is not itself discoverable as a task.
10. `_harness.sh` emits TAP, and a converted exemplar's pass/fail is identical
    before and after conversion.
11. `.endless/tasks/CLAUDE.md` exists and the refusal messages reference it.
12. `just verify` with no argument resolves the same task `just land` would from
    the same shell, echoes what it derived, runs from inside that task's
    worktree against the worktree's own endless, and errors with a usage line
    when neither the session nor the cwd yields one.
13. THE REGRESSION THIS MUST NEVER CAUSE: a task that has landed, been reopened,
    and re-claimed verifies successfully from its own worktree — by id and with
    no id. A predicate that refuses it is wrong however elegant.
14. A freshly registered project has `.endless/tasks/CLAUDE.md` on disk, and
    re-running registration neither duplicates nor overwrites a customized one.
