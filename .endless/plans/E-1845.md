# E-1845 — Add `unevaluated` status upstream of `unplanned`

Prerequisite for E-1859 (the description-sufficiency evaluator). Ships FIRST:
the evaluator has nothing to route until this status exists.

`tasks.status` is plain TEXT validated in application code (schema.sql carries
no CHECK constraints and there is no status enum table), so this is a code +
docs change with **no migration and no backfill**. Existing rows keep their
current status; only newly filed tasks start at `unevaluated`.

## Decisions settled before implementation

**1. No shipping deadlock — the manual route is the duplicated slice.**

Shipped alone, `task add` defaulting to `unevaluated` would strand every new
task: `_SUBMITTABLE_FROM = ("unplanned", "revisit")` rejects it, and the
evaluator that would route it is blocked on this task.

Fix: add `unevaluated` to `_SUBMITTABLE_FROM` here, so a human can route with
`endless task submit`. E-1859 later adds the automatic path that writes the same
transition. The one-line overlap is deliberate, and the manual path is
permanently useful as the human override — it is not scaffolding to remove.

`task add` therefore flips its default in THIS task; nothing is deferred.

**2. Description-edit reset fires from pre-work statuses only, on a material
change.**

| Fires from | Never fires from |
|---|---|
| `unevaluated`, `unplanned`, `submitted`, `ready`, `revisit` | `underway`, `unverified`, `confirmed`, `assumed`, `completed`, `declined`, `obsolete` |

Guards, mirroring E-1762's auto-revisit:

- An identical rewrite is a no-op — only a REAL change resets.
- `--keep-status` suppresses it, for typo/formatting edits.
- Excludes `underway` specifically so a description tweak cannot yank work out
  from under a live session.

`ready` IS included: approval was granted against the old description, so a
material rewrite should require re-approval. `--keep-status` covers the case
where the author knows the edit is cosmetic.

## Verification — `tests/tasks/e-1845-verify.sh`

Fail-fast, folding the task's own tests in as check 1.

1. Python + Go unit tests for the new behavior.
2. `task add` with no `--status` lands in `unevaluated`; with `--tier 1` still
   lands in `ready`; with an explicit `--status` honors it.
3. **No deadlock**: a freshly added task can be moved out by `task submit`
   alone, with no evaluator present. This is the check that would have caught
   the shipping trap.
4. Description-edit reset: fires from each of the five pre-work statuses;
   does NOT fire from `underway`, `unverified`, or any terminal status; an
   identical rewrite no-ops; `--keep-status` suppresses.
5. `unevaluated` renders in `session status` with its own glyph and is NOT
   labeled "plan" — and, critically, is not the ⁇ unknown glyph.
6. `task next` does not offer an `unevaluated` task as actionable work.
7. An `unevaluated` task still blocks its dependents.
8. Canonical lifecycle: the three mermaid copies match, and the prose status
   table lists `unevaluated`.
9. `endless guide` renders the updated lifecycle and table.
