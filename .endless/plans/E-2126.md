# Return populated field bodies from `task show --json`, and surface children

## The defect

`endless task show <id> --json` returns `"analysis": null` for a field holding
6503 characters. The display flags that gate the human renderer (`--analysis`,
`--text`, `--outcome`, `--all-fields`, `--no-description`) also gate the JSON
payload.

This was deliberate: E-1601's description says to apply the placeholder
treatment "consistently across human, `--llm`, and `--json` output", and it was
confirmed. This task revisits that for the machine format only.

Two things are wrong with it:

1. **A machine format withholds content by default.** A consumer that does not
   know to pass a display flag reads a populated task as an empty one. The
   terminal at least prints `Analysis: 6503 chars (--analysis to display)`;
   JSON prints nothing.

2. **`null` carries two meanings.** For `analysis`, `text` and `outcome` a
   consumer can disambiguate via the `_chars` sibling (populated when withheld,
   null when empty) — but only by knowing an undocumented convention. For
   `description` there is no `description_chars` key at all, so under
   `--no-description` withheld and empty are indistinguishable.

## Decided (with Mike, 2026-09-08)

- `--json` returns full bodies by default. Display flags stop affecting it.
- `--brief` opts into a light payload by **truncating, not omitting**. A
  populated field is always a string; a truncated one ends in `…`.
- **`null` acquires exactly one meaning: the field is empty** — in every format,
  under every flag combination. This is the fix; everything else is delivery.
- Truncation default is **256 characters**, overridable as `--brief=N`.
- The count keys keep the name `<field>_chars`, not `<field>_size`. `size`
  conventionally implies bytes; these count CHARACTERS, and this tree's content
  is full of multi-byte punctuation, so `_size` would invite a consumer to
  assume a number that is wrong for most tasks here. `_chars` also shares its
  unit with `--brief=N`, which counts characters — the two names reinforce each
  other. Keeping the existing name additionally costs no churn.
- A count key is **always an integer, `0` when its content field is empty** —
  never null. A nullable count forces every consumer to null-check before
  comparing or summing, and it would spend `null` on a second meaning inside
  the very change whose purpose is to give `null` exactly one.
- `--llm`'s default is unchanged (counts only). `--brief` works there too,
  upgrading a bare count to a readable preview.
- Children are always advertised as a count, and the full list stays gated
  behind `--children`. This makes children consistent with the `_chars` pattern
  rather than an exception to it.

Truncation beats omission because omission keeps `null` doing double duty and
merely moves the ambiguity behind an opt-in flag. Truncation makes the type
stable and gives a consumer the gist of a field, which a char count cannot.

## Deliverable 1 — `--json` stops consulting the display flags

In the JSON branch of `task show` (search `task_cmd.py` for the dict literal
containing `"analysis_chars"`), the four body fields are built as
`item[f] if show_f else None`. They become `item[f]` unconditionally.

## Deliverable 2 — `--brief[=N]`

A new flag on `task show`. Truncates every long field to a preview. Applies to
human, `--llm` and `--json` alike: one flag, one meaning — previews, not bodies.

- Default length 256 characters. `--brief=N` overrides.
- Truncation counts characters, not lines, and appends a single `…`. In JSON,
  truncate the decoded string before serializing so no escape sequence is split.
- A field shorter than the limit renders whole with no ellipsis, so the absence
  of `…` reliably means "not truncated".
- `--brief` wins over the display flags. `--all-fields --brief` yields previews.
  One rule, no per-format exception; state it in the flag's help text.
- `--brief` does not affect children. They are short rows, not a long field.

## Deliverable 3 — `_chars` keys become universal

They stay, and gain a `description_chars` companion, because under `--brief`
they are the only way to know the true length behind a preview.

Uniform rule: `<field>_chars` is the true character count of the stored value,
present for all four body fields, always an integer, and `0` when the field is
empty. It is never null.

The resulting invariant, which the tests pin: `<field>_chars == 0` if and only
if `<field>` is `null`. A consumer can branch on either one and get the same
answer, and needs no null-check to do arithmetic on a count.

## Deliverable 4 — one spelling of absent

The same task can report `text` as `""` and `outcome` as `null` because the
column values differ; to a consumer both mean "no content". Normalize empty to
`null` for all four body fields in the JSON payload, with `<field>_chars` set to
`0` alongside.

So `null` appears on body fields only, and only for empty. Counts never carry
it.

## Deliverable 5 — children before the long fields, and always counted

Two changes to the human renderer, plus their machine equivalents.

### 5a. A `Children:` line in the header block

Rendered beside the existing `Analysis:` / `Text:` / `Outcome:` placeholders,
immediately after `Outcome:`. Sourced from one grouped query
(`SELECT type, COUNT(*) ... WHERE parent_id = ? GROUP BY type`).

Format:

- No children — omit the line entirely, matching how the other placeholders
  behave when their field is empty.
- All children share one type: `Children: 3 todo`
- Mixed types: `Children: 5 tasks (3 todo, 2 bugfix)`

Breakdown order is descending count, ties broken alphabetically by type, so the
dominant kind reads first and the rendering is deterministic.

### 5b. The `— Children —` section moves earlier

The detail renderer emits a fixed sequence of multi-line sections. Children are
last today. The sequence becomes:

    1. Description
    2. Children      <- moved here
    3. Analysis
    4. Text
    5. Outcome

**Children occupy slot 2 — the position Analysis would occupy if it rendered —
whether or not Analysis, Description, Text or Outcome actually render.**

State it as slots rather than as "before Analysis" or "after Description"
because EVERY section in that list is conditional: each large field renders only
when its display flag is set and its content is non-empty, and Description is
additionally suppressed by `--no-description` and skipped when it merely repeats
the title. Naming a neighbour would make the spec depend on whether that
neighbour exists, which is exactly the ambiguity this wording removes. The
implementor needs no knowledge of which neighbours are present.

Rationale for the move: children are structure, and the flag-gated long prose
goes last where it cannot push the structure off-screen. `(none)` still renders
when `--children` is passed and there are none — the user asked a direct
question and gets a direct answer.

### 5c. Machine formats

- `--json`: `children_count` (integer, always present, `0` when none) and
  `children_by_type` (object, always present, `{}` when none). The `children`
  array remains gated behind `--children`.
- `--llm`: `children_count=5` and `children_by_type=todo:3,bugfix:2`, emitted
  only when the count is non-zero, matching how `analysis_chars=` behaves.

This costs one grouped query per task rendered. That is accepted: it is indexed
on `parent_id`, bounded, and it is what makes the count available without
fetching every child row.

## What must not change

- The human renderer's default body output. The placeholder line
  (`Analysis: NNNN chars (--analysis to display)`) is what a person reads, and
  E-1601 built it deliberately. `--brief` adds a mode; it replaces nothing.
- `--llm`'s default output, beyond the new children lines.
- The display flags' behavior in human and `--llm` output.

## Verification

- `task show <id> --json` on a task with a populated analysis returns the body
  with no flags passed. This is the reported defect; assert it directly.
- `task show <id> --json --brief` returns a truncated string ending in `…`,
  never null, with `analysis_chars` reporting the untruncated length.
- `--brief=N` honours N; a field shorter than N carries no ellipsis.
- A task with a genuinely empty field returns `null` for it and `0` for its
  `_chars`, under every combination of `--brief`, `--all-fields` and the display
  flags. Assert the biconditional directly — `<field>_chars == 0` if and only if
  `<field>` is `null` — as a matrix, not a single case. This is what makes
  `null` unambiguous.
- No `_chars` key is ever null, on any task, under any flags.
- `--no-description --json` no longer loses the description, and
  `description_chars` is present.
- `--llm` with no flags is byte-identical to before the change except for the
  new children lines. Pin this; it is the regression most likely to go unseen.
- The `— Children —` section renders in slot 2 across the full presence matrix:
  Description present or absent (`--no-description`, and a description equal to
  the title) crossed with Analysis present or absent (flag unset, and flag set
  with an empty field). Children must land in the same relative position in all
  of them, including the case where Children is the ONLY section that renders.
- The `Children:` header line renders in all three shapes (single-type, mixed,
  absent) and `children_count` is `0` rather than missing on a childless task.

## Blast radius

No in-repo consumer reads these keys — a search for `_chars` across `src`,
`internal` and `cmd` finds only the producer. The consumers are agents and
external tooling, so the change is additive for anyone already passing display
flags, and a fix for anyone who was not.
