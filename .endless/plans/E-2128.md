# Plan — one writer computes the unlanded verdict, every reader reads it

This task conforms to decision ED-1589. Defers the patch-id index to E-2127 and
both worktree-sync directions to E-1881.

## The decision

The exact "does this branch hold work the base lacks?" verdict stops being
computed by its consumers and becomes **derived state owned by one background
job** (ED-1589). Consumers read a per-repo file cache. The reaper comes off the
PreToolUse/PostToolUse hook path entirely and becomes a job of its own.

This is one change, not two, because the reaper's periodic-sweep cost and the
monitor's continuous fan-out are the same defect: *the verdict is recomputed
from scratch by every consumer on every tick, with no shared derived state.*
Under ED-1550 §3 that is one cause, so it is one task.

## The invariant this rests on, and how it is checked rather than trusted

The unlanded set can only SHRINK as the base branch gains commits. The probe
asks, for each branch commit since the fork, whether a matching commit exists on
base since the fork. Adding commits to base only adds candidates to match
against: a commit that already matched keeps its match, and one that did not may
acquire one. Nothing that matched becomes unmatched.

Therefore:

- **A verdict of ZERO unlanded stays true as long as the BRANCH tip does not
  move**, no matter how far the base advances.
- **A verdict of N>0 is only valid while BOTH tips are unchanged**, because base
  movement can shrink it.

The invariant assumes the base is append-only. That assumption is CHECKED, not
trusted, by a repo-level watermark (below). An amended, reset, or force-pushed
base is detected and flushes the cache; a `--amend` on a task BRANCH moves the
branch tip and self-invalidates that one entry.

Two things the invariant deliberately does not cover, both pre-existing and
neither introduced here: work that landed and was later REVERTED still reads as
settled (the original landed commit is still in base's history to match
against), and uncommitted/untracked files are not commits at all — they are a
separate probe that stays live.

## The cache — content-addressed paths, no file format

**Location.** `<git-common-dir>/info/endless/unlanded/`

`git rev-parse --path-format=absolute --git-common-dir` from inside any linked
worktree resolves to the main checkout's `.git`, so every worktree of a repo
shares one cache directory for free. Verified on git 2.52.0. `.git/info/` is
untracked, never pushed, per-clone, and survives `git gc` — the correct home for
derived state describing this clone. No database, so sandbox routing does not
apply and the probe stays DB-free (the property `_unsettled_probe` documents:
`--db main` from inside a worktree and a bare run agree by construction).

**Layout. There is no file format — every key is a path, and the only file with
contents holds exactly the bytes a consumer needs.**

```
<git-common-dir>/info/endless/unlanded/
  base-<name>                                  # 41 bytes: last-verified base tip OID
  settled/<branch-tip-oid>                     # EMPTY file. presence = fully landed.
  unsettled/<base-tip-oid>/<branch-tip-oid>    # unlanded commit lines, one per line
```

Why each piece carries no fields:

- **`settled/<branch-tip-oid>` is empty.** "Fully landed" is a property of the
  branch-tip OID and the base branch ALONE — same HEAD and same base give the
  same answer whichever directory the probe ran in — and the invariant above says
  it is permanent while the base is append-only. There is nothing left to qualify
  it with. Two worktrees at one OID legitimately share an entry.
- **`unsettled/<base-tip-oid>/<branch-tip-oid>` nests under the base tip.** A
  non-zero verdict is valid only until the base moves; nesting makes base movement
  render the whole directory unreachable, so INVALIDATION IS A PATH MISS requiring
  zero logic and zero stored field. Its contents are the exact lines
  `parseUnlandedRows` already produces, bounded by the existing `unlandedLogLimit`;
  the count is the line count.
- **`base-<name>` holds one OID.** The base NAME is in the filename, so editing
  `default_branch` in `.endless/config.json` orphans the old watermark
  automatically and reads as full invalidation.

Deliberately absent, each removable without breaking a rule: a format version
(the cache is rebuildable derived state, so an unreadable file is simply a miss
and no migration can ever be needed), the worktree path, a per-entry base name,
a stored probe error (absence already means unknown, and unknown already fails
closed — a failed compute writes nothing), and a computed-at timestamp (no
validity rule reads one). Nothing here can drift out of sync with git, because
every key IS a git object id.

**Validity protocol**, run once per process, not per row:

1. One call to `git worktree list --porcelain` yields every worktree path, every
   worktree's HEAD OID, and the base branch's own tip. **Measured: 14ms for 135
   worktrees on this repo.** That is the entire enumeration and tip-reading step.
2. Read `base-<name>`. Absent, or the name has changed → treat every `settled/`
   entry as a miss (the job then rebuilds). Equal to the current base tip →
   proceed. Different → `git merge-base --is-ancestor <stored> <current>`:
   - exit 0 → base only appended. Every `settled/` entry stands. The job writes
     the new tip; readers never write it.
   - exit 1 → base history was rewritten (amend, reset, force-push). Every
     `settled/` entry is invalid; the job empties `settled/` and recomputes.
   - any other exit → fail closed: every lookup is a miss.
3. Per worktree, with HEAD `B` and current base tip `T`: `settled/B` exists →
   settled. Else `unsettled/T/B` exists → unsettled, and its lines are the log.
   Else → not yet determined.

**Writes.** An empty `settled/` marker is a create-or-nothing operation with no
partial state. An `unsettled/` file is written temp-then-rename in the same
directory. The job prunes `settled/` entries matching no current worktree HEAD
and removes every `unsettled/` directory that is not the current base tip.

**When the cache directory cannot be created or written** — a read-only checkout,
a permissions problem — every lookup is a permanent miss: displays show the
uncomputed marker and on-demand callers recompute each time. Correct, just not
fast. Record ONE fault fingerprinted on the directory so the condition is
visible, matching how `recordDefaultBranchFault` handles a resolver that will
never succeed; do not fault per worktree per pass.

## `runGit` takes a context — one signature, every call site

E-2113 landed the classification but not a context: `runGit` still builds its
child with `exec.Command`, and `killedBySIGINT` tags a SIGINT death as
`ErrGitInterrupted` so an interrupted probe is undetermined rather than an
incident. The pool needs cancellation, and `jobs.Job` requires `Run` to honour
the lease deadline its ctx carries.

`runGit` gains a `context.Context` as its first parameter and builds with
`exec.CommandContext`. No second entry point and no wrapper: a probe that cannot
be cancelled is the defect, so leaving a context-free door open just preserves
it for the next caller. It should have taken one from the start.

**The trap this must not walk into.** `exec.CommandContext` kills with SIGKILL
on cancellation, and E-2113 deliberately keeps SIGKILL faultable, because a
SIGKILL is usually the OOM killer and a probe large enough to be OOM-killed is a
real operational fact. Cancelling a lease would therefore record a fault per
in-flight worktree. So `runGit` checks `ctx.Err() != nil` after `Wait` and
classifies that death as `ErrGitInterrupted` — a second benign case alongside
SIGINT, rather than widening `killedBySIGINT` and losing the OOM signal it was
narrowed to keep.

With that, the job records probe faults exactly like every other caller. No
consecutive-failure counter: the noise it would have suppressed was E-2113's
bug, and E-2113 has landed.

## One job, plus the reap trigger that already exists

**`internal/unlandedjob`** — name `worktree-unlanded`. `Interval: 60s`,
`LeaseTTL: 15m`. Follows the existing `internal/backupjob` shape: own package,
`init()` registers, `Name`/`Schedule`/`Run`. It runs the validity protocol,
recomputes every invalid entry through the bounded pool, writes each marker,
advances the watermark, and prunes entries for worktrees git no longer lists.

It covers EVERY worktree git lists, ordered by the worktree directory's mtime,
newest first. Ordering matters more than scope: the cache converges on the
worktrees someone has actually been working in within the first seconds of a
cold pass, and the long tail of dormant directories fills in behind them without
anyone waiting on it. Directory mtime is one `stat` per worktree and reads no
database, which keeps the probe DB-free — the property E-2087 established and
`_unsettled_probe` documents. It is a slightly noisy signal (any write touches
it, including a build artifact) and that is acceptable for an ordering heuristic
that affects nothing but warm-up order.

A cold pass over 135 worktrees is ~10-20s through the pool; a warm pass is one
14ms git call plus N path lookups. The lease exceeds the cold case comfortably.

`MaxBackoff` is zero, matching `backupjob`'s rationale: failures here are cheap
and idempotent, and backing off would leave the cache stale exactly when the
probe path is known to be sick. The runner's recorded fault is the alarm.

It is triggered by the existing `liveview` job runner, which already fires
`jobs.RunDue` on each monitor refresh behind a single-in-flight guard and a
database lease. Nothing new is wired.

**The reaper gets no job and no new trigger.** It already runs where it should:
`worktree_cmd.land_worktree` calls `_reap_stale_worktrees(main_root)` as a
post-land best-effort sweep, shelling to `endless-go event reap-worktrees` with
stderr forwarded so reaped directories are printed to the person who ran the
land. That is the right moment and the right visibility — a land is what makes
other worktrees reclaimable, and the person who caused the reclamation sees what
was reclaimed. This task neither moves it nor adds a cadence to it.

What DOES change in the reaper: `maybeReapWorktree`'s condition 4 reads the
cache in COMPUTE-ON-MISS mode instead of running `reapNothingToLand`, because a
delete must never act on a guess. Conditions 5 (`git status --porcelain`) and
3/5 (`WorktreeInUse`) stay live and unchanged — a destructive decision
re-verifies the filesystem itself.

That is what closes the leak the E-2087 hotfix accepted: condition 4 becomes the
exact content answer again, so a worktree whose work landed under rewritten SHAs
with no `task_landings` row is finally reclaimable, and the ◆ marker,
`task unsettled` and the reaper agree about "landed" once more.

**Removing the reaper from the hook path is the other half**, and it is
subtraction only: delete the five `ReapWorktreesForProject` calls in
`internal/hookcmd/claude.go` (SessionStart, PreToolUse, PostToolUse, Stop,
SessionEnd). Nothing replaces them. Reaping was already happening at land; the
hook copies were duplicating it before and after every tool call.

## Who computes and who does not

**Never computes — cache-only (ED-1589):**
`monitor.AnnotateSessionStatusUnsettled` (the ◆ column in `session status` and
`session monitor`). A missing or invalid entry yields "not yet computed", never
a fabricated verdict. This is the change that removes the continuous range-diff
load: **measured 584ms per row for e-1077, gone from every tick of every pane.**

**Computes on a miss, and writes what it computed:**
- `session-query worktree-unsettled` (the Go entry point Python's `task
  unsettled` shells to) — a direct question deserves a real answer.
- The reaper's condition 4 — a guess is not acceptable before a delete.
- `internal/unlandedjob` — it is the writer.

**Misses are computed CONCURRENTLY through one bounded pool**, shared by the
batch probe and the job's cold pass. `task unsettled --all` batches every active
worktree into a single `session-query` call, so a cold cache would otherwise
cost ~0.6s per worktree serially — over a minute of silence before the first row
prints. With the pool it is bounded by pool size instead.

Pool size is `min(8, runtime.NumCPU())`: git is CPU-bound here (patch-ids) and
oversubscribing one repo buys nothing. Serial callers — the reaper computing one
condition-4 answer, `task unsettled <id>` on one worktree — do not enter the
pool.

**Stays live everywhere, never cached:** `git status --porcelain`. Filesystem
state changes without any ref moving, so it has no honest cache key. Measured
15-27ms per worktree; a pane renders a handful of rows (this session's view
renders 2), so the live cost is tens of milliseconds per tick — three orders of
magnitude below the range-diff it replaces.

## The fourth marker state

`unsettledMark` currently has three states: `◆` unsettled, `⊙` no work product,
space settled. Cache-only reading introduces a fourth, transient state — "not
computed yet" — and collapsing it into either `◆` or space would be a lie the
column already refuses to tell.

New glyph: **`~` (U+007E TILDE)**, meaning "not yet determined".

`·` was the obvious pick and is WRONG: `sessionstatuscmd` already defines it as
`referencedGlyph` (in `relation_tier.go`) and `buildLegend` prints it as
`· referenced`. In a row, position disambiguates (unsettledMark precedes the id,
relationField follows it) — but the legend has no position, and a frame holding
both states would print `~ not yet determined  · referenced` on one line under
one glyph. Flagged by the E-2017 session.

`~` clears the whole vocabulary in play in a single frame — actions
`● ↑ ↩ ⟳ ▶ ⚑ ✎ ☑ ◷ ⏚ ⁇ ⇥ ◌`, unsettled `◆ ⊙`, phase `✓ ! 1 2 3 ?`, hidden `⊘`,
relation `⊕ ·`, block `⊗ ⏸`. Being ASCII it is display width 1 BY DEFINITION,
which sidesteps the East Asian Ambiguous trap that forced `⊙` to be asserted
rather than assumed (E-1765, E-2107) — the width test is still written, but it
cannot fail. Its silhouette is a horizontal wave, colliding with nothing in a
set of circles, diamonds, arrows and boxes; `◌` being taken is what rules out
every dotted-circle variant. "Approximate, unresolved" is the right reading.

**Precedence: `~` is tested FIRST.** If the expensive answer has not been
computed, the row says so rather than reporting a state derived from something
else — so `~` outranks `◆`, `⊙` and blank:

```
case !r.UnsettledKnown: "~"
case r.Unsettled:       "◆"
case !Shipped:          "⊙"
default:                " "
```

Two refinements keep `~` from swallowing rows whose answer IS known, and both
fall out of what each probe costs rather than being policy:

- **A task with no worktree is KNOWN**, not unknown. There is nothing to land
  and no git ran, so `UnsettledKnown` is true and the row resolves to `⊙` or
  blank as it does today.
- **A dirty worktree is KNOWN to be unsettled.** `git status --porcelain` stays
  live, so modifications are visible every tick without the cache. A row whose
  working tree is modified is `◆` even with no cached commit answer. `~`
  therefore means specifically: the worktree is CLEAN, and whether its commits
  reached the base has not been computed yet.

That makes `~` rarer than the precedence rule alone suggests — it appears on
clean worktrees during the first job pass after a cold start, and on a machine
where nothing fires the job. It is visible only until the job's next pass, and
the monitor tick is what fires the job, so the window is normally one interval.

`buildLegend` documents it on any rendered row that bears it, like the other two.
Like `⊙`, it must not veto `dim`.

## Consequences accepted

- **No monitor running anywhere means nothing is reaped.** Reaping is a TTL-gated
  cleanup with a 14-day default; a machine with no monitor open for a while
  accumulates directories and reclaims them on the next monitor tick. On this
  project, jobs are suppressed inside self-dev worktrees, so it is the
  main-checkout monitor that drives both jobs — unchanged from how the existing
  three already behave. On a stranger's project `InSelfDevWorktree` is false and
  any monitor drives them.
- **A fresh clone shows `·` until the job's first pass.** One interval.
- **E-2113 still matters.** The job runs on a goroutine inside the monitor
  process, so Ctrl-C in a pane still kills in-flight git children and still
  records ERR-0010 against an innocent task. This change shrinks the window
  enormously — the probe is no longer running continuously — but does not close
  it. E-2113 is already filed and is not folded in.

## Not in scope

- **The shared per-repo patch-id index.** Filed as E-2127 (`maybe`). It
  would cut a cold miss from ~584ms to ~100ms, but every miss is now paid by a
  background job off any critical path, and a settled verdict survives base
  movement, so cold-miss storms are small. Measure before building it.
- **Reliable landing recording.** A fourth symptom, not this root cause. Worth
  doing for the ledger's own sake; not required to make this correct.
- **Keeping worktrees in sync with the base**, both directions, which is
  E-1881: endless-managed commits UP to main, which is what makes worktrees
  settle and become reclaimable, then a rebase DOWN into idle worktrees, which
  collapses `baseRange` and removes this probe's cost at the source. It composes
  with this task rather than competing — both steps move the branch tip and
  invalidate that cache entry, but the recompute is then cheap by construction,
  because the drift it would have measured is exactly what the rebase removed.

## What implementation added to this plan

Recorded here because each of these is in the diff and none of it is in the plan
above. Every one was cheaper to do inside this change than to file beside it; the
bound applied was size, not kinship.

- **ERR-0012 `unlanded-cache-unwritable`, with its `docs/errors.md` section.** The
  plan says to "record ONE fault fingerprinted on the directory" when the cache
  cannot be written, and did not say under which code. Reusing ERR-0010 would have
  been wrong: that code means a git probe could not RUN, and here every probe runs
  and every on-demand answer is still exact — what is lost is the ability to
  remember one. So it is a warning with its own remedy, and `internal/faults`
  already asserts every code has a documented section.

- **The base branch NAME is percent-escaped in the watermark's filename.** The plan
  specifies `base-<name>` and takes the orphan-on-rename property from it, but a
  branch may contain `/` — `release/2.0` is an ordinary default branch on someone
  else's repository — and an unescaped name would not be one path component.
  Escaping keeps both properties: injective, reversible, one component.

- **The cache stores the unlanded lines UNBOUNDED, not capped at
  `unlandedLogLimit`.** The plan says the stored contents are bounded by that limit
  and "the count is the line count". Those two cannot both hold: with no file
  format the line count IS the count, so truncating to 20 would silently cap
  `UnlandedCount` for exactly the worktrees that have drifted furthest, and
  `TestUnlandedLogIsCappedButTheCountIsNot` pins the opposite. The reader applies
  the display cap instead, identically to the computing path.

- **The cache-only reader takes the base TIP from the watermark, not from git.**
  The plan's validity protocol reads as the job's, and the display-path bullet says
  readers get the base from the watermark and do not resolve it at all. Following
  that literally means a reader addresses `unsettled/<base-tip>/` through the
  watermark's stored tip, so a non-zero verdict can be at most one job interval
  stale — the same window a cold start already has, and the price of a display that
  runs no git beyond `status` and one `rev-parse HEAD`.

- **The per-repo pass resolves the base tip with `rev-parse`, not from
  `git worktree list`.** The plan takes the base branch's own tip out of the
  worktree listing, which only works when the base is checked out in some worktree.
  That is true of this project and not of a repository whose main checkout sits on
  a feature branch, so the pass asks for it directly — one extra call per pass.
