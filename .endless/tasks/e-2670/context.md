Preparing a Go package for a tagged release is the same job every time: commit and push pending work, make every versioned module require published sibling versions with no `replace` outside `test/` and `examples/`, run build, vet and tests with `GOWORK=off`, and propose a semver version and release description per module for the owner to tag through the Release workflow. One session filed that task for go-cliutil, go-testutil and go-logutil with the same plan text three times, only the package name changing; the go-cliutil one became unnecessary when the owner tagged a release first.

Mike asks whether Endless should gain one or both of: task templates (a stored plan and item set with parameters, instantiated into a task), or user-defined task types (a type beyond todo, bugfix, research, epic and brainstorm, with its own fields, statuses and gates).
