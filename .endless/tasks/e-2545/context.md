He had edited go-dt, go-cliutil, go-cfgstore and gomion in their main checkouts (a StdIO type and a RunCLI signature), and the task worktree for E-2540, branched from main, could not see the gomion edits.

What the planning session did instead, found on 2026-11-13 while investigating E-2551: it filed one task per repo, then ran `task claim --unattended` on all four to get worktrees, applied Mike's diff in each worktree, committed it there and reverted main. Each task was left underway with no session bound, which `session goto` cannot reach and `task spawn` silently adopts. E-2621 removes the flag.

Mike's framing, 2026-11-13: this was never "I need a worktree". A worktree without a session is an orphan Endless chose never to create, and a spawned session always gets its own. The need was to adopt edits made outside any task: get them off main and under Endless. The session could have created a branch, reset main, and delegated everything else to project-specific tasks whose spawned sessions bring the edits into their own worktrees.

Things to settle: 1) the holding branch: Mike proposes `wip/E-NNNN`, named for the task that will consume it; it must not be the task branch itself, because worktree creation refuses a pre-existing task branch that carries real work and leaves the keep-or-discard choice to the user; 2) how a task names the branch and commit it consumes, and how its spawned session brings them into its worktree (cherry-pick, apply, merge) and what happens to the holding branch after; 3) whether Endless needs a verb for the branch-and-reset step or a documented git recipe is enough; 4) how such edits interact with bespoke tasks, related or concurrent tasks, or no task at all; 5) anything else found for these cases.
