Found 2026-10-27 from go-dt's ES-1369. E-2444 precedes E-2445 (task_deps row: source E-2444, target E-2445, dep_type precedes), both rows appear in session status's table, yet the ordering graph under the table shows no 'E-2444 -> E-2445' line; it does show 'E-2449 => E-2440'. Mike has seen '->' lines work in many sessions, so this read as a regression.

Cause, read from the code: graphSeeds (internal/sessionstatuscmd/graph.go) leaves out rows stewarded by another session; E-2444 is claimed by ES-1372, so it is not a seed. SessionGraphData (internal/monitor/session_graph.go) then adds predecessors of the node set, but its recursive walk follows only dep_type = 'blocks', so a precedes predecessor is never added. buildOrderGraph draws an edge only when both ends are nodes, so the edge is dropped. A blocks predecessor in the same position would be drawn. The seed rule and the blocks-only walk came in with E-2345 (commit bbb43d506, 'Draw the session task's blocker chain in the status graph'); '->' still appears when both tasks are this session's own seeds, which is why it has been seen working.

Likely fix: let the predecessor walk in SessionGraphData follow precedes as well as blocks, so a soft predecessor stewarded elsewhere still enters the graph and its '->' is drawn; add a test with a precedes predecessor stewarded by another session.
