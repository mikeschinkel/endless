One new built-in check in `endless task verify`, written in Go beside the runner, plus its documentation.

**The check.** A new package, `internal/gomodcheck`, holds the pure parts and one runner: `Modules(worktree)` finds every go.mod under the worktree outside `.endless/`, `vendor/`, `testdata/` and `.git/`, the rule `go_support.go_modules` uses; `RerootModfile(src, mainModuleDir, dst)` copies a go.mod rewriting each replace path that begins with `./` or `../` to the absolute path it resolves to from `mainModuleDir`, and copies the go.sum beside it; `Run(moduleDir, mainModuleDir)` writes the copy into a temporary directory, runs `go mod tidy -diff -modfile=<copy>/go.mod` with GOWORK=off and `moduleDir` as the working directory, and returns pass, or the diff and go's stderr on exit 1, or an error for any other failure. `mainModuleDir` is the module's path relative to the worktree root, joined to the main checkout root (the parent of `git rev-parse --git-common-dir`). The check is skipped as a whole when the main checkout root contains a go.work.

**Wiring in the runner.** `internal/verifycmd` runs the check before the suite's own checks, once per module found, and reports each as a check row named for the module (`go.mod is tidy without go.work` for the root, with the module's relative directory appended for a nested one). The row carries the diff and the remedy, `go mod tidy` in that directory followed by a commit, when it fails, and it is fail-fast like the suite's first native test. With no Go module in the worktree nothing is added, so non-Go projects see no change. The `go` on PATH is the one used; a `go` older than 1.23 fails the row naming the version.

**Tests.** `internal/gomodcheck` tests with the real `go` tool: a module whose go.mod understates a transitive requirement fails with a diff naming the version; a tidy module passes; a module with a relative replace that resolves only from the main checkout's location passes after re-rooting; a replace for a module not in the require list is tolerated; nested modules are each found and the excluded directories are not. A `verifycmd` test shows the row first in the report for a Go worktree, absent for a non-Go one, and absent when the main checkout has a go.work.

**Docs.** `.endless/tasks/CLAUDE.md` gains a short section under "Writing one" saying that every Go worktree's run begins with this built-in row, what it checks, and the remedy; the "per-task verification suite" topic in `docs/guide/orchestration.md` gets one sentence pointing there.

**Endless itself.** On landing, the first Go task to verify meets the row; its go.mod is tidy as of E-2357's land fix, so it passes unless something drifts again.
