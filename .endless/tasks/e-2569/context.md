Found while landing E-2357 on 2026-11-07. The land fast-forwarded main, then its build of the installed endless-go failed with "updates to go.mod needed": endless's go.mod required go-dt v0.7.0 while the local go-cliutil checkout it is replaced with, raised by E-2520, requires go-dt v0.7.1. The drift had sat on main since E-2520 landed, and every verify and every pre-merge build in between passed. The fix was one line of `go mod tidy`, but it had to be made in the main checkout outside any task, and E-2357 then needed a fresh verify because the failed land's rebase had moved the branch.

Why nothing caught it: Go's workspace mode. When a go.work is in effect, `go build`, `go vet` and `go list -m all` all accept a go.mod that understates a requirement; with GOWORK=off the same commands refuse with "updates to go.mod needed". Proven on a toy module during planning. E-2563 writes a go.work into every Go task worktree, so every verify runs in workspace mode while the main checkout, which has no go.work, does not. Endless's own worktrees also carry replace directives in that go.work, written by the project's post-worktree-create hook through `just go-work-init`, but they are not the mask: a go.work holding only `use .` masks the same way.

PRODUCT: a user's plain Go project gets the same go.work from E-2563 on day one, and the land builds nothing on main outside self-dev, so for them the drift surfaces nowhere at all. Their main checkout simply stops building, with no message from Endless.

One more fact shapes the fix: endless's go.mod replaces its go-pkgs modules with paths relative to the main checkout's parent directory. From a task worktree, three directories deeper, those paths do not exist, so a plain `go mod tidy -diff` in the worktree fails with "replacement directory does not exist" before it can say anything about drift.
