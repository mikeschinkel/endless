Every task belongs to one project, and each project's repo has its own db-ledger. Work that spans projects has no home: a task in one project can't change another project's repo, so the work is split into one task per project and the coordination lives in no task.

Motivating case: gomion E-2454 (2026-10-28) built `gomion repo setup` to generate CI and Release workflows for 14 go-pkgs repos, each its own Endless project. Mike said E-2454 should not edit those repos, only file tasks in them, and later confirmed that rule applies to cross-project work generally. The result was 14 near-identical adoption tasks (E-2464 to E-2467, E-2469 to E-2478), each blocked by E-2454, and nothing that tracks the rollout as a whole.

Mike's idea (2026-10-30): at first a single special project for "global" concerns, but grouping projects is more useful, for example all xmlui-related projects. So, rather than one special project, a new project type: a group of other projects. Its members could be named projects, all projects, or a formula, such as all Go projects. A task in a group project is a cross-project task, able to do what it needs to update the member repos, each with its own db-ledger.

Related work: E-2254 adds a group task type (children within one project, coordinated by a session), not a group of projects. E-816 pairs local and global task ids for cross-repo dependencies. E-2426 reads across project databases over ATTACH, read-only. E-2247, E-2249 and E-2244 cover cross-project links and their visibility. E-1862 is the same gap for decisions that apply to all projects.
