A controlling task creates and tracks one child task per member repo; it does not change member repos itself. Mike ruled out one task changing several repos directly, because that would violate the invariants of Endless's architecture (2026-11-05). Open points for the plan: how a child's worktree sees sibling children's in-progress code when they depend on each other, for example a go.work in each child worktree pointing at the sibling worktrees, created together; the order children land in when one depends on another's release; and how the controlling task's status follows its children.
