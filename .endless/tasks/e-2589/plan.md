Two kinds of self-clearing failure, handled two ways.

**Transient failures** clear on their own without anyone confirming why: a refused tmux connection, a brief network loss, a single API error. They are logged, and they become a fault only when they repeat past the source's threshold. The job runner already does this for jobs (`jobs.Transient`, `jobs.TransientThreshold`, E-2260), and main-sync already marks an unreachable remote transient (`unreachable` in `internal/mainsyncjob`). This task extends that mechanism to sources outside the runner — `monitor-wake` and the stopfailure hook — rather than building a second one.

**Outages** are confirmed by the provider's own status page. An outage is a new kind of record, not a fault: it opens when a provider's status API confirms an incident on the component a failure depends on, and it closes itself when the status API reports the component operational. It never needs clearing and carries no action hint.

- **Providers.** A provider is a Statuspage base URL (its `api/v2/summary.json` endpoint, e.g. https://www.githubstatus.com/api/v2/summary.json) plus the component to watch. GitHub ("Git Operations") and Anthropic (the Claude API) both use Atlassian Statuspage, so both ship. A git remote on github.com maps to GitHub; an API-error stop maps to Anthropic.
- **Opening.** When a git remote operation against github.com fails — any failure, an authentication failure included, since GitHub answered `Permission denied (publickey)` during its 2026-11-04 incident — Endless asks the status API. If the component is degraded, it opens (or extends) the outage and raises no fault. If the status API fails or reports nothing, the failure is handled as today: unreachable is transient, an authentication failure is a fault. GitHub posts incidents late or not at all, so the status check never stands in for the threshold.
- **Polling.** One outage-check job in the job runner polls each provider with an open outage once a minute, and makes no request when none is open. Monitors read the outage records from the database; no monitor polls. Closing a GitHub outage makes main-sync due at once instead of waiting out its backoff.
- **Showing.** `session status` and `session monitor` show each open outage on its own line under the fault row, in a calm colour (not the warning or error colours), with no `Run eeh` hint — in a short, scannable form: `Outage[GitHub]: Degraded for 4h59m; polling every 1 min` — a duration, not a start time, so the reader need not do clock arithmetic (`9m49s` under an hour, `4h59m` above). `endless errors list` shows open outages under their own "Outages" heading above the faults; `--all` adds closed ones as history. Agents receive open outages through hook context, so a failed push during an outage is not debugged as a local problem.

**monitor-wake.** Concurrent wakes coalesce rather than being spaced out: a wake takes a non-blocking lock under the tmux server's runtime directory; a wake that finds it held sets a rerun flag and exits, and the holder runs once more if the flag is set. A refused connection (`no server running` while the socket file exists) is retried with jittered backoff for about two seconds before it counts as a failure, and WARN-0033 becomes transient.

**API-error stops.** The stopfailure hook treats `unknown`, overloaded, rate-limited and server errors as transient per session, and opens an Anthropic outage instead when the status API confirms one. `max_output_tokens`, authentication and billing errors stay faults on first occurrence.

Touches `internal/jobs` (transient handling reused outside the runner), `internal/mainsyncjob`, `internal/monitorvis` (`RunWake`), `internal/hookcmd` (stopfailure, hook context), `internal/faultrow` and the status views, `endless errors list`, a new outage store and outage-check job, `docs/errors.md` and the guide.

**History for later classification.** Each closed run of transient failures records its fingerprint, how many occurrences it had, and how long it took to clear (or that it became a fault). Today the transient phrase lists are written by hand; with this history, a later change can classify a message pattern as "passes", "doesn't pass" or "might pass" from evidence, and set each pattern's threshold from how long it usually takes to clear.
