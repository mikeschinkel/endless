A fault source can declare a failure transient. A transient failure is written to the detail log with its occurrence, and becomes a fault only when it persists past a threshold the source sets (consecutive failures, or a duration). The first success after a run of logged failures closes that run without a fault. A non-transient failure is a fault on first sight, as today.

**GitHub outages.** When a git remote operation against github.com fails, main-sync (and the land's push and fetch, which share the git helpers) asks GitHub's status API (`https://www.githubstatus.com/api/v2/components.json`, the "Git Operations" component; `summary.json` for open incidents) whether Git Operations is degraded. If it is, the failure is not a fault: Endless shows a notice — on `session status` and to agents through the same channel faults reach them — naming the incident and its status page, and clears it when the status API reports the component operational. If the status API itself fails or reports all operational, the failure falls through to the transient threshold, since GitHub posts incidents late (the 2026-11-04 incident was posted nine minutes after the first failure) and sometimes not at all. Status lookups are cached for a few minutes so a burst of failures makes one request. A remote on another host gets only the threshold; the status check sits behind a per-host provider so another host's status page can be added later.

**monitor-wake.** Coalesce concurrent wakes instead of spacing them out: a wake takes a non-blocking lock under the tmux server's runtime directory; a wake that finds the lock held sets a rerun flag and exits, and the holder runs once more when it finishes if the flag is set. One wake then answers a burst of hook events with no added latency. A refused connection (`no server running` while the socket file exists) is retried with jittered backoff for up to about two seconds before it counts as a failure, and WARN-0033 becomes transient.

**API-error stops.** `hook:stopfailure` treats error types that pass on their own (`unknown`, overloaded, rate-limited, server errors) as transient per session, and raises WARN-0013 only when one session repeats them past the threshold. `max_output_tokens`, authentication and billing errors stay faults on first sight.
