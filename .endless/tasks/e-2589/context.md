Endless raises a fault on the first occurrence of failures that clear on their own, so `session status` fills with warnings the user learns to ignore. A triage on 2026-11-09 found three, all cleared since:

- **WARN-0033, monitor-wake (184 occurrences).** All read `no server running on <socket>` for the endless-tasks tmux server, in two one-minute bursts (38 on 2026-10-29 16:03 UTC, 146 on 2026-11-07 04:42 UTC). The tmux server had run without a break since 2026-10-16. tmux prints "no server running" for any refused connection (ECONNREFUSED), not only for an absent server. A test confirmed it: a throwaway tmux server frozen with SIGSTOP for one second refused 123 of 250 concurrent clients with exactly that text, matching macOS's listen backlog (kern.ipc.somaxconn = 128). Every tmux hook event (client-attached, client-detached, client-session-changed, session-window-changed) runs its own `run-shell -b endless-go monitor-wake`, so a run of events piles concurrent wakes onto the server.
- **WARN-0001, job main-sync (11 occurrences).** `git fetch origin` failed with `Permission denied (publickey)` on 2026-10-30 14:21–14:26 UTC (endless) and 2026-11-04 09:40–11:11 UTC (go-cliutil). The key and agent were fine throughout. The second window matches GitHub's posted incident "Pull Requests, Git Operations and Issues", 2026-11-04 09:49–11:50 UTC. GitHub posted nothing for the first.
- **WARN-0013, hook:stopfailure (5 occurrences).** One gomion session's turns ended on API errors of type `unknown` across forty minutes on 2026-10-31. The catalog's own remedy says "usually nothing but take the turn again".

Mike's direction: a transient failure should not become a fault on first sight, GitHub outages should be detected through GitHub's status API and shown as a notice, and error types the user must act on — a reply cut off at the output-token limit — stay faults immediately.
