Today setup problems only surface after something fails, spread across errors list, worktree check and jobs list. Design from the doctor brainstorm: doctor reports problems only, ordered by severity then scope, and points to --suggestions, which lists unset opt-in settings with reasons from the settings registry. Errors and job health are folded in. --accept <check-id> --reason records a problem the user chooses to live with, at the check's scope and bound to the observed condition; accepted problems are counted and listed with --accepted. --fix has three tiers (auto, confirm, advice only) and is user-only. --all-projects runs per-project checks in every registered project plus cross-project checks such as stale or duplicate registrations. Checks run in Go via endless-go; only --suggestions depends on the settings registry.

Design note (a choice for this work, not an architectural decision): worktree check becomes a thin alias for doctor's worktree scope, running the same checks with the same output, while keeping its handoff contract (silent when clean, same exit code, failing on errors only). Adding a worktree-scope check to doctor then adds it to the handoff gate automatically, and the gate cannot drift from doctor. Chosen because worktree check's purpose is opaque to users and nobody would think to look for it.
