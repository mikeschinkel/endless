# Which tmux server each endless command may run on

## Recommendation

Where a command is typed and which server it acts on are separate questions. Endless should allow a command to be typed anywhere, and should make it act only on Endless's own servers, addressed by socket path.

| # | Question | Answer |
|---|---|---|
| 1 | Refuse outside an `endless-*` server? | **No blanket refusal.** A command refuses only when the server it needs is not running, or when its job is to replace the current pane (`session resume`). |
| 2 | Console, tasks or neither? | By class, in the table below. Most commands need no server. |
| 3 | Add an `endless-scratch` server? | **No.** Commands that need no server have nothing to run on it. |
| 4 | May a hook bind a pane off `endless-tasks`? | **No.** Bind on `endless-tasks`, block on `endless-console`, and touch no tmux anywhere else. |

## Command classes

| Class | Commands | May be typed | Acts on | When the server is down |
|---|---|---|---|---|
| No tmux | task and decision commands, `project register`, `setup`, `guide`, `jobs run`, `event emit`, verify | anywhere | nothing | works |
| Tasks server | `task spawn`, `task prime`, shell `task claim`, `session goto`, `session back`, `session resume --new-window`, `resume-windows`, `session monitor --restart`, `stop tasks` | anywhere | `endless-tasks` | refuses with "Endless isn't running"; `stop` reports already stopped |
| Console server | `project monitor --tmux`, `stop console` | anywhere | `endless-console` | same |
| Both servers | `start`, `stop all` | anywhere | both | `start` starts them |
| Replaces this pane | `session resume` | a pane on `endless-tasks` only | that pane | refuses and names `session goto <ref> --resume` |
| Run by tmux inside a server | `tmux status-line`, `show-menu`, `monitor-wake`, `record-windows`, `spawn-launch`, `tmux init` | generated by Endless, not typed | the server named by `--socket` in the generated line | does not run |
| Live views | `session monitor`, `project monitor` | anywhere | their own pane, on an Endless server only; elsewhere they run as they do outside tmux | works |
| Claude hooks | every hook event | n/a | see below | n/a |

`tmux apply` and `tmux init` should stop acting on the caller's server, because that is how Endless's status line, key bindings and hooks reach a user's own tmux.

## The rule for `$TMUX`

The proposed ED-1673 and the earlier plan say a command never reads `$TMUX`. That cannot hold: `session resume` and the hooks have to know where they are running, and only `$TMUX` says.

The workable rule: **`$TMUX` may answer "am I in a pane of an Endless server, and which one?" by comparing its socket with the configured sockets. It never supplies the address.** `$TMUX_PANE` is trusted only after that match. `tmuxservers.InTasksServer` and `session_cmd._own_tasks_pane` already work this way.

Proposed ED-1673 wording:

> Endless's tmux work happens only on the two servers it starts, endless-tasks and endless-console, each addressed by the socket path from the tmux settings. A command may compare $TMUX with those sockets to learn whether it is running in a pane of one of them, and must not otherwise use the caller's server. Endless never changes the user's own tmux servers. Commands can be typed anywhere; a command refuses only when the server it needs is not running or when it must replace a pane on endless-tasks. tmux is the multiplexer Endless integrates with today, not a permanent requirement: Endless expects to support other multiplexers through an abstracted integration, and this rule then applies to whichever servers Endless starts.

## Claude hooks

| Claude runs on | Hook behavior | Session reads |
|---|---|---|
| `endless-tasks` | binds the pane, as today | `live` / `dead` |
| `endless-console` | message at SessionStart, every prompt refused | n/a |
| The user's own tmux, a plain terminal, an IDE terminal | activity, task context and gates still run; no tmux call, nothing stamped | `unbound` |

The console block is your planning answer, and the evidence supports keeping it: no headless `claude -p` child depends on a hook. `run_internal_claude` sets `ENDLESS_NO_HOOKS`, and the triage sender passes `disableAllHooks`.

**What this costs.** Endless learns that a session is gone in one of two ways: Claude's SessionEnd hook reports it, or the session's recorded pane has disappeared. A crash skips the hook, so only the pane can show it. Under this rule, a Claude in the user's own tmux has no recorded pane, the same as a plain-terminal Claude today. It reads `unbound`, and Endless counts `unbound` as still present because it cannot prove the session is gone.

While that Claude is running, nothing is lost:
- **A second session in the same worktree:** the worktree lock still keeps it out (`worktreeLockHeldByLiveOther`).
- **Resuming a running session:** still refused, because the process listing finds it (`_running_session`).

After it crashes and its pane closes, the two cases differ like this:

| After the crash | Session with a recorded pane | Session with no recorded pane (`unbound`) |
|---|---|---|
| `session status`, `worktree` guards | reads `dead` | stays present until someone ends it |
| `task claim` or `task spawn` on its task | refused, and names `session goto E-N --resume` | refused, says the task is "already active" in pane `?`, and names `session goto E-N`, which then points to `--resume` |
| A fresh `claude` started in its worktree | not bound; told to use `session goto E-N --resume` | same |
| Worktree reaper and `worktree drop` | may remove the worktree | treat the worktree as in use |

The task is not stranded. A task continues only from the session that held it (E-2418), so the refusal itself is the same with or without a pane. `session goto E-N --resume` reopens the crashed session in a new window on `endless-tasks`. `session end ES-N` clears the stale session, after 10 minutes without activity or sooner with `--force`.

The real costs are a session that looks present after it has gone, a misleading refusal, and a worktree that stays protected until someone ends the session. A recorded pane has a limit too: if the pane stays open after Claude crashes, that session keeps reading `live`, because liveness checks the pane and not Claude.

I'd accept that cost. The misleading refusal is worth fixing in the follow-up task. Binding by OS process would remove the rest, and `processes` already has a `pid` kind, but nothing writes that kind today and no reported problem calls for it yet.

## PRODUCT

- **Someone who does not use tmux:** every no-tmux command works, and Claude is tracked as `unbound`. Spawning and `goto` need `endless start`, and they say so.
- **Someone who uses tmux for their own work:** Endless never changes their servers. Claude works there unbound.
- **Someone who uses another multiplexer:** tmux is not a permanent requirement for Endless. This policy describes today's tmux integration, and Endless expects to support other multiplexers by abstracting its integration points. The rule carries over: Endless acts only on the servers it starts, addresses them explicitly, and leaves the user's own alone.

## Entry points checked

Run with both servers stopped and `$TMUX` unset, on a private socket directory:

| Entry point | Result |
|---|---|
| `jobs run`, `task list`, `task add`, `hook prompt`, `hook claude` outside tmux | work; fit the policy |
| `task spawn`, `task prime`, `session goto`, `session resume`, `resume-windows`, `project monitor --tmux` | refuse with "Endless isn't running"; fit the policy |
| `stop --all` | reports already stopped; fits the policy |
| `tmux show-menu`, `session monitor --restart` | **depart:** raw tmux connection error |
| `tmux apply`, `tmux init` | **depart:** tell the user to run them inside their own tmux |
| Verify runner | stays on its private servers (`verifycmd` tests under a logging `tmux` wrapper; `task verify` itself was not run) |
| `project register` | not completed: the worktree build refuses the scratch main database. Code read found no tmux call |
| `endless start` | started the console on the private socket directory, then stopped at the same database refusal, so its tasks-server half was not exercised |

## Where today's code departs

1. **Hooks use whichever server `$TMUX` names.** `TouchSession` can stamp `@server_uuid` there, and `setTmuxSessionUUID` writes a window option. `hook prompt` runs from the zsh prompt and stamps `@session_uuid`, `@window_uuid` and `@pane_uuid` on the user's own servers.
2. **Pane identity uses the ambient server.** This is `monitor.TmuxServerUUID` and its callers, plus two bare reads in `task_cmd`.
3. **Generated command lines do not carry their socket,** apart from `record-windows`. `Server.Init` fakes `$TMUX` to aim `tmux init`.
4. **Live views install global hooks and pane tags on whichever server holds them.**
5. **Tests reach the live servers, and still pass.**
   - Run from an `endless-tasks` pane, the Go `hookcmd` and `monitor` tests sent 130 calls at the live server, all refused by the wrapper. 47 would have overwritten `@endless_session_uuid` on real windows.
   - `tests/conftest.py` sets a `tmux.socket_dir` that gives a 151-byte socket path on macOS, over the 103-byte limit. `Resolve` rejects it and `tmuxservers.SocketDir()` falls back to the real directory, so liveness probes the live servers.
   - The `resume_harness` fixture in `tests/test_continue_from_earlier_session.py` fakes `$TMUX` with the user's real default socket.
