Every `endless task verify` in a Go worktree first runs the built-in "go.mod is tidy without go.work" rows (E-2569): `go mod tidy -diff` under GOWORK=off per module. They run in `runGoModChecks`, called from verifycmd's verify flow before `runSetup`, with the run's isolated env and nothing from the suite. verify.toml has no key that sets environment variables.

That breaks a suite whose modules require versions that exist only once the task lands. E-2440 (go-tealeaves) makes every publishable module require its siblings at the tags its release.sh creates after landing (`teautils v0.5.4`, `teacolor v0.1.1`, ...). Its own suite checks tidiness against those exact tags: setup.sh zips the proposed tags from the commit into a file GOPROXY, so the hashes match what sum.golang.org will record, and its tidy check passes. The built-in rows can't see that proxy, so 14 modules fail with "unknown revision teautils/v0.5.4". Their remedy ("run `go mod tidy`") fails the same way.

The rows describe main correctly: main already requires those tags since E-2440's first landing, and only the release fixes it. But nothing in the suite can show the check the versions the release will publish, so E-2440 cannot verify green until the tags exist.
