Yes — five things felt either missing or wedged into the wrong slot:

**1. Test probes don't fit anywhere clean.** I created E-1290, E-1292, E-1299 just to emit synthetic events for verification. They're not real work, but they're real task IDs that will linger forever as `needs_plan`. I put them under `<tasks>` with prose notes saying "can be obsoleted," but that's me asking a future reader to act on prose. Either (a) the XML should have a `<test-probes>` section with auto-obsolete semantics, or (b) the right answer upstream is `endless task add --ephemeral` that auto-marks obsolete after N days. The fundamental gap: I had no structured way to say "this task ID exists only because I needed an artifact, not because we owe it work."

**2. Cross-session surfacing has no slot.** I wanted to flag "E-1309 is the root cause — another session should pick it up" prominently. I crammed it into a `<task status="needs_plan">` entry plus a sentence in `<notes>`. That gets the data into the row but doesn't *signal* to another session reading my status: "hey, this is for you." A `<for-other-sessions>` or `<handoff>` element that the web UI/CLI could highlight differently would close that loop.

**3. Resolution patterns are runbooks, not notes.** My `<notes>` ends with a multi-sentence procedure for diagnosing-and-resolving the ledger rebase conflict (head/tail diff → verify superset → take main → skip). That's a *runbook* — generalizable, applies to any future session hitting the same conflict, should be findable by anyone who hits the conflict, not by anyone reading session ES-356's status. The right home is probably a memory entry or `~/.claude/LESSONS.md`, but at the moment of capture, the status flow was the natural sink. A `<lesson>` or `<runbook>` element that *prompts* me to also write the memory entry — and maybe even generates a draft — would convert the burial into propagation.

**4. Multi-phase sessions get flattened.** This session had two clearly distinct arcs: status-line/menu polish (E-1245 through E-1258) and per-session-tracking infrastructure (E-1284 through E-1317). My `<headline>` captures only the second arc. The latest-row-wins design means readers see only the most recent phase. I could add multiple status rows mid-session, but I didn't think to — and the design doesn't prompt me to. An `<arc>` element or a CLI nudge like `you haven't recorded a status in N hours; want to capture a checkpoint?` would help.

**5. Empty sections clutter the rendered output.** My status produced `## Blocked (empty)`, `## Verify (empty)`, `## Commits (empty)`, `## Memory (empty)`, `## Summary (empty)` — five "empty" headers eating screen space. For chat-readability the renderer should suppress empty sections by default; add a `--show-empty` flag if completeness ever matters. Same for the CLI's display.

**Bonus #6 (minor):** the rendered markdown shows task IDs without titles — `E-1284` not `E-1284: Add session_id to event Actor...`. The CLI knows the titles (it has DB access); auto-joining would make the status self-documenting for someone reading without prior context.

**Bonus #7 (structural):** observations of *new bugs* (my note about main's `commit --amend` pattern) belong in tasks, not status. The status XML has no slot like `<to-file>` that would prompt me to convert observations into `endless task add` calls. Without that prompt, observations die in `<notes>`. Either a structured slot that auto-files at insert time, or a post-insert nudge like `you mentioned 1 observation worth filing — want to add a task?`.

Of these, **#1 (test probes), #2 (cross-session handoff), and #3 (runbook capture)** are the structural gaps I'd prioritize. **#5 (empty sections), #6 (task titles), and #7 (to-file slot)** are cheap renderer/UX wins.
