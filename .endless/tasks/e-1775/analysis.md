Reference: glow renders tables via glamour → lipgloss/table (github.com/charmbracelet/lipgloss table/resizing.go). Its resizer computes per-column min/max/median cell widths, expands-to-fill when narrow, and shrinks via three passes (shave columns >= half-width, shave most-over-median, shave biggest) with NO floor. Two flaws we deliberately avoid: (1) headers are hard-coded to height 1 even with wrap on, so a shrunk column TRUNCATES the header with … ('Frequency'→'Fr…'); we instead wrap headers to 3 rows then truncate WITH a legend. (2) shrink uses cell-width min/median, never the longest word, so a column can be squeezed below its longest token and lipgloss then breaks mid-character ('high'→'hig'/'h'); we instead set a computed minCol floor = floor(W/(N*2.5)) and hard-break only tokens that exceed the allocated width.

Why build our own allocator, not import lipgloss/table: (a) it bakes in both flaws above; (b) it pulls in lipgloss + x/ansi, breaking mdterm's deliberate 'no third-party style deps, same surface as the goldmark parser' design; (c) it over-pads (expands to fill full width). We borrow its ideas (min/max/median, shrink-biggest, shrink-to-median), not its code.

Panning: less 668 pans horizontally on-demand via arrow keys (man: RIGHTARROW '...acts as though -S were in effect' while scrolled), so we need NOT launch with -S (which would break the prose no-reflow-but-soft-wrap design). less slides raw text (half-screen default step), not column-snapping like a TUI grid, so it's gentler than teagrid — but we still cap column width (maxColFraction ~0.65W, hard cap W-minCol) so >=2 columns stay visible and panning reads as sliding.

Constants (minColDivisor 2.5, maxHeaderRows 3, targetMaxRows 6, maxColFraction 0.65) have no closed-form optimum — they are balanced empirically via the eyeball-tuning harness in the plan.
